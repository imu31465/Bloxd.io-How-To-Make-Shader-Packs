# Guía de migración a API v5

> Versión: 5 · Estado: Historical (guía de migración de la era; el build objetivo se indica en el texto)

Build objetivo: `ab90qa.main.6188124c.js` — **en producción y preprod simultáneamente (medido 2026-11-03)**, y los dos bundles vuelven a ser idénticos byte a byte (md5 `fc3322212d15be2445c0e8dfc9733fcc` en el bundle principal, descargado en vivo de ambos hosts), así que todo lo que sigue se aplica a producción tal cual. Es la mayor revisión de la API desde v3: el bundle principal creció a 3,39 MB (+115 KB sobre el último build v4), el mapa de chunks tiene ahora 195 ids (c0–c195, 188 emitidos tras los 7 huecos conocidos), el pipeline de sombreadores sigue en el clúster c51–c56 (cargador c53, validador/cabecera/constructor del registro c55, WebGPU/codegen c56, niebla c9) — pero la plantilla del pack por defecto se movió a c116 (estaba en c124 en `tcwczu`). Ninguno de esos detalles de disposición es visible para un paquete. Reverificado en el build de producción actual `xkg8x.main.641a7732.js` (2026-11-04, md5 `f11cc032efd474aca567d3793b792057`): la cabecera del motor es idéntica byte a byte y todas las mediciones de cargador / variantes / hooks / nombres reservados de abajo se re comprobaron sin cambios — la única superficie que se movió es el registro de texturas (896 → 906 nombres utilizables; adenda §80). Preprod (`2lcqcl`) sirve un bundle principal distinto pero midió idéntico en todas las superficies de shader packs. Reverificado de nuevo en `bny9u.main.02116121.js` (2026-11-05, md5 `60eea80ec48253b7ac6cc45604dc8273`, servido byte a byte idéntico por producción y preprod): cabecera, plantilla de pack por defecto, límites del cargador, disposición del uniform, hooks, variantes, macros, nombres reservados y mensajes de validación volvieron a medirse sin cambios; el registro volvió a moverse (906 → 911 nombres utilizables; adenda §80), el número de definiciones de juego creció de 111 a 115 y los chunks del pipeline de sombreado se renumeraron (cargador c54, validador/cabecera c56, WebGPU/codegen c57, plantilla c122).

Lo que *sí* es visible: la cabecera del motor creció de 6.021 a **8.954 bytes decodificados** (151 → 208 líneas) — casi toda estructura ganó campos, cuatro funciones nuevas documentan la propia receta de iluminación del motor, y la máscara de bits `blockFlags` desapareció, sustituida por una estructura `BloxdFlags` de booleanos como Dios manda. La compuerta de compilación `#ifdef BLOXD_LIGHTING` también desaparece: el estado de iluminación pasó al uniform por fotograma como miembro `lit: u32` y se consulta en tiempo de ejecución con `bloxdLit()`. La plantilla del pack por defecto incluye ahora **los nueve hooks** en lugar de seis. Y el espacio de nombres interno del motor `bloxdSp*` creció de 27 a 46 símbolos.

El conjunto de cambios de v5 en una pantalla:

| Área | v4 | v5 |
|---|---|---|
| `apiVersion` de `pack.json` | `4` (estricto) | **`5` (estricto)** — los paquetes v4 se rechazan al cargar |
| Identidad de bloque | `blockFlags: u32` + 6 constantes de bits `bloxdBlockFlag*` | **`flags: BloxdFlags`** — 14 campos bool con nombre (§71) |
| Clases de flag nuevas | — | **`slab` `stairs` `flat` `placed` `held` `dropped` `thrown` `lifeform`** — modelos y entidades ya se distinguen del terreno (§71) |
| Posición de modelo | — | **`localPosition: vec3f`** en toda estructura de entrada (§72) |
| Encantamiento y superposición | solo motor | **entradas + salidas `enchantTier` / `enchantColour` / `enchantSpeed` / `overlayColour`** (§72–§73) |
| Compuerta de iluminación | `#ifdef BLOXD_LIGHTING` (tiempo de compilación, 8 variantes) | **eliminada** — el uniform gana `lit: u32` @ offset 4; prueba **`bloxdLit()`** en tiempo de ejecución; 6 variantes (§74) |
| Ayudantes de iluminación | `litColour` privado del motor | **público**: `bloxdShading()`, `bloxdWorldLight()`, `bloxdLitColour()` (§74) |
| `bloxdFragmentBlockPosition()` | documentado en la cabecera | **fuera de la cabecera documentada** — pero todavía inyectado y todavía aceptado por el validador (§75) |
| Pack por defecto | 6 hooks (vértice+superficie) | **9 hooks** — incluidos los de luz (§76) |
| `bloxdChunkSize` | no estaba en la cabecera | **nueva const `bloxdChunkSize: i32 = 32`** (§78) |
| Espacio `bloxdSp*` | 27 símbolos | **46 símbolos** (+20, −1) (§79) |
| Registro de texturas | 905 nombres utilizables | **896 nombres utilizables** — +1, −10 (§80) |
| Límites del cargador, reglas de zip, forma de `pack.json`, nombres de hooks, contrato estricto | — | **congelados, límites idénticos byte a byte** (§70) |

La conversión desde v4 es en su mayoría mecánica (§77): esta vez la trampa silenciosa es distinta — un paquete que todavía lea `blockFlags` o proteja sus hooks de luz con `#ifdef BLOXD_LIGHTING` **falla la validación con un mensaje específico** (el analizador ahora explica ambos), así que nada se comporta mal en silencio; pero un paquete que solo *lea las constantes de bits antiguas* por nombre se negará a cargar hasta que se porte. Como siempre, verifica con una compilación en el juego antes de distribuir.

## 69. Destino de los paquetes v4 (conclusión primero)

**Todo paquete v4 — incluido todo paquete distribuido como v4 — falla ahora en producción exactamente al cargar.** El cargador compara `manifest.apiVersion !== 5` con el `!==` estricto de JavaScript — la constante de versión `5` y la plantilla de cabecera viven en el mismo módulo de este build (módulo 29836), así que la comprobación y el texto de cabecera contra el que valida se mueven juntos. El JSON debe llevar el *número* `5`; una cadena `"5"` falla y se informa con su grafía JSON, exactamente como en v4.

Los dos mensajes de carga no cambian respecto a v4, verbatim del diccionario i18n activo:


> `This pack is for shader pack API version {{packVersion}}. Bloxd supports version {{version}}.` — la clave está presente pero no es igual a 5.

Un paquete v4 guardado (que antes funcionaba) no le lanza nada al jugador: el resultado del paquete guardado resuelve a `{kind: "none", reason: "otherApiVersion"}`, el paquete queda inactivo en silencio, y la pestaña de ajustes de paquetes de sombreadores se explica con la línea de estado:

> `This shader pack is for API version {{packVersion}}, so it won't run. Load a version {{version}} pack to replace it.`

Las reglas del manifiesto, en lo demás, remedidas y sin cambios: `pack.json` debe ser un objeto JSON en la raíz del zip; `apiVersion` debe estar presente y ser `=== 5`; `name` es obligatorio, una cadena, no vacío tras recortar; `author` es opcional pero debe ser una cadena si está; todo lo demás del manifiesto lo ignora el cargador.

## 70. pack.json, el cargador y el uniform (lo que no cambia)

Todo el modelo de paquetes se traslada de v4 byte a byte. Los límites del cargador, remedidos en el chunk del cargador activo (c53):

| Límite | Valor | Mensaje al superarlo |
|---|---|---|
| Archivos `.wgsl` por paquete | 256 | `The pack has more than 256 .wgsl files.` |
| Fuente `.wgsl` total | 256 KB | `The pack's .wgsl files are over 256 KB in total.` |
| Tamaño de `pack.json` | 64 KB | `pack.json is over 64 KB.` |
| Tamaño del zip | 32 MB | `The zip is over 32 MB.` |
| Entradas del zip | 1.024 | `The zip has more than 1024 entries.` |
| Forma del zip | — | los zips divididos, Zip64, las entradas cifradas y los métodos de compresión no soportados se rechazan cada uno con un mensaje dedicado; todo archivo debe ser UTF-8 válido; exactamente un `pack.json`; sin rutas duplicadas |

El uniform por fotograma sigue siendo `@group(3) @binding(0) var<uniform> bloxdPackInputs: BloxdPackInputs`, sigue siendo de 64 bytes — pero ganó un miembro. La tabla de disposición, del módulo de disposición de uniforms activo:

| Offset | Campo | Tipo | Nota |
|---|---|---|---|
| 0 | `seconds` | `f32` | respalda `bloxdSeconds()` |
| 4 | `lit` | `u32` | **nuevo en v5** — 1 cuando la iluminación de bloque/cielo está activa; respalda `bloxdLit()` |
| 16 | `renderOffset` | `vec3i` | respalda `bloxdRenderOffset()` |
| 32 | `sunDirection` | `vec3f` | respalda `bloxdSunDirection()` |
| 48 | `eyePosition` | `vec3f` | respalda `bloxdEyePosition()` |

`lit` se instala en el relleno que v4 ya tenía entre `seconds` y `renderOffset` (los offsets 4–15 eran holgura de alineación en v4; `renderOffset` se queda en 16 porque un `vec3i` necesita alineación de 16 bytes), así que el tamaño total de la estructura y el offset de todos los demás miembros no cambian. El motor lo escribe con un único `setUint32(4, lit ? 1 : 0)` — es un flag, no un nivel de luz: los nombres del lado JS de v4 `terrainLightLevels` / `terrainHeldLight` desaparecen por completo del bundle.

La disposición de bind groups del paquete no cambia en lo demás: el grupo 3 sigue siendo `0` uniform · `1` textura de profundidad de escena (variantes de líquido) · `2` el búfer de almacenamiento `bloxdSpTextureLayers`. `minBindingSize` sigue siendo 64.

## 71. La reescritura de flags: `blockFlags` → `BloxdFlags` (lo principal)

v4 identificaba una cara con un `blockFlags: u32` y seis constantes `bloxdBlockFlag*` (opaque 1, emissive 2, vegetation 4, dirt 8, sand 16, rock 32). v5 sustituye todo el mecanismo por una estructura de booleanos con nombre, citada verbatim de la cabecera activa:

```wgsl
// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    // Drawn as block models, so never part of terrain or flagged as opaque.
    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    placed: bool,     // Blocks placed as part of chunks. Not items or vehicles.
    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}
```

Las seis pruebas de bits de v4 se mapean una a una con campos — la migración es un renombrado, no un rediseño:

| v4 | v5 |
|---|---|
| `(surface.blockFlags & bloxdBlockFlagOpaque) != 0u` | `surface.flags.opaque` |
| `(surface.blockFlags & bloxdBlockFlagEmissive) != 0u` | `surface.flags.emissive` |
| `(surface.blockFlags & bloxdBlockFlagVegetation) != 0u` | `surface.flags.vegetation` |
| `(surface.blockFlags & bloxdBlockFlagDirt) != 0u` | `surface.flags.dirt` |
| `(surface.blockFlags & bloxdBlockFlagSand) != 0u` | `surface.flags.sand` |
| `(surface.blockFlags & bloxdBlockFlagRock) != 0u` | `surface.flags.rock` |

Los ocho campos **nuevos** son la historia real. v4 no tenía forma de distinguir una losa de un bloque completo, un ítem en mano del terreno, o un jugador de una calabaza — toda cara no terrestre era solo «no opaca» con un id de textura. v5 responde «qué estoy mirando» directamente:

- **`slab` / `stairs` / `flat`** — las tres formas de modelo de bloque. `flat` cubre las plantas de planos cruzados (hierba alta, flores, cultivos, telarañas). Estas se *dibujan como modelos de bloque*, así que la cabecera indica que nunca forman parte del terreno y nunca son `opaque`.
- **`placed`** — geometría de chunk tal como se colocó en el mundo; explícitamente *no* ítems ni vehículos.
- **`held`** — ítems en una mano, en primera o tercera persona. Este es el campo que los autores de sombreadores en primera persona querían desde v1: por fin puedes detectar el ítem en mano y tratarlo distinto del mundo.
- **`dropped` / `thrown`** — ítems en el suelo / en cintas / en tuberías, frente a ítems en vuelo (bolas de nieve, flechas, cohetes).
- **`lifeform`** — jugadores, mobs y NPCs, *incluyendo armadura y cosméticos*.

Combinado con `localPosition` (§72) y las entradas de encantamiento/superposición, el pipeline de modelos ya puede sombrearse con pleno conocimiento de lo que está renderizando. Una receta mínima de «brillo del ítem en mano», imposible en v4:

```wgsl
fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    // Ilumina lo que sostiene el jugador local, nada más.
    if (surface.flags.held) {
        out.colour *= 1.15;
    }
    return out;
}
```

Nota lo que *no* cambió: los campos viven en el mismo lugar en las tres estructuras de entrada (`BloxdVertexIn`, `BloxdSurfaceIn`, `BloxdLightIn` — nombre de campo `flags`, tipo `BloxdFlags`), la semántica de los seis booleanos supervivientes es la semántica v4 con los mismos casos límite que la cabecera ahora deletrea («Rocky Dirt es también roca», «toda arenisca es también roca»), y varios flags siguen combinándose libremente («la arenisca es arena y roca», «posiblemente incluso ninguno»).

## 72. Entradas nuevas: `localPosition`, el cuarteto de encantamiento y `overlayColour`

`BloxdVertexIn`, `BloxdSurfaceIn` y `BloxdLightIn` ganan todos los mismos miembros nuevos. De la cabecera, verbatim:

```wgsl
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
```

- **`localPosition`** — la posición en espacio de modelo del vértice/fragmento, antes de que la instancia del modelo se coloque en el mundo. `vec3f(0.0)` para caras de terreno y líquido (no tienen modelo). Para el brazo de un jugador, una espada en mano, el aspa de un molino, esta es la coordenada que rota con el modelo — una animación por modelo o un efecto de curvatura anclado a «en qué parte de la espada estoy» ahora toma un campo en lugar de adivinanzas en espacio de mundo. En la estructura light la cabecera indica que es «igual que en BloxdVertexIn, tras el hook de vértice» — es decir, si tu hook de vértice mueve el vértice, el `localPosition` del hook de luz lo sigue.

Y solo en `BloxdSurfaceIn` / `BloxdLightIn` (la estructura de vértice no los necesita):

```wgsl
     // Enchanted items and armour only, all 0 for anything else.
     enchantTier: u32,     // 1-5 for Tier 1-5.
     enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
     enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

     // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
     // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
     overlayColour: vec4f,
```

- **`enchantTier`** — el nivel de encantamiento del ítem como entero 1–5, para el clásico efecto «intensidad de destello por nivel» sin parsear el color.
- **`enchantColour`** — el RGB vivo del encantamiento más su alfa *animado* en `.a`: el motor anima el barrido del destello, así que leer `.a` por fragmento te da gratis el patrón en movimiento. Todo ceros en caras sin encantar.
- **`enchantSpeed`** — la velocidad a la que se mueve el patrón de encantamiento; la nota de la propia cabecera es «más rápido a niveles más altos», así que `enchantTier` y `enchantSpeed` son consistentes por construcción.
- **`overlayColour`** — el destello de daño/herida y superposiciones similares de entidades (RGB + alfa), 0 para todo lo que no sea jugador o mob. El motor mezcla esto *antes* de la iluminación; ver §73 para el lado de salida.

El viejo cuarteto (`textureId`, `textureRotation`, `uv`, `mipLevel`) se traslada intacto, con un comentario redactado de nuevo: v4 decía que `uv` eran «coordenadas de textura en bloques»; v5 dice «The texture spans 0-1. `fract(uv)` is drawn.» — el mismo campo, descrito desde el punto de vista de la textura: una tesela de textura abarca `0.0–1.0` de uv, y los pasos enteros de uv la teselan a lo largo de un muro repetido. No hace falta acción de porte salvo que escribieras a mano suposiciones sobre rangos multibloque.

## 73. Salidas nuevas: `BloxdSurface` gana `enchantColour` y `overlayColour`

La estructura de **salida** de superficie gana dos campos, verbatim:

```wgsl
struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}
```

Tu hook de superficie ahora posee el destello de encantamiento y el destello de daño, igual que ya poseía la emisión:

- `bloxdDefaultSurface` pasa `surface.enchantColour` y `surface.overlayColour` sin cambios, así que el look por defecto es idéntico al comportamiento del lado motor de v4.
- **Poner `out.enchantColour` a cero** en tu hook elimina el destello de encantamiento de tu iluminación personalizada — un paquete de «realismo sin destello» ahora son dos líneas.
- **Amplificar `out.overlayColour.a`** hace el destello de daño más contundente sin tocar el color base; la mezcla ocurre en `bloxdLitColour` (§74), tras el sombreado, exactamente donde el motor lo ponía.
- La nota sobre el orden de la emisión se traslada verbatim: la emisión se *suma tras la iluminación, antes de la niebla* — y los dos campos nuevos se *mezclan en `bloxdLitColour`*, que va *antes* de la emisión y la niebla. La cadena de salida completa, en orden: `colour` → mezcla de superposición → sombreado → mezcla de encantamiento → luz de mundo → `+ emission` → niebla.

## 74. La receta de iluminación se hace pública: `bloxdLit()` y los tres ayudantes

v4 cerraba la iluminación en tiempo de compilación: 8 variantes (`strict|allow` × `lit|unlit` × `terrain|liquid`), con `#ifdef BLOXD_LIGHTING` decidiendo si los hooks de luz corrían la ruta lit o unlit. v5 saca todo el eje de iluminación de la compilación:

- La **matriz de variantes es 6, no 8**: `strict|allow` × `terrain|liquid|model`, con nombres `allow.terrain` … `strict.liquid` etc. (las etiquetas que el propio motor construye para la pantalla del cargador).
- `BLOXD_STRICT` sigue siendo solo-estricto; `BLOXD_ALPHA` sigue siendo todo-líquido más toda variante allow (apagado para terreno estricto y modelo estricto); `BLOXD_SCENE_DEPTH` sigue siendo solo-líquido. **`BLOXD_LIGHTING` ya no existe.**
- El estado de iluminación pasó al uniform (`lit: u32`, §70) y se consulta en código con la nueva función de cabecera:

```wgsl
// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}
```

Si tu paquete v4 envolvía sus hooks de luz en `#ifdef BLOXD_LIGHTING ... #else ... #endif`, el porte a v5 es un retorno anticipado: `if (!bloxdLit()) { return bloxdDefaultLight(surface, light); }`. El analizador incluso te lo dice — usar `BLOXD_LIGHTING` ahora produce el mensaje de validación *«BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead.»* (medido verbatim del validador activo).

Tres funciones más se unen a la cabecera, y son las que los autores v4 seguían rederivando a mano — la propia iluminación del motor, documentada como WGSL invocable:

```wgsl
// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}
```

Y el propio `bloxdDefaultLight` ahora las usa — el valor por defecto es literalmente «aplicar la receta del motor y luego poner niebla al resultado extendido con emisión»:

```wgsl
fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
```

Para alimentar `bloxdShading`, `BloxdLightIn` también gana dos entradas (comentarios verbatim):

```wgsl
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
```

`diffuse` y `emissive` son nuevos en v5 (v4 tenía solo `directional` y `ambient`): te permiten reconstruir `bloxdShading` con modificaciones — p. ej. conservar la luz de mundo del motor pero reemplazar el término Lambert por tu propio sombreado envolvente — sin perder la respuesta de material que el motor ya conoce. Los comentarios de documentación de los niveles de luz también se redactaron de nuevo, de «0 without BLOXD_LIGHTING» a «0 when !bloxdLit()», que es el mismo hecho en el vocabulario v5.

Un hook de luz de «sombreado propio, luz de mundo del motor» — la receta que los autores v4 aproximaban escalando `litColour`, ahora exacta:

```wgsl
fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    // Half-Lambert envolvente: suave, nunca del todo oscuro en la cara de atrás.
    let nDotL = light.directional; // ya es el término Lambert sumado
    let wrapped = nDotL * 0.5 + 0.5;
    let shaded = saturate(wrapped * light.diffuse + light.emissive + light.ambient);
    let colour = max(shaded * bloxdWorldLight(light), vec3f(0.0));
    return BloxdLight(bloxdApplyFog(colour + surface.emission, light));
}
```

## 75. Eliminaciones: `bloxdFragmentBlockPosition()`, `bloxdBlockFlag*`, `bloxdSpLitColour`

Tres cosas se van, y el validador lo dice por su nombre:

- **`bloxdFragmentBlockPosition(position, normal) -> vec3i`** — fuera de la cabecera documentada, pero **no muerto en la práctica**: la tabla de firmas del validador conservó su entrada (así que las llamadas siguen pasando la validación en cualquier hook, vértice incluido), y el generador de código todavía inyecta una definición en el módulo de terreno/líquido y en ambos programas de modelo (`vec3i(floor(position - normal * 0.5)) + bloxdRenderOffset()` para terreno/líquido; una variante con offset de 1/64 y ajuste a celda para modelos). Los paquetes v4 que la llaman siguen funcionando. Trátala como deprecada: hoy está sin documentar, así que prefiere `bloxdWorldPosition()` para posiciones continuas y `flags` para «sobre qué bloque estoy», y espera que pueda desaparecer en una versión futura.
- **Las seis constantes `bloxdBlockFlag*`** — sustituidas por `BloxdFlags` (§71). Cualquier referencia superviviente falla la validación con el diagnóstico de nombre reservado del analizador.
- **`bloxdSpLitColour`** — el símbolo interno del motor cuyo trabajo pasó a ser el público `bloxdLitColour()` (§74). Deja el espacio `bloxdSp*`, que por lo demás solo crece (§79).

Las funciones de la era v4 que sobreviven sin cambios: `bloxdEyePosition()`, `bloxdRenderOffset()`, `bloxdSunDirection()`, `bloxdSeconds()`, `bloxdWorldPosition()`, `bloxdApplyFog()`, `bloxdDefaultVertex()`, `bloxdDefaultSurface()`, `bloxdDefaultLight()`, más toda la API de texturas (`bloxdTexel`, `bloxdTextureSize`, `bloxdTextureId*` — §79 remide el registro) y `BloxdOpaqueBehind` / `bloxdSceneDepth` con su semántica de variantes de líquido.

## 76. El paquete por defecto incluye los nueve hooks

La plantilla de la que parte un paquete nuevo incluye ahora los hooks de luz — la plantilla de v4 tenía seis (vértice+superficie por programa) y dejaba los hooks de luz para copiarlos de la documentación. La de v5, verbatim y completa (1.633 bytes tal como se distribuye):

```wgsl
// Every hook here returns its engine default. Modify the return values to start
// building a shader pack. If you delete a hook, the default is used instead.

// All blocks but water and block models use terrain hooks.
#ifndef BLOXD_STRICT
// Strict games keep terrain where it is. Without the #ifndef, this hook would
// turn the whole shader pack off there.
fn bloxdTerrainVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Water uses liquid hooks. To share code with another hook, define a function
// and call it from both places.
#ifndef BLOXD_STRICT
fn bloxdLiquidVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdLiquidSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdLiquidLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Models: block models such as slabs and plants, items, players and mobs.
#ifndef BLOXD_STRICT
fn bloxdModelVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdModelLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}
```

Los comentarios son redacción nueva y conviene leerlos como documentación del modelo de borrado: *«Modify the return values to start building a shader pack. If you delete a hook, the default is used instead.»* La nota de líquido también cambió — v4 decía «If deleted, water uses your terrain hooks instead», v5 dice «To share code with another hook, define a function and call it from both places» — y la nota estricta ahora explica el `#ifndef` en una frase: *«Strict games keep terrain where it is. Without the #ifndef, this hook would turn the whole shader pack off there.»*

El contrato de juegos estrictos en sí (v4 §60) no cambia: un hook de vértice sin guardia informa `<hook> moves terrain, which strict games prevent.`, un `discard` alcanzable informa `discard makes terrain see-through, which strict games prevent.`, y cualquiera de los dos desactiva *todos* los hooks en juegos estrictos. Los 12 títulos allow se remidieron en el bundle activo — siguen siendo 12, sin cambios.

## 77. Lista de migración de v4 a v5

1. **`pack.json`**: `"apiVersion": 5` — el número, no una cadena.
2. **Porta los flags** (mecánico, §71): cada `blockFlags & bloxdBlockFlagX != 0u` → `flags.x`; elimina las constantes — el validador las rechaza por nombre.
3. **Porta la compuerta de iluminación** (la que tiene mensaje del validador): `#ifdef BLOXD_LIGHTING` → `if (bloxdLit()) { ... } else { return bloxdDefaultLight(surface, light); }`; `BLOXD_LIGHTING` ahora dispara *«BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead.»*
4. **Migra fuera de `bloxdFragmentBlockPosition`** (§75) — todavía compila, pero hoy está sin documentar; usa `bloxdWorldPosition()` / `flags`.
5. **Decide sobre las entradas/salidas nuevas** *(opcional)*: `flags.slab/stairs/flat/placed/held/dropped/thrown/lifeform` (§71), `localPosition` (§72), el cuarteto de encantamiento + `overlayColour` (§72–§73). El paso a través de `bloxdDefaultSurface` conserva exactamente el look v4.
6. **Adopta los ayudantes de la receta del motor** *(opcional pero recomendado)*: reemplaza el color de luz hecho a mano con `bloxdLitColour(surface, light)` — o mezcla y combina con `bloxdShading` / `bloxdWorldLight` (§74) — y luego añade `surface.emission` y `bloxdApplyFog` como hace `bloxdDefaultLight`.
7. **Auditoría estricta** (sin cambios respecto a v4): `#ifndef BLOXD_STRICT` alrededor de los hooks de vértice y cualquier `discard` alcanzable.
8. **Comprobación de compilación en el juego**: el cargador valida las **6** variantes a la vez (estricto × terreno/líquido/modelo — el eje de iluminación ya no compila por separado, §74). Luego revisa visualmente un juego allow y un juego estricto.
9. **Sube los metadatos de tu propia versión y redistribuye**: las copias v4 guardadas en las máquinas de los jugadores quedan inactivas en silencio (§69) y solo la pestaña de ajustes dice por qué.

## 78. Otros cambios y notas de v5

- **`bloxdChunkSize` se une a la cabecera** — `const bloxdChunkSize: i32 = 32;` («Blocks along each side of a chunk»). Antes un número mágico del lado del motor; ahora una constante con nombre sobre la que puedes ramificar. `bloxdPi`/`bloxdTau` sin cambios.
- **La sección de funciones por fotograma de la cabecera ganó un comentario compartido** — «These functions return the same value for the entire frame» (v4: «return 1 value per frame, the same for every call site») — pura redacción.
- **Las derivadas en Y se niegan automáticamente en el código del paquete.** El analizador reescribe toda llamada a `dpdy`, `dpdyCoarse` o `dpdyFine` en `(-dpdy(...))` — el eje y del espacio de pantalla apunta hacia abajo, así que la negación hace que «derivada respecto a arriba» coincida con la intuición. Tú escribes `dpdy(h)` esperando «cómo cambia h al subir»; el código emitido lo niega por ti. `dpdx` y la familia `fwidth` quedan intactas. (Medido en el paso de reescritura de tokens del validador; la familia dpdy está listada específicamente como el conjunto de negación.)
- **Los diagnósticos de nombre de textura ganaron un motor de grafías.** Un nombre que empieza por `bloxdTextureId` pero no resuelve recibe ahora una sugerencia por Levenshtein: *«'X' isn't part of the shader pack API. Texture names start with exactly bloxdTextureId: did you mean bloxdTextureIdY?»* — más mensajes dedicados para grafías de fotograma (*«names a frame of the animated texture Z: use bloxdTextureIdZ, which bloxdTexel animates.»*) y grafías giradas (*«names a turned copy of Z: use bloxdTextureIdZ, which bloxdTexel turns as each face shows it.»*). La regla general de reserva se reenuncia en los diagnósticos: *«Packs can't declare names starting with bloxd, other than the hook functions bloxd<Terrain|Liquid|Model><Vertex|Surface|Light>»*, y *«Packs can't use X: the engine binds every texture and sampler. Surface and light hooks can read atlas textures with bloxdTexel.»*
- **Solo se emiten las constantes de textura referenciadas.** El bloque `bloxdTextureId*` de la cabecera se genera por paquete a partir de los nombres que realmente referencias — un paquete que usa tres constantes recibe tres líneas `const` anteuestas, no las ~900 completas.
- **`HEADER_VERSION` pasó a `9.<hash>.<hash>`** — misma estructura de dos sufijos que v4 (fnv1a32 del material de cabecera, fnv1a32 del registro ordenado nombre-id), con el entero inicial subido de 8 a 9. La lógica de recomprobación de paquetes guardados (§55 de [la guía de migración v4](v4.md)) no cambia: un cambio de cabecera/registro pasa los paquetes guardados a «necesita revisión».
- **Superficie i18n**: la familia de claves de paquetes de sombreadores no cambia en forma (las claves `load*`, `status*` y de etiquetas de variante de la guía v4 §62 remedidas todas presentes; `loadNoWgsl`/`loadNotZip` siguen exactas).
- **Disposición del bundle para re-investigadores**: cabecera c55 (sin cambios), cargador/persistencia c51–c53, validador + constructor del registro c55, codegen WebGPU c56, niebla c9, **plantilla del pack por defecto c116** (movida desde c124), los sitios de BLOXD_ALPHA c51/c52/c53/c55/c9. Nota de formato de chunks: cada chunk es ahora un módulo ES (`export const modules = {...}`) — c53 incluso lleva módulos tanto de c52 como de c53 — lo que importa si buscas texto en el bundle (un id de módulo como `1371` vive en el array disperso de módulos de *main*, no en ningún chunk).

## 79. Interioridades del motor v5: el pipeline de texturas y el espacio `bloxdSp*` de 46 símbolos

```wgsl

// The Bloxd shader pack API, apiVersion 5. Read-only, prepended to all packs.

const bloxdPi: f32 = 3.1415926535898;
const bloxdTau: f32 = 6.2831853071796;

// Blocks along each side of a chunk.
const bloxdChunkSize: i32 = 32;

// These functions return the same value for the entire frame.

// The camera's render position.
fn bloxdEyePosition() -> vec3f {
    return bloxdPackInputs.eyePosition;
}

// Integer distance, in blocks: render position + this offset = world position.
// Changes as the player travels, so render positions stay close to 0,0,0.
// See bloxdWorldPosition for one way to use it.
fn bloxdRenderOffset() -> vec3i {
    return bloxdPackInputs.renderOffset;
}

// The unit vector towards the sun, in world orientation; 0 when there's no sun.
fn bloxdSunDirection() -> vec3f {
    return bloxdPackInputs.sunDirection;
}

// Seconds since the page loaded. As an f32, it has sub-millisecond precision
// for the first 4.5 hours. Get a recurring timer using bloxdSeconds() % period.
fn bloxdSeconds() -> f32 {
    return bloxdPackInputs.seconds;
}

// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}

// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    // Drawn as block models, so never part of terrain or flagged as opaque.
    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    placed: bool,     // Blocks placed as part of chunks. Not items or vehicles.
    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}

// Convert a render position to a world position, with possible f32 inaccuracy.
fn bloxdWorldPosition(position: vec3f) -> vec3f {
    return position + vec3f(bloxdRenderOffset());
}

struct BloxdVertexIn {
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
}

struct BloxdVertex {
    position: vec3f,      // The render position output.
}

struct BloxdSurfaceIn {
    colour: vec3f,        // RGB colour = texture * tint * ambient occlusion.
    alpha: f32,           // Opacity.

    // Enchanted items and armour only, all 0 for anything else.
    enchantTier: u32,     // 1-5 for Tier 1-5.
    enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
    enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

    // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
    // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
    overlayColour: vec4f,

    // These mean the same as in BloxdVertexIn, after the vertex hook.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.

    // These are all 0 if the face has no texture. Most models use textureId 0.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}

// blockLight, skyLight and heldLight are 0-1, from the 0-15 light levels on an
// ease-out curve, e.g. 6->0.45, 12->0.92. They all exclude ambientLightColour.
// bloxdLitColour lights a surface from these as the engine does.
struct BloxdLightIn {
    litColour: vec3f,  // Lit and enchanted RGB colour, before emission and fog.
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
    ambient: vec3f,    // RGB ambient colour, added to directional light.
    blockLight: vec3f, // RGB block light; 0 when !bloxdLit().
    skyLight: f32,     // Sky light; 1 when !bloxdLit().
    ambientLightColour: vec3f, // Minimum RGB light; 1 when !bloxdLit().
    skyLightColour: vec3f, // RGB colour of skyLight; 1 when !bloxdLit().
    heldLight: vec3f,  // RGB held light; 0 when !bloxdLit() or no light held.
    fogColour: vec3f,  // The game's RGB fog colour; 0 when the game has no fog.
    fogAlpha: f32,     // 0 = no fog, 1 = only fogColour.

    // These are the same as in BloxdSurfaceIn.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdLight {
    colour: vec3f, // RGB colour output.
}

struct BloxdOpaqueBehind {
    hit: bool,       // False where nothing opaque is behind (sky).
    position: vec3f, // The render position; 0 when !hit.
    distance: f32,   // From the camera; 0 when !hit.
}

fn bloxdDefaultVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return BloxdVertex(vertex.position);
}

fn bloxdDefaultSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return BloxdSurface(
        surface.colour,
#ifdef BLOXD_ALPHA
        surface.alpha,
#endif
        vec3f(0.0),
        surface.enchantColour,
        surface.overlayColour,
    );
}

// Apply this fragment's fog to colour, as the engine does.
fn bloxdApplyFog(colour: vec3f, light: BloxdLightIn) -> vec3f {
    return mix(colour, light.fogColour, light.fogAlpha);
}

// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}

fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
```

Cada firma de hook, estructura, constante y comentario de arriba es estructural: es lo que el validador activo parsea, lo que el generador de código antepone y contra lo que tu paquete compila.
