# Руководство по миграции на API v4

> Версия: 4 · Статус: Historical (руководство по миграции той эпохи; целевой билд указан в тексте)
> **Заменено 2026-11-03: текущий API — версия 5** — паки v4 отклоняются при загрузке ровно так, как здесь описано для v3. Примените эту часть *и затем* [руководство по v5](v5.md) (v4 → v5: структура `BloxdFlags` заменяет `blockFlags`, `bloxdLit()` и публичный рецепт освещения, входы зачарования/оверлея, дефолтный пак с 9 хуками). Внутрянка этой части (§56–§66) остаётся верной для тех v4-билдов, на которых она была измерена.

Целевой билд: `cnty9.main.669f8081.js` — **живёт в продакшене и предпродакшене одновременно с 2026-10-26**. В отличие от раскатки v3 (предпродакшн-билд, продвинутый в продакшен), v4 одним махом перевела оба окружения на один и тот же новый бандл, и оба бандла байт-в-байт идентичны (основной бандл и каждый чанк шейдер-паков проверены по md5), так что всё здесь применимо к продакшену как есть. Вокруг этого релиза бандл к тому же был реорганизован — основной бандл сжался с 4,73 МБ до 3,03 МБ (-36%), число чанков выросло со 169 до 193, и весь пайплайн шейдер-паков (загрузчик, валидатор, генератор кода, компилятор WebGPU) теперь живёт в сплошном кластере c49–c54. Модель пака при этом сохраняет форму: те же поля `pack.json`, те же лимиты загрузчика, тот же uniform на 64 Б, те же шесть хуков.

**Перепроверено на `tcwczu.main.357faec1.js` (2026-10-30, продакшен и предпродакшен снова байт-в-байт идентичны): вся поверхность API v4 без изменений.** Заголовок движка (6 021 Б декодированных), шаблон дефолтного пака (1 122 Б как отгружен), 27 символов `bloxdSp*`, биты blockFlags, лимиты загрузчика и 12 allow-титулов — всё байт-в-байт совпадает с базой `cnty9`, которую документирует эта часть — заморозка v4 выдержала первый после v4 рефреш бандла. Раскладка бандла сдвинулась дальше: основной бандл вырос до 3,28 МБ, карта чанков теперь насчитывает 202 id (195 эмитировано), кластер шейдерного пайплайна сидит в c51–c56 с дефолтным паком в c124, а ссылки §66 на «чанк c8» для констант лифта/конуса теперь ведут на c9. Ничто из этого паку не видно. Единственное, что эта перепроверка *не* перемерила, — реестр имён текстур (§68): его id из `cnty9` остаются снимком, а имена остаются стабильным API.

Одна вещь изменилась вокруг этого релиза и при этом *не* в бандле: **движок теперь цитирует справочные файлы по имени.** Его собственные сообщения об ошибках указывают на `bloxd-api.wgsl` (аннотированный заголовок движка) и `BLOCK_TEXTURES.md` (полный список имён текстур) — `...BLOCK_TEXTURES.md lists them.` Это руководство несёт содержимое обоих файлов вместо отсылки куда-то ещё: полный заголовок, восстановленный дословно из живого билда, встроен в [Внутрянка движка: заголовок движка](../internals/engine-header.md), а полный каталог пригодных имён текстур (905 в билде v4) — это [Каталог текстур](../api/texture-catalog.md). Каждый факт этой части, касающийся паков, восстановлен из продакшн-бандла.

Набор изменений v4 на одном экране:

| Область | v3 | v4 |
|---|---|---|
| `pack.json` `apiVersion` | `3` (strict) | **`4` (strict)** — паки v3 отклоняются при загрузке |
| Доступ к текстурам | нет («нельзя сэмплить текстуры») | **новый текстурный API**: `bloxdTexel()`, `bloxdTextureSize()`, константы `bloxdTextureId*` |
| Входы хуков | 13/5 полей | **+4 поля в каждом**: `textureId`, `textureRotation`, `uv`, `mipLevel` (surface *и* light) |
| `fogVisibility` | `1 = без тумана` | переименован в **`fogAlpha`**, смысл **инвертирован**: `0 = без тумана, 1 = только fogColour` |
| `bloxdFaceBlock()` | — | переименован в **`bloxdFragmentBlockPosition()`** (та же математика) |
| `BloxdOpaqueBehind.found` | `found` | переименован в **`hit`** |
| Strict-игры | политика + guard'ы задокументированы | теперь **принуждаются встроенным валидатором** с точными диагностиками (§60) |
| Всё остальное | — | заморожено: 6 хуков, биты `blockFlags`, раскладка uniform, лимиты загрузчика, матрица вариантов, биндинги `@group(3)` пака |

Переход с v3 механический (§61), кроме одной тихой ловушки: если вы перенесёте всё, но проигнорируете инверсию `fogAlpha`, ваш зависящий от тумана код будет работать с инвертированным туманом и при этом *компилироваться без ошибок*. Как всегда, перед распространением проверяйте компиляцией в игре.

## 55. Судьба v3-паков (сначала вывод)

**Каждый v3-пак — включая каждый пак, распространявшийся как v3, — теперь падает в продакшене ровно при загрузке.** Загрузчик сравнивает `manifest.apiVersion !== 4` строгим JavaScript-оператором `!==`, поэтому сравнение точное и по типу, и по значению: JSON обязан нести *число* `4`. Строка `"4"` проверку проваливает и выводится со своим JSON-написанием (`{{packVersion}}` проходит через `JSON.stringify`, так что экран настроек показывает `This pack is for shader pack API version "4"...` вместе с кавычками — полезный признак того, что вы написали строку).

Два сообщения при загрузке, дословно из живого словаря i18n:

>
> `This pack is for shader pack API version {{packVersion}}. Bloxd supports version {{version}}.` — ключ присутствует, но не равен 4.

Сохранённый (раньше работавший) v3-пак не бросает в игрока никаких ошибок. Результат для сохранённого пака разрешается в `{kind: "none", reason: "otherApiVersion"}`, пак молча неактивен, а вкладка настроек шейдер-паков объясняет положение статусной строкой:

> `This shader pack is for API version {{packVersion}}, so it won't run. Load a version {{version}} pack to replace it.`

Правила манифеста вокруг `apiVersion` в остальном не изменились, и их стоит повторить, потому что загрузчик исполняет их прежде всего остального:

- `pack.json` обязан быть JSON-объектом в корне пака (не массивом, не числом).
- `apiVersion` обязан присутствовать и быть `=== 4`.
- `name` обязателен: строка, непустая после обрезки пробелов.
- `author` опционален, но при наличии обязан быть строкой — явный `null` отклоняется (`pack.json's "author" must be a string.`).
- Всё остальное в манифесте загрузчик игнорирует.

## 56. pack.json и uniform-буфер (что не меняется)

Вся не-текстурная модель пака переносится из v3 байт-в-байт, так что справочником остаётся §41 [руководства по v3](v3.md). Перепроверенные значения v4, из живого чанка загрузчика (c51):

| Лимит | Значение | Сообщение при превышении |
|---|---|---|
| Файлов `.wgsl` на пак | 256 | `The pack has more than 256 .wgsl files.` |
| Исходников `.wgsl` суммарно | 256 КБ | `The pack's .wgsl files are over 256 KB in total.` |
| Размер `pack.json` | 64 КБ | `pack.json is over 64 KB.` |
| Размер zip | 32 МБ | `The zip is over 32 MB.` |
| Zip-записей | 1 024 | `The zip has more than 1024 entries.` |
| Форма zip | — | разрезанные zip, Zip64, зашифрованные записи и неподдерживаемые методы сжатия — каждое отклоняется отдельным сообщением; каждый файл обязан быть корректным UTF-8; ровно один `pack.json`; без дублирующихся путей |

Покадровый uniform не тронут: `@group(3) @binding(0) var<uniform> bloxdPackInputs: BloxdPackInputs`, 64 байта, раскладка в стиле std140:

| Смещение | Поле | Тип | Заметка |
|---|---|---|---|
| 0 | `seconds` | `f32` | питает `bloxdSeconds()` |
| 16 | `renderOffset` | `vec3i` | питает `bloxdRenderOffset()` |
| 32 | `sunDirection` | `vec3f` | питает `bloxdSunDirection()` |
| 48 | `eyePosition` | `vec3f` | питает `bloxdEyePosition()` |

Шаблон из шести хуков поставляется лишь с полировкой комментариев (1059 → 1122 байта; описанное в §45 поведение v3 не изменилось). Шаблон v4, дословно — по-прежнему лучший стартовый скелет и по-прежнему тот strict-паттерн, который стоит копировать:

```wgsl
// Every hook here returns its engine default.
// Copy a hook and change its output to start a shader pack.

// Strict games keep terrain where it is. We use #ifndef to define the hook for
// non-strict games, but to disable it in strict games, so our pack can stay on.
#ifndef BLOXD_STRICT
fn bloxdTerrainVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Water uses liquid hooks. If deleted, water uses your terrain hooks instead.
#ifndef BLOXD_STRICT
fn bloxdLiquidVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdLiquidSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdLiquidLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}
```

## 57. API текстур: `bloxdTexel`, `bloxdTextureSize`, `bloxdTextureId*` (главное)

Паки v3 могли читать *цвет* грани, но не её *текстуру*. v4 открывает сам атлас блочных текстур: три новые функции движка, одно семейство именованных констант и четыре новых входных поля (§58). Собственная однострочная сводка заголовка движка о главном: *"This face's texture. Compare with `bloxdTextureId*`."*

### 57.1 `bloxdTexel(textureId: u32, uv: vec2f, mipLevel: f32) -> vec4f`

Сэмплит атлас блочных текстур **в точности так, как это делает собственный сэмплер движка** — те же атласы `texture_2d_array<f32>`, тот же `atlasSampler`, `textureSampleLevel` на `round(mipLevel)` — поэтому тексел, который читаете вы, и тексел, который отрисовал движок, совпадают по построению. Семантика, целиком восстановленная из сгенерированного WGSL (в §63 — дословный исходник):

- **`textureId == 0` возвращает `vec4f(1.0)`** — белый. Это id «нет текстуры», и именно его несут четыре входных поля, когда у грани нет текстуры, поэтому вызов `bloxdTexel(surface.textureId, ...)` всегда безопасен.
- **Анимированные текстуры автоматически возвращают текущий кадр.** Кадры идут по игровому таймеру анимации — заморозить их или шагать нельзя, да и не нужно: сэмплирование id анимированной текстуры *и есть* сэмплирование её живого кадра (математика кадров — в §63.3).
- **`mipLevel` клампится так же, как движок клампит свой:** `clamp(round(mipLevel), 0, textureNumLevels(textureAtlas0) - 1)`. Мипы вне диапазона сатурируются, а не дают ошибку.
- **`textureRotation` текущего фрагмента применяется к передаваемому вами uv** — см. 57.4; это единственная тонкость с реальными визуальными последствиями.

`textureId` — **1-based**: `bloxdTextureIdGrassTop` — это и есть id, а слой атласа, который движок для него сэмплит, — `id - 1`. id стабильны по *имени* текстуры, а не по раскладке атласа — движок свободно перекомпоновывает атлас между билдами, а ваши сравнения `bloxdTextureId*` продолжают означать «эта текстура».

### 57.2 `bloxdTextureSize(mipLevel: f32) -> vec2u`

`textureDimensions(textureAtlas0, <клампнутый mip>)` — размер атласа в текселях на этом уровне мипа. Поскольку каждая текстура занимает один слой массива этого атласа, это ещё и *размер в текселях любой отдельной текстуры на этом мипе* (все блочные текстуры одного уровня атласа имеют одинаковый квадратный размер). Используйте её вместе с `bloxdTexel`, когда нужны эффекты по тексел-сетке:

```wgsl
// Тексел-выровненный ресемплинг «пиксель-арт» собственной текстуры этой грани.
let size = bloxdTextureSize(surface.mipLevel);
let uv = fract(surface.uv);
let texel = bloxdTexel(surface.textureId, uv, surface.mipLevel);
```

### 57.3 `bloxdTextureId*`: именованные константы текстур

Каждое пригодное имя текстуры становится `const`, с которой можно сравнивать, — пишется **CamelCase по имени файла текстуры**:

| Файл текстуры | Константа | Примечание |
|---|---|---|
| `grass_top.png` | `bloxdTextureIdGrassTop` | собственный пример движка |
| `lava0.png` (кадры `lava0`–`lava7`) | `bloxdTextureIdLava` | семейство анимации: суффикс кадра отпадает от канонического имени |
| `black_portal0.png` (кадры 0–3) | `bloxdTextureIdBlackPortal` | то же правило |
| `radar_screen0` (повёрнутые копии `[rot[1`–`[rot[4`) | `bloxdTextureIdRadarScreen0` | семейство поворотов: сворачивается к корневому имени |

Правило написания, восстановленное из валидатора: разрежьте имя по каждой не-буквенно-цифровой последовательности, капитализируйте каждую часть и склейте после префикса `bloxdTextureId`. Поиск в обратную сторону **не различает регистр и подчёркивания** (движок так же сворачивает ваше написание перед сопоставлением), а когда написание не разрешается — три специальных семейства ошибок, все дословно из живого валидатора:

> **Опечатка в префиксе / неверный регистр:** `bloxdTextureIdGrassTop isn't part of the shader pack API. Texture names start with exactly bloxdTextureId: did you mean bloxdTextureIdGrassTop?`
>
> **Кадр анимированной текстуры:** `...names a frame of the animated texture lava: use bloxdTextureIdLava, which bloxdTexel animates.`
>
> **Повёрнутая копия:** `...names a turned copy of radar_screen0: use bloxdTextureIdRadarScreen0, which bloxdTexel turns as each face shows it.`
>
> **Неоднозначность после сворачивания:** `...could name X and Y, which differ only by case or underscores, so it can't be used.`
>
> **Не найдено (с подсказкой):** `There's no texture called X. Did you mean bloxdTextureIdY?` — порог подсказки — расстояние Левенштейна `max(2, floor(len/4)) + 1`.
>
> **Не найдено (без подсказки):** `There's no texture called X. Texture names are the file names texture packs use, as in bloxdTextureIdGrassTop for grass_top.png; BLOCK_TEXTURES.md lists them.`

Последнее сообщение указывает на файл, содержимое которого это руководство встраивает прямо сюда: полный измеренный каталог — каждое из 905 пригодных имён с его тогдашним id плюс таблицы семейств поворотов и анимации — это §68 ниже; §64 содержит измерение реестра и стоящие за ним правила сворачивания. Живой преемник этого каталога — [Каталог текстур](../api/texture-catalog.md).

### 57.4 Тонкость с поворотом — и нейтральный сэмплер

`bloxdTexel` контр-вращает переданный вами uv на `textureRotation` **текущего фрагмента**, каким бы id вы его ни передали. Для двух типичных случаев это ровно то, что нужно:

- **Ресемплинг собственной текстуры этой грани** с `surface.uv` — uv находится в повёрнутой системе координат грани, контр-поворот переводит его в систему атласа, и вы получаете истинный тексел. Это задуманное основное применение.
- **Сэмплирование с uv, вычисленным в *атласных* координатах**, для *другой* текстуры на грани, чей поворот не 0 — контр-поворот всё равно срабатывает, и выборка попадает повёрнутой. Это и есть ловушка.

Движку не с чего узнавать поворот конкретной текстуры (поворот — данные геометрии грани, §63.2), поэтому он всегда использует значение фрагмента. Чтобы сэмплить другую текстуру нейтрально к повороту, поверните uv заранее на ту же четверть оборота — инверсию контр-поворота, — и она погасится:

```wgsl
// Нейтральный к повороту сэмплинг тексела: заранее поверните uv, чтобы контр-поворот
// bloxdTexel (на textureRotation этой грани) погасился.
// Из своего хука передавайте surface.textureRotation как r.
fn texelNeutral(id: u32, uv: vec2f, mip: f32, r: u32) -> vec4f {
    var turned = uv;
    if (r == 1u) {        // поворот: (x,y) -> (1-y, x)
        turned = vec2f(1.0 - uv.y, uv.x);
    } else if (r == 2u) { // (x,y) -> (1-x, 1-y)
        turned = vec2f(1.0 - uv.x, 1.0 - uv.y);
    } else if (r == 3u) { // (x,y) -> (y, 1-x)
        turned = vec2f(uv.y, 1.0 - uv.x);
    }
    return bloxdTexel(id, turned, mip);
}

// использование, внутри surface-хука:
//   let t = texelNeutral(bloxdTextureIdLava, fract(surface.uv),
//                        surface.mipLevel, surface.textureRotation);
```

(При `textureRotation == 0` компенсация не нужна. На практике большинство граней несёт 0; повёрнутые грани в меньшинстве — но дистрибутивный пак не должен на это полагаться.)

### 57.5 Разобранные примеры

**Эмиссия из яркости тексела.** Движок уже перемножает texture × tint × AO в `surface.colour`; здесь же мы вместо этого ведём эмиссию от собственной яркости текстуры, сэмплируя на один мип *выше* мипа грани — мягкое «блочное» среднее, переживающее дистанцию:

```wgsl
fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    // +1 мип = четверть разрешения: усреднение по 4x4 тексела, дёшево и стабильно
    let avg = bloxdTexel(surface.textureId, surface.uv, surface.mipLevel + 1.0);
    let lum = dot(avg.rgb, vec3f(0.2126, 0.7152, 0.0722));
    if ((surface.blockFlags & bloxdBlockFlagEmissive) != 0u) {
        // сохраняем вид движка, добавляем мягкий источник блума, пропорциональный самой текстуре
        out.emission += avg.rgb * lum * 0.5;
    }
    return out;
}
```

**Эффекты для конкретных текстур.** Сравнивайте `textureId` и действуйте только на избранных текстурах — замена v4 для «угадывания по цвету» и санкционированный способ, напр., заставить руды блестеть:

```wgsl
fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    var out = bloxdDefaultLight(surface, light);
    if (light.textureId == bloxdTextureIdDiamondOre) {
        // мерцание: фаза из мировой позиции + время
        let p = bloxdWorldPosition(light.position);
        let s = sin(bloxdSeconds() * 3.0 + p.x * 2.7 + p.y * 1.3 + p.z * 4.1);
        out.colour += vec3f(0.35, 0.45, 0.55) * max(0.0, s);
    }
    return out;
}
```

**Дистанционное размытие в стиле глубины резкости на деталях террейна** — далеко читается высокий мип, вблизи — родной:

```wgsl
fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    let d = distance(surface.position, bloxdEyePosition());
    if (d > 40.0 && surface.textureId != 0u) {
        // собственный тексел движка для этой грани — несёт с собой тинт и AO
        let own = bloxdTexel(surface.textureId, surface.uv, surface.mipLevel);
        if (any(abs(own.rgb - vec3f(0.0)) > vec3f(1e-6))) {          // защита от деления
            // уровень размытия растёт с дистанцией, до +3 мипов
            let blur = clamp((d - 40.0) / 60.0, 0.0, 3.0);
            let t = bloxdTexel(surface.textureId, surface.uv, surface.mipLevel + blur);
            // восстанавливаем тинт и AO отношением: (t / own) * colour
            out.colour = t.rgb / own.rgb * out.colour;
        }
    }
    return out;
}
```

(Трюк с отношением сохраняет движковое `colour = texture × tint × AO`: деление размытого тексела на родной тексел отменяет содержимое текстуры, оставляя коэффициент размытия, который перемножается обратно в `surface.colour`. На белых показаниях `vec4f(1.0)` — нетекстурированных гранях и гранях, вырезанных анти-X-ray, — проверка целиком пропускает эффект.)

### 57.6 Куда текстурный API *не* дотягивается

- **Из vertex-хуков вызвать нельзя.** `bloxdTexel` / `bloxdTextureSize` — функции surface/light-хуков; vertex-хук, до них дотягивающийся, отклоняется диагностикой «reaches» (§65.3).
- **Добавить текстуры нельзя.** Атлас принадлежит движку; API его читает, и только. Собственные текстуры остаются задачей системы текстур-паков, а не шейдер-паков.
- **Конфигурации рендерера без атласа деградируют до заглушек.** В конфигурации, где материал террейна не атласный, движок компилирует `bloxdTextureSize() -> vec2u(1u)` и `bloxdTexel(...) -> vec4f(1.0)` и подаёт четыре входных поля как `0u, 0u, vec2f(0.0), 0.0`. Код, написанный под настоящий атлас, там по-прежнему компилируется и выполняется — он просто видит белые текселы и размер 1×1. Напишите такой код терпимым к `textureId == 0` — и он будет терпим и к этому.

## 58. Четыре новых входных поля

И `BloxdSurfaceIn`, и `BloxdLightIn` получают одни и те же четыре поля в хвосте, процитированные из заголовка v4 (структура light несёт тот же квартет, что и surface, — ваш light-хук может действовать по текстуре, ничего не протаскивая через surface-хук):

```wgsl
    // These are 0 if the face has no texture.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // Texture coordinates in blocks; fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
```

- **`textureId`** — стабильный id, производный от имени (§57.3). `0` на нетекстурированных гранях; иначе никогда `0`.
- **`textureRotation`** — `0`–`3`, четверти оборота **по часовой стрелке**, как грань *показывает* текстуру. Берётся из геометрии/оверрайдов текстур-паков (§63.2); одинаковое значение в обоих хуках.
- **`uv`** — интерполированная текстурная координата **в блоках**: один блок площади грани отображается на один `1.0` размаха uv, поэтому `fract(uv)` — внутриблочный тайл текстуры, формулировка самого заголовка. На стене из повторяющегося камня `uv` растёт вдоль стены, а `fract(uv)` тайлится.
- **`mipLevel`** — собственный выбор мипа движка для этого фрагмента, выведенный из экранных производных позиции тексела и заклампленный в диапазон уровней атласа (точная формула — в §63.1). `0` на заполняющих экран гранях, растёт с дистанцией/наклоном. Это *чтение* — направить сэмплирование движка им нельзя, но можно передать его (или `± n`) в `bloxdTexel`.

Идея рецепта, уникальная для v4, — **привязанные к uv паттерны детализации, соблюдающие блочную сетку без мировых координат**:

```wgsl
// Тонкая сетка, привязанная к собственному тайлингу текстуры: видна на каждой
// текстурированной грани, стабильна при движении камеры и свободна от мирового
// дрейфа плавающей точки.
fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    let cell = fract(surface.uv * 8.0);               // 8x8 суб-тайлов на блок
    let edge = min(min(cell.x, 1.0 - cell.x), min(cell.y, 1.0 - cell.y));
    out.colour *= mix(vec3f(0.86), vec3f(1.0), step(0.06, edge));
    return out;
}
```

## 59. Переименования и семантические изменения

Четыре переименования, одно из которых инвертирует смысл. Всё остальное в заголовке — `bloxdPi`, `bloxdTau`, шесть констант `bloxdBlockFlag*` и их биты (1/2/4/8/16/32), `bloxdEyePosition` / `bloxdRenderOffset` / `bloxdSunDirection` / `bloxdSeconds`, `bloxdWorldPosition`, дефолтные хуки, матрица макросов `BLOXD_*`, матрица из 8 вариантов — не изменилось по сравнению с v3, а правила классификатора имён `blockFlags` из §42 переносятся дословно.

| v3 | v4 | Заметка |
|---|---|---|
| `l.fogVisibility` | `l.fogAlpha` | **смысл инвертирован** — переносите выражения, а не просто переименовывайте |
| `bloxdFaceBlock(pos, nrm)` | `bloxdFragmentBlockPosition(pos, nrm)` | тело идентично: `vec3i(floor(pos - nrm * 0.5)) + bloxdRenderOffset()` |
| `behind.found` | `behind.hit` | переименование поля `BloxdOpaqueBehind` |
| первая строка заголовка | — | `// Engine-provided and read-only, prepended to all packs. apiVersion 3.` → `// The Bloxd shader pack API, apiVersion 4. Read-only, prepended to all packs.` |

### 59.1 `fogVisibility` → `fogAlpha`: инвертированное

v3: `fogVisibility: f32, // 1 = no fog, 0 = fully fogged.` v4: `fogAlpha: f32, // 0 = no fog, 1 = only fogColour.` Применение тумана по умолчанию перевернулось вместе с ним:

```wgsl
// v3
fn bloxdApplyFog(colour: vec3f, light: BloxdLightIn) -> vec3f {
    return mix(light.fogColour, colour, light.fogVisibility);
}
// v4
fn bloxdApplyFog(colour: vec3f, light: BloxdLightIn) -> vec3f {
    return mix(colour, light.fogColour, light.fogAlpha);
}
```

Таблица переноса — у каждого идиома тумана v3 есть механическая замена в v4:

| Выражение v3 | Перенос в v4 |
|---|---|
| `l.fogVisibility` | `1.0 - l.fogAlpha` |
| `mix(l.fogColour, col, l.fogVisibility)` | `mix(col, l.fogColour, l.fogAlpha)` (или `bloxdApplyFog(col, l)`) |
| `mix(l.fogColour, col, max(l.fogVisibility, 0.15))` (пол тумана) | `mix(col, l.fogColour, min(l.fogAlpha, 0.85))` |
| «видимость тумана вблизи равна 1» | «fogAlpha вблизи равен 0» |

Поведение тумана по *дистанции* не изменилось — та же кривая, те же цвета; переехали только полярность поля и его имя. Отметьте также изменение комментария у `fogColour`: v3 говорил, что игры «always have fog»; v4 документирует `0 when the game has no fog` (и движок действительно подаёт `vec3f(0.0)`, когда туман сцены выключен) — это важно, если вы делите на `fogColour` или сравниваете с ним.

### 59.2 `bloxdFaceBlock` → `bloxdFragmentBlockPosition`

Чистое переименование — собственный doc-комментарий движка сменился с "the world block the face ... belongs to" на "identify the block's world position", тело байт-в-байт идентично, имена параметров по-прежнему свободны. Рецепт R4 и каждый вызов `bloxdFaceBlock(l.position, l.normal)` переносится поиском-и-заменой.

### 59.3 `found` → `hit`

`bloxdOpaqueBehind()` по-прежнему возвращает `BloxdOpaqueBehind`, по-прежнему компилируется только там, где определён `BLOXD_SCENE_DEPTH` (жидкостные программы — §60.4), и её реализация не изменилась, кроме имени поля. Перенесите `behind.found` → `behind.hit` и перечитайте семантику в комментариях заголовка v4: `position` и `distance` равны `0` (а не «бессмысленны») при `!hit`. R-E (поглощение водой) и компании переносятся механически.

## 60. Контракт strict-игр: vertex-хуки, `discard` и X-ray

Strict-игры — правило, а не исключение: **всё по умолчанию strict**, и только 12 allow-титулов, перечисленных в [списке режимов применения по играм](../internals/policy.md), выходят из правила (перепроверено дословно на бандле v4, 2026-10-27 — те же 12 титулов: Test Gym, Doodle Cube, Rocket Obby, Creative, Bloxd Hop, Fishing, Dress Up, Evil Tower, Plots, Test Mode, Tsunami Steal Brainrots, Work at a Restaurant; любой другой тайтл — survival, bedwars, skywars, custom games, ... — strict). v4 превращает то, что раньше было контрактом уровня документации, в **принуждаемый**: встроенный валидатор анализирует каждый strict-вариант и выдаёт специальные диагностики.

### 60.1 Два принуждаемых правила и их точные диагностики

> `bloxdTerrainVertex moves terrain, which strict games prevent.`
>
> `discard makes terrain see-through, which strict games prevent.`

Механика, восстановленная из валидатора:

- **Vertex-хук, определённый в strict-варианте** (т.е. не обёрнутый в `#ifndef BLOXD_STRICT`), вызывает первое сообщение. «Moves terrain» понимается буквально: подходит любой vertex-хук, не являющийся точным дефолтным passthrough (проверка — `movesVertices = vertexHook && !isExactDefault`; даже хук, возвращающий вход неизменным, но записанный иначе, считается движением).
- **`discard`, достижимый из surface- или light-хуков**, вызывает второе. Сам `discard` в v4 *впервые легален* для не-strict игр — жёсткий запрет v1–v3 снят, — но strict-игры трактуют его как X-ray (см. ниже).
- **Одно срабатывание отключает в strict-играх всё.** Если анализ strict-варианта выдаёт любую такую диагностику, валидатор обнуляет *все три* хука для strict-вариантов: пак по-прежнему загружается, по-прежнему работает в allow-играх, а в strict-играх не делает ровным счётом ничего. Незащищённый vertex-хук поэтому теряет не только колыхание — он теряет и ваше освещение.
- **Защищённый код сохраняет остальное живым.** С обёртками `#ifndef BLOXD_STRICT` из шаблона strict-варианты не определяют vertex-хук, не выдают диагностику, а ваши surface/light-хуки продолжают работать в strict-играх. В этом и весь смысл комментария шаблона: *"so our pack can stay on."*

UI настроек проводит автора ровно через это. Статусная строка, дословно:

> `Off in strict games. To run any other parts of the pack in them, wrap each one listed below in #ifndef BLOXD_STRICT ... #endif`

…за ней следует список провинившихся хуков, каждая запись при необходимости с суффиксом `(only in {{variants}})`, где оси вариантов пишутся как `strict / non-strict`, `lighting on / off`, `terrain / liquid`. А в игре, когда у пака в текущем режиме не остаётся ничего для запуска, чат показывает: `Your shader pack is off in this game.`

### 60.2 Почему: X-ray

Оба правила существуют по одной причине — в соревновательных играх шейдер, двигающий террейн или пробивающий в нём дыры, может раскрыть погребённые структуры и руды: vertex-хук, отодвигающий загораживающие блоки, — это wall-hack, а `discard` на избранных фрагментах — точечный X-ray. По этой же причине собственный шаблон движка защищает *только* vertex-хуки: эффекты surface/light (цвет, освещение, эмиссия) не могут двигать геометрию, поэтому безопасны везде. Комьюнити-канал туториалов подтверждает политику со стороны игроков — паки с колыханием травы — канонический пример «не работает в strict-играх», а анти-X-ray-выбраковка, которую выполняют strict-игры, ещё и целиком прячет некоторые текстуры от пути рендера, так что даже чтения текселов могут возвращаться белыми. Проектируйте strict-в-первую-очередь: относитесь к эффектам только для allow-игр (колыхание, дыры) как к прогрессивному улучшению, никогда — как к главной фиче.

### 60.3 Чего в v4 *нет*: API теней

Тот же комьюнити-канал фиксирует, что у автора движка был черновик API теней (файл-компаньон `bloxd-api`), который в этом релизе **не** отгружен; тени блоков/травы ожидаются вместе с будущим обновлением API шейдер-паков. Ничего теневого в бандле v4 нет (ни теневых символов, ни зарезервированных имён сверх списка §63.4) — считайте тени анонсированными, но неотгруженными, и не стройте дистрибутивные паки под них. Рецепты проекционных теней на `skyLight` из R9.12 остаются единственным теневым видом, доступным в v4.

### 60.4 Strict-резюме для авторов жидкостей

Матрица макросов не изменилась по сравнению с §46: `BLOXD_ALPHA` в каждом жидкостном варианте плюс не-strict террейн; `BLOXD_SCENE_DEPTH` в каждом жидкостном варианте; `BLOXD_STRICT` / `BLOXD_LIGHTING` на своих осях. Strict-жидкостные программы по-прежнему дают вам alpha и глубину — гейтируется по strict только alpha террейна.

## 61. Чек-лист миграции v3 → v4

1. **`pack.json`**: `"apiVersion": 4` — число, а не строка.
2. **Переименуйте** `bloxdFaceBlock` → `bloxdFragmentBlockPosition` везде (аргументы не изменились; имена параметров свободны, как всегда).
3. **Перенесите туман** (тихий шаг — пак, который его пропускает, компилируется и выглядит неправильно):
   - каждое чтение `l.fogVisibility` → `1.0 - l.fogAlpha`
   - каждый самописный `mix(l.fogColour, col, VIS)` → `mix(col, l.fogColour, ALPHA)` — или лучше замените на `bloxdApplyFog(col, l)` и отдайте формулу движку
   - идиомы пола/потолка инвертируются вместе с полем: `max(VIS, 0.15)` → `min(ALPHA, 0.85)`
4. **Перенесите рецепты глубины**: `behind.found` → `behind.hit`; `position`/`distance` равны `0` при `!hit`.
5. *(Опционально)* **Освойте текстурный API**: `bloxdTexel` / `bloxdTextureSize` / `bloxdTextureId*` и четыре новых поля (§57–§58). Помните о тонкости с поворотом (57.4) и о том, что код с текселами должен терпеть `textureId == 0`.
6. **Strict-аудит** (обязателен для распространения): оберните каждый vertex-хук в `#ifndef BLOXD_STRICT ... #endif`; если используете `discard`, оберните так же его (или содержащий его хук) — либо смиритесь с тем, что strict-игры отключат все хуки пака.
7. **Проверка компиляцией в игре** по всем 8 вариантам: экран загрузчика "Checking the pack..." валидирует все варианты разом — strict/не-strict × свет вкл/выкл × террейн/жидкость — так что одного прохода достаточно. Затем глазами проверьте одну allow-игру (Test Mode — самая быстрая) и одну strict-игру.
8. **Поднимите собственные метаданные версии** и перераспространите: сохранённые копии v3 на машинах игроков молча неактивны (§55), и только вкладка настроек говорит почему.

### 61.1 Полный перенос v3 → v4, до и после

```wgsl
// ---- пак v3: мерцание горячего песка + завязанная на туман эмиссия ----
fn bloxdTerrainSurface(s: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(s);
    if ((s.blockFlags & bloxdBlockFlagSand) != 0u) {
        let p = bloxdWorldPosition(s.position);
        out.colour *= 1.0 + 0.04 * sin(p.x * 7.0 + bloxdSeconds() * 2.0);
    }
    return out;
}

fn bloxdTerrainLight(s: BloxdSurface, l: BloxdLightIn) -> BloxdLight {
    var out = bloxdDefaultLight(s, l);
    // v3: светимся на дистанции, добавляя emission ПОСЛЕ тумана
    let col = mix(l.fogColour, out.colour, l.fogVisibility);
    out.colour = col + s.emission * l.fogVisibility;
    return out;
}
```

```wgsl
// ---- перенос в v4: тот же вид, плюс песок с учётом текселов и защита по текстуре ----
fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    if ((surface.blockFlags & bloxdBlockFlagSand) != 0u) {
        let p = bloxdWorldPosition(surface.position);
        out.colour *= 1.0 + 0.04 * sin(p.x * 7.0 + bloxdSeconds() * 2.0);
    }
    // дополнение v4: настоящее знание текстуры — затемняем мелкое зерно на близких гранях
    if (surface.textureId != 0u && surface.mipLevel < 1.0) {
        let t = bloxdTexel(surface.textureId, surface.uv, surface.mipLevel);
        let grain = abs(dot(t.rgb, vec3f(0.33)) - 0.5);
        out.colour *= 1.0 - 0.08 * grain;
    }
    return out;
}

fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    var out = bloxdDefaultLight(surface, light);
    // v4: перенос fogAlpha — emission добавляется после тумана, гейтится через (1 - fogAlpha)
    let col = mix(out.colour, light.fogColour, light.fogAlpha);
    out.colour = col + surface.emission * (1.0 - light.fogAlpha);
    return out;
}
```

Оба хука — только surface/light, поэтому этому паку не нужны обёртки `#ifndef BLOXD_STRICT`, и он работает (со своими новыми тексел-эффектами) и в strict-играх. Guard `textureId != 0u` покрывает нетекстурированные грани; на случай анти-X-ray-выбраковки strict-игр стилевые эффекты также должны изящно деградировать, если чтение тексела возвращается белым при ненулевом id — ветвитесь по диапазонам и отношениям, никогда — по одному ожидаемому значению тексела.

- **Текст заголовка переписан для ясности** — каждый doc-комментарий переформулирован (лаконичнее, во втором лице), без семантических изменений сверх §59. Размер 5 637 → 6 021 байт, 128 → 150 строк; первая строка теперь `// The Bloxd shader pack API, apiVersion 4. Read-only, prepended to all packs.`
- **Порядок эмиссии теперь документирован в самом заголовке**: `emission: vec3f, // Emissive RGB output, added after lighting, before fog.` — вывод §43 из v3, ставший официальной формулировкой.
- **i18n-поверхность** функциональности шейдер-паков — 58 ключей (билд v4); семейство загрузчика (`load*`) цитируется в §55–§56, семейство статусов (`status*`) — в §55, метки вариантов — в §60.1.
- **Справочный материал, встроенный** (вступление): сообщения об ошибках движка ссылаются на `bloxd-api.wgsl` и `BLOCK_TEXTURES.md`; это руководство вместо цитирования отгружает их содержимое — полный восстановленный заголовок (§67) и полный измеренный каталог (§68), — так что для создания или отладки пака ничего внешнего не нужно.
- **Автоперепроверка теперь срабатывает и на изменениях реестра текстур** (§65.1) — следствие присоединения хеша реестра к HEADER_VERSION. Сохранённый пак может переключиться в состояние «нужна перепроверка» после обновления движка, которое лишь *добавляет текстуры*, даже когда текст заголовка не изменился. Это сделано намеренно: ваши константы `bloxdTextureId*` запекаются в момент валидации.
- **Резервирование `bloxdSp*` расширено до 27 символов** (§63.4) — приватное пространство имён движка внутри генерируемых шейдеров. Правило резервирования на уровне пака не изменилось и шире: всё, что совпадает с `/^bloxd/i` (без учёта регистра), зарезервировано.

## 63. Внутрянка движка: как `bloxdTexel` на самом деле сэмплит

Как и §49–§51 для v3, всё ниже восстановлено дословно из продакшн-бандла (генератор кода чанка c54, билд `cnty9`, 2026-10-26) и является самым глубоким публичным описанием механизма. Ничто в §57 не выходит за рамки того, что доказывают эти фрагменты.

### 63.1 Сгенерированные функции, дословно

В конфигурациях рендерера с атласным текстурным режимом и без анимации движок эмитит в точности:

```wgsl
var<private> bloxdSpTextureRotation: u32;
@group(3) @binding(2) var<storage, read> bloxdSpTextureLayers: array<u32>;

fn bloxdTextureSize(bloxdSpMipLevel: f32) -> vec2u {
    return textureDimensions(textureAtlas0,
        u32(clamp(round(bloxdSpMipLevel), 0.0,
                  f32(textureNumLevels(textureAtlas0) - 1u))));
}

fn bloxdTexel(bloxdSpTextureId: u32, bloxdSpUv: vec2f, bloxdSpMipLevel: f32) -> vec4f {
    if (bloxdSpTextureId == 0u) {
        return vec4f(1.0);
    }
    // Each quarter turn clockwise the face shows its texture at reads the
    // unturned texture at (v, 1 - u)
    var bloxdSpTurned = bloxdSpUv;
    if (bloxdSpTextureRotation == 1u) {
        bloxdSpTurned = vec2f(bloxdSpUv.y, 1.0 - bloxdSpUv.x);
    } else if (bloxdSpTextureRotation == 2u) {
        bloxdSpTurned = 1.0 - bloxdSpUv;
    } else if (bloxdSpTextureRotation == 3u) {
        bloxdSpTurned = vec2f(1.0 - bloxdSpUv.y, bloxdSpUv.x);
    }
    let bloxdSpLayer = bloxdSpTextureId - 1u;
    return textureSampleLevel(textureAtlas0, atlasSampler, bloxdSpTurned,
                              bloxdSpLayer, round(bloxdSpMipLevel));
}
```

Когда атласов больше одного, хвост превращается в лестницу окон слоёв — атлас *k* владеет слоями `[k * layersPerAtlas, (k+1) * layersPerAtlas)`:

```wgsl
    if (bloxdSpLayer < 2u * layersPerAtlas) {
        return textureSampleLevel(textureAtlas1, atlasSampler, bloxdSpTurned,
                                  bloxdSpLayer - layersPerAtlas, round(bloxdSpMipLevel));
    }
    // ... одна ступень на каждый атлас, последняя — без проверки ...
    return textureSampleLevel(textureAtlasLast, atlasSampler, bloxdSpTurned,
                              bloxdSpLayer - N * layersPerAtlas, round(bloxdSpMipLevel));
```

Отметьте, что это доказывает: `textureId` — **глобальный 1-based индекс слоя по всем атласам** (`bloxdSpLayer = textureId - 1u`), а `bloxdTextureSize` читает только атлас 0 — это корректно, потому что все уровни атласов имеют одинаковые размеры.

### 63.2 Откуда берётся текстурный квартет фрагмента

Повершинный атрибут `texAtlasIndices` (индекс текстурного слота геометрии) разрешается **через storage-буфер**, напрямую не используется:

```wgsl
// vertex-стадия (вставляемый код):
vertexOutputs.vPackTexture = bloxdSpTextureLayers[
    min(u32(vertexInputs.texAtlasIndices), arrayLength(&bloxdSpTextureLayers) - 1u)];
```

`bloxdSpTextureLayers` заполняется на стороне JS, по одному `u32` на слот, упакованному ровно так:

```js
layers[slot] = (id & 0xffff) | ((rotation & 3) << 16);
```

Fragment-стадия распаковывает обе половины до запуска вашего surface-хука:

```wgsl
// fragment-стадия (вставляемый код, перед surface-хуком):
let bloxdSpTexture = fragmentInputs.vPackTexture;
bloxdSpTextureRotation = bloxdSpTexture >> 16u;      // -> поле textureRotation
// хвост конструктора BloxdSurfaceIn:
//   bloxdSpTexture & 0xffffu,        // textureId
//   bloxdSpTextureRotation,          // textureRotation
//   fragmentInputs.vMainUV1,         // uv
//   bloxdSpMipLevel                  // mipLevel (выводится ниже)
```

а мип выводится в точности так, как движок выводит свой:

```wgsl
let bloxdSpTexelUV = fragmentInputs.vMainUV1 * atlasWidth;
let bloxdSpDdx = dpdx(bloxdSpTexelUV);
let bloxdSpDdy = dpdy(bloxdSpTexelUV);
let bloxdSpLod = 0.5 * log2(max(max(dot(bloxdSpDdx, bloxdSpDdx),
                                    dot(bloxdSpDdy, bloxdSpDdy)), 1e-10));
let bloxdSpMipLevel = clamp(bloxdSpLod, 0.0,
                            f32(textureNumLevels(textureAtlas0) - 1u));
```

Два следствия, которые стоит усвоить: поворот — действительно **данные геометрии на слот** (нигде нет таблицы поворота-на-текстуру — это и есть *причина* существования тонкости из §57.4), и *дефолтный* (безпаковый) шейдер террейна сэмплит атлас иначе — он использует предповёрнутые копии слоёв прямо на сыром uv, тогда как путь пака нормализует к неповёрнутому слою и заново применяет поворот в `bloxdTexel`. Те же пиксели, два представления.

### 63.3 Анимация: лестница кадров

Для анимированных текстур назначение слоя обрастает вычислением кадра (это *вся* разница — сэмплирование, поворот и логика мипов не изменились):

```wgsl
    let atlasIdxIn = f32(bloxdSpTextureId - 1u);
    let animTick = material.anim.x;               // таймер анимации
    let animTickStride = material.anim.y;
    let numAnimTextures = material.anim.z;
    let animParamIndex = 3.0 * min(numAnimTextures, floor(atlasIdxIn));
    let animStateMask = animDataPerTex[i32(animParamIndex)];        // frames - 1
    let animTexIndexStart = animDataPerTex[i32(animParamIndex + 1.0)];
    let animInterval = max(animTickStride, animDataPerTex[i32(animParamIndex + 2.0)]);
    let animTickForTex = floor((animTickStride / animInterval) * animTick);
    let animState = animTickForTex
        - (animStateMask + 1.0) * floor(animTickForTex / (animStateMask + 1.0));
    let isAnimTex = min(1.0, animState);
    let bloxdSpFrame = (1.0 - isAnimTex) * atlasIdxIn
                     + isAnimTex * (animTexIndexStart + animState - 1.0);
    let bloxdSpLayer = u32(round(bloxdSpFrame));
```

`animDataPerTex` (группа 2, `array<f32>`) несёт по одному триплету `{mask, startLayer, interval}` на анимированную текстуру, кадры **считаются степенями двойки** (сборочная проверка на стороне JS отклоняет количества кадров не-степенью-2 сообщением `<block> has N animation states, which is not a power of 2`), а устройство со статическим сентинелом означает, что неанимированные индексы разрешаются той же арифметикой без ветвления. Сводка для авторов паков, ещё раз: *id стабилен, кадр автоматичен.* Интервалы — контент движка, и на `cnty9` они принимают ровно три значения — 200 мс (`lava`, `toxic_waste`, `radar_screen`), 250 мс (`smoke`, `homestead_core_mid`, машинные семейства `*_running`), 300 мс (семнадцать порталов, `toxic_waste_barrel_top`) — колонка по семействам — это §68.4.

## 64. Реестр имён текстур

Движок строит каталог имён один раз за сессию из реестра блоков — тот же конвейер, что породил `textureNameToIndex` системы текстур-паков. Сборщик (модуль 28833 в бандле), восстановленный как псевдокод:

```
for each (name, index) in textureNameToIndex:           # напр. ("lava0", 0), ("radar_screen0[rot[2", 19)
    if name matches /(.*)\[rot\[([1-4])$/ :              # слот повёрнутой копии
        turnedSlot → { id: rootUnturnedId, rotation: N-1 }   # запись таблицы из §63.2
        register alias: name  → root,  kind "rotation"
    else if index is an animation frame (not the base):  # через animDataPerTex
        register alias: name  → base,  kind "frame"
    else:
        canonical name = strip trailing "_?0" if this texture is animated
        named[canonical] = index + 1                     # значение bloxdTextureId*
```

Правила, важные для автора, без повторов:

1. **Пригодные имена — канонические имена**: базы анимации отбрасывают свой суффикс кадра (`lava0` → `lava`), семейства поворотов сворачиваются к корню (`chest_top[rot[1..4]` → `chest_top`), и оба сворачивания компонуются (`radar_screen0[rot[1..4]` → `radar_screen`, потому что это семейство к тому же анимировано). Любое другое имя файла — само по себе. Правописание константы затем переводит каноническое имя в CamelCase (§57.3).
2. **Псевдонимы кадров и поворотов известны и объясняются в ошибках** — их использование не даёт гадания «did you mean», а получает конкретное сообщение кадра/поворота (§57.3). Это намеренное проектирование API: `bloxdTexel` берёт на себя и анимацию, и поворот, поэтому обращаться к кадру или повёрнутой копии напрямую — всегда неверный ход.
3. **Неоднозначность убивает имя**: два имени, сворачивающиеся к одному ключу без учёта регистра/подчёркиваний, непригодны оба (`could name X and Y ... it can't be used`). Редко, но бывает — если ожидаемого вами имени нет в каталоге §68, это одна из причин.
4. **id — 1-based и равен «слой атласа + 1»**; id 0 «нет текстуры» зарезервирован как белый.

Измерено на живом реестре (билд `cnty9`, 2026-10-27, исполнением собственного модуля-сборщика движка на отгруженных данных): **1 219 записей атласа**, сворачивающихся в **57 семейств поворотов** (228 повёрнутых написаний) и **42 семейства анимации** (188 написаний кадров), что оставляет **905 пригодных именованных констант** — полный список, с id по каждому имени и обеими таблицами семейств, встроен как §68 ниже (а в актуальной форме — как [Каталог текстур](../api/texture-catalog.md)). Именно механизм хеша реестра из §65.1 не даёт запечённым значениям `bloxdTextureId*` молча устаревать по мере дрейфа этих чисел.

## 65. Внутрянка валидации v4: HEADER_VERSION, хеш реестра, специальные функции

### 65.1 HEADER_VERSION обрастает вторым хешем

Формат v3 был `6.<fnv1a32>` по пяти входам (§53). v4 сохраняет те же пять входов — токены заголовка по вариантам, лексический универсум парсера, четыре имени макросов, карту специальных функций и объявление `BloxdPackInputs`, — но префикс переезжает на `8.` **и добавляется второй FNV-1a-32, хеш по отсортированному списку `"<имя> <id>"` всего реестра текстур**:

```
v2 (sjr0p7):   6.bc5e8338
v3 (3ymzdd):   6.5bc26a63
v4 (cnty9):    8.<header-hash>.<registry-hash>     ← формат восстановлен из бандла
```

(Конкретные хеши v4 для этого руководства не измерялись — они вычисляются во время выполнения, — но формат точен, а значения v2/v3 выше — ранее опубликованные измерения. Любой экран настроек пака после обновления движка показывает текущий.)

Следствие — важная часть: **сохранённая валидация хранимого пака теперь инвалидируется и при изменениях реестра текстур** — движок добавляет текстуры, переименовывает, меняет порядок, — потому что ваши сравнения `bloxdTextureId*` разрешались против старого реестра. У потока «нужна перепроверка», который v3 запускал правками заголовка, появился второй, контентный триггер. Авторам действовать не нужно (движок перепроверяет автоматически); распространителям стоит просто этого ожидать.

### 65.2 Зарезервированные имена, снова и точно

Правило — regex `/^bloxd/i`, **без учёта регистра**, поэтому `BloxdFoo` зарезервирован точно так же, как `bloxdFoo`, а `bloxdTextureIdAnything` попадает под него, даже когда ничего не называет (вот почему диагностика опечатанного префикса в §57.3 существует как отдельное семейство сообщений). Набор `bloxdSp*` из 27 символов (§63.4) — дополнение со стороны движка внутри генерируемого кода.

### 65.3 Специальные функции: теперь три

Реестр специальных функций валидатора вырос с одной записи в v3 до трёх — две функции текстурного API зарегистрированы рядом с глубиной:

```js
[
  ["bloxdOpaqueBehind", { params: "", returns: "BloxdOpaqueBehind", symbol: "BLOXD_SCENE_DEPTH" }],
  ["bloxdTexel",        { params: "textureId: u32, uv: vec2f, mipLevel: f32", returns: "vec4f", symbol: null }],
  ["bloxdTextureSize",  { params: "mipLevel: f32", returns: "vec2u", symbol: null }]
]
```

`symbol: null` означает «без гейта по вариантам» — вызов возможен везде, где функция существует (surface/light-хуки). Обе диагностики «reaches» переносятся дословно и теперь покрывают и неправильное использование текстур:

> `${hook} reaches ${name}, which only surface and light hooks can use.` — например, `bloxdTexel` из vertex-хука.
>
> `${hook} reaches ${name}, which needs ${symbol}, but this hook also runs on ${program}, which doesn't define it; guard the call with #ifdef ${symbol}.` — например, `bloxdOpaqueBehind()` из террейн-хуков без обёртки (без изменений с v3 §53).

### 65.4 Что ещё переносится из v3 §53 без изменений

Проверка сигнатур хуков (точность по токенам в типах, свобода в именах — три записи сигнатур байт-в-байт идентичны v3), переименование с префиксом `pack_` с отображением в диагностике, семейство сообщений о необъявленных идентификаторах, дополнительный лексический универсум парсера (`bufferView`, `bufferArrayView`, `bufferLength`, `atomicStoreMax`, `atomicStoreMin` — по-прежнему не гарантированы в браузерах) и двухступенчатая валидация (собственный парсер, затем WGSL-компилятор браузера — по-прежнему строже; уроки §38 в силе).

## 67. Полный заголовок движка v4, дословно

Это заголовок в 6 021 байт и 150 строк, который движок предпосылает каждому паку, в точности как он отгружен в `cnty9` — тот же текст, чья первая строка открывается `// The Bloxd shader pack API, apiVersion 4. Read-only, prepended to all packs.` (§66). Он воспроизведён здесь целиком, потому что автору пака никогда не должно приходиться гадать, что движок объявляет от его имени: каждая свободная функция, которую вы можете вызвать, каждая `const`, с которой можно сравнивать, и обе входные структуры со всеми их полями и комментариями — ниже, в порядке движка.

Двух вещей в этом тексте *нет* — и никогда не было, потому что они генерируются по конфигурации рендерера во время компиляции, а не предпосылаются каждому паку: пары `bloxdTexel`/`bloxdTextureSize` (§63.1 содержит дословный сгенерированный WGSL) и 27 символов `bloxdSp*` движка (§63.4). Гейт `#ifdef BLOXD_ALPHA`, который вы видите в `BloxdSurface` и `bloxdDefaultSurface`, разрешается собственным препроцессором движка по вариантам — канонический текст сохраняет гейт, а §59.1/§56 объясняют, какие варианты его определяют.

// The Bloxd shader pack API, apiVersion 4. Read-only, prepended to all packs.

const bloxdTau: f32 = 6.2831853071796;

// These functions return 1 value per frame, the same for every call site.

// The camera's render position.
fn bloxdEyePosition() -> vec3f {
    return bloxdPackInputs.eyePosition;
}

// Changes as the player travels, so render positions stay close to 0,0,0.
// Integer distance, in blocks. Render position + this offset = world position.
// See bloxdWorldPosition for how this can be used.
fn bloxdRenderOffset() -> vec3i {
    return bloxdPackInputs.renderOffset;
}

// This unit vector points towards the sun, in world orientation; 0 when no sun.
fn bloxdSunDirection() -> vec3f {
    return bloxdPackInputs.sunDirection;
}

// Seconds since the page loaded. As an f32, it has sub-millisecond precision
// for the first 4.5 hours. Get a recurring timer using bloxdSeconds() % period.
fn bloxdSeconds() -> f32 {

}

// Each bit of the binary representation of blockFlags is a flag corresponding
// to a collection of blocks. The collections overlap, so blocks can be in 0-2+.
// (blockFlags & bloxdBlockFlagRock) != 0 // The block has this flag.
// (blockFlags & bloxdBlockFlagRock) == 0 // The block doesn't have this flag.

// Opaque blocks, leaves and ice included. Not glass, water, spawners, etc.
const bloxdBlockFlagOpaque: u32 = 1;

// These blocks emit light, e.g. neon, portals, lamps, lava, and glowing ores.
const bloxdBlockFlagEmissive: u32 = 2;

// 'Leafy', e.g. leaves, and grass blocks. Not cacti, mushroom blocks or hay.
const bloxdBlockFlagVegetation: u32 = 4;

// Dirt and soil, grass blocks included. Rocky Dirt is both dirt and rock.
const bloxdBlockFlagDirt: u32 = 8;

// Sand, Red Sand, and every sandstone, which is rock too.
const bloxdBlockFlagSand: u32 = 16;

// Stone variants, and more, e.g. gravel, ores, sandstone, magma and obsidian.
const bloxdBlockFlagRock: u32 = 32;

// Convert a render position to a world position, with possible f32 inaccuracy.
fn bloxdWorldPosition(position: vec3f) -> vec3f {
    return position + vec3f(bloxdRenderOffset());
}

// Using a fragment's position and normal, identify the block's world position.
fn bloxdFragmentBlockPosition(position: vec3f, normal: vec3f) -> vec3i {
    return vec3i(floor(position - normal * 0.5)) + bloxdRenderOffset();
}

struct BloxdVertexIn {
    position: vec3f, // Render position.
    normal: vec3f,   // Unit vector direction pointing away from the face.
    blockFlags: u32, // What kind of block. See bloxdBlockFlag*.
}

struct BloxdVertex {
    position: vec3f, // The render position output.
}

struct BloxdSurfaceIn {
    colour: vec3f,   // RGB colour = texture * tint * ambient occlusion.
    alpha: f32,      // Opacity.
    normal: vec3f,   // Unit vector direction pointing away from the face.
    position: vec3f, // Render position.
    blockFlags: u32, // What kind of block. See bloxdBlockFlag*.

    // These are 0 if the face has no texture.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // Texture coordinates in blocks; fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdSurface {
    colour: vec3f,   // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,      // Opacity output.
#endif
    emission: vec3f, // Emissive RGB output, added after lighting, before fog.
}

// ease-out curve, e.g. 6->0.45, 12->0.92. They all exclude ambientLightColour.
struct BloxdLightIn {
    litColour: vec3f,  // RGB surface colour, lit, before emission and fog.
    directional: f32,  // Summed Lambert from directional lights; 0 when off.
    ambient: vec3f,    // RGB ambient colour, added to directional light.
    blockLight: vec3f, // RGB block light; 0 without BLOXD_LIGHTING.
    skyLight: f32,     // Sky light; 1 without BLOXD_LIGHTING.
    ambientLightColour: vec3f, // Minimum RGB light; 1 without BLOXD_LIGHTING.
    skyLightColour: vec3f, // RGB colour of skyLight; 1 without BLOXD_LIGHTING.

    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // Texture coordinates in blocks; fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdLight {
    colour: vec3f, // RGB colour output.
}

struct BloxdOpaqueBehind {
    hit: bool,       // False where nothing opaque is behind (sky).
    position: vec3f, // The render position; 0 when !hit.
    distance: f32,   // From the camera; 0 when !hit.
}

fn bloxdDefaultVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return BloxdVertex(vertex.position);
}

fn bloxdDefaultSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
#ifdef BLOXD_ALPHA
    return BloxdSurface(surface.colour, surface.alpha, vec3f(0.0));
#else
    return BloxdSurface(surface.colour, vec3f(0.0));
#endif
}

// Applies this fragment's fog to colour, as the engine does.
fn bloxdApplyFog(colour: vec3f, light: BloxdLightIn) -> vec3f {
    return mix(colour, light.fogColour, light.fogAlpha);
}

fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return BloxdLight(bloxdApplyFog(light.litColour + surface.emission, light));
}

## 68. Полный каталог текстур (905 имён, измерено)

### 68.1 Как читать

Колонка **Имя** — это имя из реестра, тот идентификатор, который вы реально пишете. Правописание константы затем переводит его в CamelCase по границам `_` и `-` в точности как документирует §57.3: `grass_top` → `bloxdTextureIdGrassTop`, `lava` → `bloxdTextureIdLava`, `chest_double_top_1_lo` → `bloxdTextureIdChestDoubleTop1Lo`. Имена — это API; они переживают дрейф реестра, потому что валидатор заново разрешает их по живому реестру при загрузке.

Колонка **id** — то, с чем эта константа сравнивается как равная, — слой атласа + 1, измерено на `cnty9`. Используйте её для интерпретации дампов `surface.textureId` и отладочного вывода, а также для перекрёстной проверки плохо себя ведущего пака против сегодняшнего билда. Не хардкодьте её в WGSL: это снимок порядка атласа одного билда (§68.5 показывает, как быстро он движется).

Колонка **Примечания** помечает два свёрнутых семейства. `anim (N кадров)` означает, что сэмплирование этого имени автоматически возвращает текущий кадр анимации — никогда не адресуйте суффикс кадра (`lava0`, `radar_screen2`): это известные псевдонимы с отдельными диагностиками. `семейство поворотов (4 копии)` означает, что текстура существует только как предповёрнутые слоты атласа; имя адресует корень, а `bloxdTexel` заново применяет поворот (§57.4). Одно имя несёт оба примечания (`radar_screen`).

Чего здесь сознательно *нет*: остальные 416 написаний реестра — 188 псевдонимов кадров и 228 повёрнутых псевдонимов — не являются пригодными константами, и движок объясняет каждое своим семейством сообщений об ошибках, когда вы их пробуете (§57.3). Стоящая за всем этим таблица слоёв на 1 219 строк (включая 171 предповёрнутый слот) — внутренняя принадлежность движка, она раскрыта в §63.2/§63.4.

### 68.5 Дрейф реестра, измеренный (sjr0p7 → cnty9)

Реестр — это контент, отгружаемый вместе с билдом, поэтому он дрейфует с обновлениями блоков. Два билда, измеренных для этого руководства (2026-10-17 и 2026-10-27, десять дней разницы), показывают в точности, как быстро:

- Записи: 1200 → 1219 (98 добавлено, 79 удалено)
- Имена, сохранившие написание: 1121 — из них **779 сменили id** (69%)
- Соглашение об именовании мигрировало в середине месяца: 68 имён с суффиксом `_rot1..4` (напр. `chest_top_rot1`) стали слотами `[rot[1..4` (напр. `chest_top[rot[1`), и вместе с ними появились текстуры двойного сундука (`chest_double_*`, 8 записей)
- Число пригодных имён сдвинулось с 900 на 905, а хеш реестра в `HEADER_VERSION` (§65.1) заново инвалидировал каждый сохранённый пак с запечёнными id

Последний пункт — операционный урок: **пишите `bloxdTextureIdLava`, а не `19`** — константа-имя без изменений переживает каждый из этих пунктов, потому что валидатор заново разрешает её по живому реестру при загрузке.

### 68.6 Списки дрейфа, полностью (98 добавлено, 79 удалено)

Головные числа §68.5, расписанные имя за именем — потому что автору текстур-пака, обновляющему октябрьский пак, нужно точно знать, какие имена файлов перестали совпадать. Списки сравнивают слой *написаний* (имена файлов, которыми пользуются текстур-паки); именно правила сворачивания из §64 превращают написания в пригодные константы §68.2.

**Миграция сворачивания поворотов — 17 машинных top-текстур (68 написаний вышло, 68 слотов вошло).** `alloy_kiln_top`, `auto_bench_top`, `belt_tunnel_exit_top`, `belt_tunnel_top`, `burner_drill_top`, `crop_harvester_top`, `crusher_top`, `crystal_vat_top`, `deep_drill_top`, `electric_drill_top`, `press_top`, `recycler_top`, `shatter_mill_top`, `sky_tap_top`, `smelter_top`, `tree_cutter_top`, `wire_mill_top` переехали с написаний-вариантов `_rot1..4` на предповёрнутые слоты `[rot[1..4`; свёрнутый корень — пригодное имя, поэтому текстур-пак теперь поставляет один `X_top.png` вместо четырёх файлов `X_top_rotN.png`.

**Top-текстуры сундуков свернулись — 3 семейства (6 написаний вышло, 12 слотов вошло).** `chest_top_1`/`chest_top_2` → `chest_top`, `iron_chest_top_1`/`_2` → `iron_chest_top`, `moonstone_chest_top_1`/`_2` → `moonstone_chest_top`: написания с двумя вариантами стали предповёрнутыми слотами под корнем — переименуйте PNG-файлы соответственно.

**Новые текстуры — 17 имён.** Двойной сундук (`chest_double_back_hi`/`_lo`, `chest_double_front_hi`/`_lo`, `chest_double_top_1_hi`/`_lo`, `chest_double_top_2_hi`/`_lo`), семейство darkstone (`darkstone`, `darkstone_bricks`, `darkstone_bricks_cracked`, `darkstone_bricks_lava`, `darkstone_engraved`, `darkstone_smooth`), `pure_copper_ore`, `pure_voltite_ore` и `forge_hopper_top`.

**Одно простое сворачивание.** `ghost_chest_top_1`/`ghost_chest_top_2` схлопнулись в единственный `ghost_chest_top`.
