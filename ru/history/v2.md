# Руководство по миграции на API v2

> Версия: 2 · Статус: Historical (руководство по миграции той эпохи; целевой билд указан в тексте)
Целевой билд: `6qxffk.main.5912a15f.js` (продакшн-деплой на 2026-10-16). Части I–VII этого руководства уже переписаны на базу v2; это руководство собирает миграционные моменты с v1 и новые возможности v2. Примеры кода новых возможностей проходят валидацию 8/8 вариантов на компиляторе v2 и валидацию браузерным WGSL-компилятором (Tint) (§38), но v2-конверсия существующих рецептов — механическая подстановка идентификаторов, поэтому перед распространением всегда проверяйте компиляцией в игре.

## 31. Судьба v1-паков (сначала вывод)

Игра требует, чтобы `apiVersion` манифеста **строго совпадал с 2**. Загрузка v1-пака отклоняется с `This pack is for shader pack API version 1. Bloxd supports version 2.` (ключ i18n `shaderPack:loadWrongApiVersion`). **Параллельной поддержки v1/v2 нет**. Движок также перепроверяет у сохранённых паков `validation.headerVersion` (хеш полного текста заголовка), так что механизм, автоматически помечающий сохранённые паки «нужна перепроверка» при обновлениях движка, тот же, что в v1.

## 32. Полное переименование идентификаторов (таблица соответствия)

В v2 подчёркивания унифицированы в camelCase. **Старые имена полностью неиспользуемы.**

| v1 | v2 |
|---|---|
| `bloxd_terrain_vertex` | `bloxdTerrainVertex` |
| `bloxd_terrain_surface` | `bloxdTerrainSurface` |
| `bloxd_terrain_light` | `bloxdTerrainLight` |
| `bloxd_liquid_vertex` | `bloxdLiquidVertex` |
| `bloxd_liquid_surface` | `bloxdLiquidSurface` |
| `bloxd_liquid_light` | `bloxdLiquidLight` |
| `bloxd_defaultVertex` | `bloxdDefaultVertex` |
| `bloxd_defaultSurface` | `bloxdDefaultSurface` |
| `bloxd_defaultLight` | `bloxdDefaultLight` |
| `bloxd_VertexIn` | `BloxdVertexIn` |
| `bloxd_Vertex` | `BloxdVertex` |
| `bloxd_SurfaceIn` | `BloxdSurfaceIn` |
| `bloxd_Surface` | `BloxdSurface` |
| `bloxd_LightIn` | `BloxdLightIn` |
| `bloxd_Light` | `BloxdLight` |
| `bloxd_packInputs` (внутренний uniform) | `bloxdPackInputs` (`@group(3) @binding(0)`, 64B) |

Виды хуков (vertex / surface / light × террейн / жидкость, всего 6) и формат `pack.json` (`apiVersion` / `name` / `author`) не изменились. Лимиты загрузчика тоже неизменны (zip 32MB / 1024 записи / 256 файлов `.wgsl` / 256KB суммарно / 64KB манифест).

## 33. Куда переехали удалённые поля

В v1 `time` / `eyePosition` / `sunDirection` / `originOffset` были полями структур. В v2 **эти поля удалены; вместо них — функции заголовка, читающие uniform движка (`bloxdPackInputs`)**. Поскольку функции читают uniform напрямую, **их можно вызывать из функций уровня модуля вне хуков и из vertex-хуков**.

| v1 | v2 |
|---|---|
| `s.time` / `v.time` / `l.time` | `bloxdTime()` |
| `s.sunDirection` / `l.sunDirection` | `bloxdSunDirection()` |
| `s.eyePosition` / `l.eyePosition` | `bloxdEyePosition()` |
| `s.originOffset` / `l.originOffset` | `bloxdOriginOffset()` |
| `s.position + vec3f(...)` для перевода в мировые координаты | `bloxdWorldPosition(s.position)` |
| `vec3i(floor(pos - normal*0.5)) + originOffset` | `bloxdFaceBlock(pos, normal)` |

## 34. Новая возможность 1: `blockId` (шейдинг по блокам)

Все три структуры `BloxdVertexIn` / `BloxdSurfaceIn` / `BloxdLightIn` получили `blockId: u32`. Это **ID владеющего блока** (0–65535), единый по всей грани (передаётся с `@interpolate(flat)`). Используйте его для идентификации типа блока независимо от цвета текстуры. Но таблица соответствия ID и типов блоков живёт внутри движка и из паков не видна, так что **какой ID какому блоку соответствует — измеряется в мире или берётся из справочника ниже**. Внутри этот ID переносится запечённым в α цвета вершины (младшие 8 бит) и в w нормали (старшие 8 бит) — всего 16 бит, откуда и берётся потолок 65535. Сама система blockId активируется, только пока существует активный шейдер-пак (без пака провода сохраняют свои целевые паддинги, но в определениях структур из части II эта разница ненаблюдаема).

**Справочник**: автор публикует список игровых записей в [Bloxd-Entries-Data](https://github.com/imu31465/Bloxd-Entries-Data) (`entries.json`: таблица id ↔ имя блока; варианты поворота/meta вроде `Furnace|meta|rot2` перечислены отдельными ID). Соответствия могут меняться с обновлениями игры — для чего-то окончательного подтверждайте в живой игре.

Примеры часто встречающихся блоков (из entries.json на 2026-10-18; показаны только семейства террейна с низкими id):

| ID | Имя блока | ID | Имя блока |
|---|---|---|---|
| 0 | Air | 15 | Maple Wood Planks |
| 1 | Unloaded | 28 | Stone |
| 2 | Dirt | 29 | Messy Stone |
| 3 | Messy Dirt | 31 | Smooth Stone |
| 4 | Grass Block | 126 | Water |
| 5 | Sand | 128 | Bricks |
| 6 | Clay | 139 | Ice |
| 7 | Gravel | 147 | Bedrock |
| 8 | Snow | 149 | Cactus |
| 9 | Maple Log | 1491 | Lava |

entries.json перечисляет и неблочные записи (инструменты и т.п.), но до хуков террейна / жидкостей доходят только id блочных семейств.

### R-F. Тинт по типу блока через blockId

```wgsl
fn blockTint(blockId: u32) -> vec3f {
    // напр.: каменные id (старший битовый паттерн) — в холодный
    let stripe = f32((blockId >> 4u) & 1u);
    return mix(vec3f(1.0), vec3f(0.85, 0.95, 1.0), stripe * 0.5);
}

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var result = bloxdDefaultSurface(surface);
    result.colour *= blockTint(surface.blockId);
    return result;
}
```

### R-G. Измерение blockId в мире — пак отображения битовых плоскостей

Дебаг-рецепт для выяснения id блоков, отсутствующих в таблице соответствий, прямо в мире. Перебирайте ведущую константу `plane` значениями `0, 1, 2, …`, читая цвет грани блока, который хотите определить.

```wgsl
const plane: u32 = 0u;

fn bloxdTerrainSurface(s: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(s);
    let d = (s.blockId >> (plane * 3u)) & 7u;
    var palette = array<vec3f, 8>(
        vec3f(0.0, 0.0, 0.0), vec3f(1.0, 0.0, 0.0), vec3f(0.0, 1.0, 0.0), vec3f(1.0, 1.0, 0.0),
        vec3f(0.0, 0.0, 1.0), vec3f(1.0, 0.0, 1.0), vec3f(0.0, 1.0, 1.0), vec3f(1.0, 1.0, 1.0));
    out.colour = palette[d];
    return out;
}
```

Цвет грани кодирует 3 бита blockId напрямую как RGB (чёрный = 0 / красный = 1 / зелёный = 2 / жёлтый = 3 / синий = 4 / маджента = 5 / циан = 6 / белый = 7). Одно наблюдение даёт одну восьмеричную цифру. Если p0 → p3 дают 3, 2, 7, 2, то восьмеричное 2723 = 1491, прочитанное со старшей цифры, и есть id (Lava). Для семейств террейна с низкими id хватает двух наблюдений (p0, p1). Использует только surface-хук, так что работает и в strict-титулах.

### R-H. Качание только листвы — ограничение vertex-хука по blockId

Рецепт ветра R7 ([Рецепты](../recipes/)) волнует весь террейн, но vertex-хук тоже может читать `blockId`, поэтому цели можно ограничить блоками листвы. Список id и массив для WGSL (замер на 2026-10-18; 22 вида — Pine / Aspen / Maple / Jungle / Plum / Cedar / Palm / Autumn Maple / Fallen Maple / Pear / Cherry / Fallen Cherry / Spectral / Mango / фруктовые варианты / Autumn Aspen):

```wgsl
const LEAF_IDS = array<u32, 22>(
    100u, 101u, 102u, 103u, 491u, 492u, 493u, 653u, 655u, 911u,
    1226u, 1227u, 1636u, 1969u, 2019u, 2020u, 2021u, 2022u, 2023u,
    2024u, 2025u, 2085u);

// vertex-хуки автоматически отключаются в strict-титулах (см. §36)
#ifndef BLOXD_STRICT

fn sp_isLeaf(id: u32) -> bool {
    for (var i = 0u; i < 22u; i++) {
        if (LEAF_IDS[i] == id) { return true; }
    }
    return false;
}

fn bloxdTerrainVertex(v: BloxdVertexIn) -> BloxdVertex {
    var out = bloxdDefaultVertex(v);
    if (sp_isLeaf(v.blockId)) {
        let wp   = bloxdWorldPosition(v.position);
        let t    = bloxdTime();
        // смещение — гладкая функция мировой позиции. Общие вершины, указывающие
        // на одну и ту же точку мира, двигаются одинаково, поэтому грани никогда не рвутся ([Рецепты](../recipes/) R7 — тот же принцип)
        let sway = sin(wp.x * 0.9 + t * 1.7) * cos(wp.z * 0.7 + t * 1.1);
        out.position.x += sway * 0.045;
        out.position.z += sway * 0.030;
    }
    return out;
}

#endif
```

- Список id растёт с обновлениями движка (только за время замера в новом билде добавилось 50 видов блоков). Чтобы продолжать им пользоваться, ищите добавления через [Bloxd-Entries-Data](https://github.com/imu31465/Bloxd-Entries-Data) или замерами с битоплоскостным дисплеем R-G — и расширяйте массив
- `Fallen Maple Leaves` (655) / `Fallen Cherry Leaves` (1227) — нетвёрдые листовые коврики на земле. Качание создаёт впечатление, что они отрываются от земли, так что исключить их из массива — один из вариантов
- В strict-титулах vertex-хук отключается целиком, но с гардом выше пак просто «перестаёт качаться» — эффекты фрагментной стороны продолжают работать

## 35. Новая возможность 2: `BLOXD_SCENE_DEPTH` и `bloxdOpaqueBehind()` (главное)

Доступ к глубине, структурно невозможный в v1, разблокирован **только для liquid-программ**. Цвета нет, но **геометрия — дистанция и позиция непрозрачной грани позади — доступна**. Типовое применение — расчёт цвета поглощения по измеренной толщине воды.

Правила использования:

| Использование | Результат |
|---|---|
| Вызов без guard'а в `bloxdLiquidSurface` / `bloxdLiquidLight` | OK (в жидкостных вариантах всегда определён) |
| Вызов без guard'а в `bloxdTerrainSurface` | ERROR. Оберните в `#ifdef BLOXD_SCENE_DEPTH` |
| Вызов в vertex-хуках | ERROR (только хуки surface / light) |

Чтобы использовать глубину и в хуках террейна, оборачивайте в `#ifdef BLOXD_SCENE_DEPTH` (хуки террейна переиспользуются liquid-программами, так что глубина жива только на жидкостной стороне).

### R-E. Поглощение по толщине воды (Beer-Lambert)

```wgsl
fn bloxdLiquidSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var result = bloxdDefaultSurface(surface);
    let behind = bloxdOpaqueBehind();
    if (behind.found) {
        // длина столба воды = отсюда до непрозрачной грани позади
        let thickness = distance(behind.position, surface.position);
        // поглощение Beer-Lambert: красный гаснет быстро, синий уходит далеко
        let absorb = exp(-thickness * vec3f(0.35, 0.14, 0.08));
        result.colour *= absorb;
    } else {
        // позади ничего = тянуть к синеве глубокой воды
        result.colour = mix(result.colour, vec3f(0.05, 0.15, 0.30), 0.4);
    }
    return result;
}
```

Применения: поглощение/рассеяние по толщине, проекция ряби в стиле каустики из мировых координат дна через `behind.position`, различение неба и перекрытия через `found=false` для отражения неба на воде, ступенчатая муть по глубине. Если пайплайн копирования глубины не удалось построить, он безопасно деградирует к «позади ничего». Готовность depth-текстуры решается один раз, при создании рендерера страницы, по признаку «читает ли активный пак глубину» — поэтому **при использовании пака, читающего глубину, всегда перезагружайте страницу**. Если глубина запрошена при активном паке, но страница не была перезагружена, консоль единожды показывает предупреждение `…reads scene depth on a page that didn't turn it on`, и текстура глубины подменяется фолбэком 1×1, из-за чего `bloxdOpaqueBehind()` всегда возвращает `found = false`.

## 36. Прочие изменения v2

- **Fallback хуков**: при неопределённом `bloxdLiquidXxx` liquid-программы падают на хуки террейна. **Пак с одними хуками террейна действует на воду как есть**. Если это нежелательно, явно определяйте хуки жидкостной стороны.
- **Guard'ы полей `BLOXD_LIGHTING` больше не нужны**: `blockLight` и др. существуют во всех вариантах, держа дефолты в unlit (0 / 1 / белый / 0). Используйте `#ifdef BLOXD_LIGHTING` только для проверки освещённости. Сохранение существующих guard'ов ничего не меняет.
- **Условие определённости `BLOXD_ALPHA` изменилось**: определён в не-strict вариантах террейна и во всех жидкостных вариантах, не определён в strict × террейн. При записи alpha в хуках террейна guard оставляйте.
- **Прямое конструирование структур запрещено**: вызовы конструкторов вроде `BloxdLight(...)` отклоняются статической валидацией. Всегда изменяйте от `bloxdDefault*` или используйте копию входа.
- **`let _ =` становится `_ =`**: отбрасывающее присваивание WGSL `_ = f();` валидно, а `let _ = f();` отклоняется.
- **offInStrict**: определение vertex-хука или достижимый из surface / light-хуков `discard` вместо ошибки автоматически деактивирует весь пак в strict-играх (UI настроек показывает `shaderPack:offInStrict`; в allow-играх всё равно работает). Оборачивайте vertex-хуки и `discard` в `#ifndef BLOXD_STRICT`. Обратите внимание: само сообщение официального UI настроек предписывает «wrap what remains with `#ifndef BLOXD_STRICT`» — эта практика — официальная рекомендация, а не конвенция.
- **Расширения тумана**: режимы LINEAR / EXP / EXP2 реализованы, но настройки игры по-прежнему всегда используют LINEAR, так что существующие спеки тумана продолжают работать. Семантика `fogColour` теперь официально задокументирована (чёрный — только в полностью бестуманных сценах).
- **Без изменений**: lift-кривая, 35%-пол каналов, затухание heldLight (`pow(lightDist, 0.75)`) и ambient-буст, спека направлений солнца/луны, дефолтный цвет тумана, цикл time (3600 с), направленные света (макс. 4), только Lite (WebGPU), механизм сохранений (IndexedDB), зарезервированность `mod`.

## 37. Чек-лист миграции v1 → v2

1. **pack.json**: `"apiVersion": 1` → `"apiVersion": 2`
2. **Идентификаторы**: заменить все по таблице §32 (имена хуков, имена структур, имена default-функций)
3. **Перенос удалённых полей**: в функции заголовка по таблице §33 (`s.time` → `bloxdTime()` и т.д.)
4. **Переименовать `fogFactor` → `fogVisibility`**
5. **Убрать прямое конструирование структур**
6. **Исправить `let _ =` на `_ =`**
7. **Обернуть vertex-хуки и discard в `#ifndef BLOXD_STRICT`**
8. **Проверить, что вода тоже ощущает эффекты хуков террейна**; при нежелательности явно определить liquid-хуки
9. (Опционально) Вести туман самим от `litColour` / добавить поглощение по толщине воды через `bloxdOpaqueBehind()` / поблочную стилизацию через `blockId`
10. **Проверить и вторую ступень (браузерный Tint)** — особенно расставить скобки в выражениях, содержащих `^` `&` `|` `<<` `>>`. Код, проходящий статическую валидацию, может быть отклонён браузером (§38)

## 38. Вторая ступень проверки — браузерный WGSL-компилятор строже встроенного парсера

Валидация паков в игре — **двухступенчатая**. Первая ступень — статическая валидация (встроенный в движок JS-парсер. Он проверяет пак-специфичные правила: сигнатуры хуков, запрещённый синтаксис, использование sceneDepth), а вторая ступень — браузерная валидация (она компилирует приложенные к результату компиляции стабы настоящей реализацией WebGPU, отображая ошибки с обратным маппингом на строки исходных файлов пака. Фраза UI «Saved, but it won't run until you fix these errors» — это и есть эта ступень). Суффикс вроде `(only in terrain)` в конце сообщения об ошибке — это «вид program того варианта, в котором возникла эта ошибка».

Встроенный парсер не реализует правила связывания операторов WGSL, поэтому **код, проходящий статическую валидацию, всё равно может быть отклонён браузером**. Классическая жертва — идиома целочисленного хеша:

| Оператор | Следствие |
|---|---|
| `<<` `>>` | Могут связываться напрямую только на унарном уровне. `a + b << c` — ошибка |
| `&` `^` `\|` | Могут связываться напрямую только на унарном уровне. `a * b ^ c` — ошибка |
| `&&` `\|\|` | Нельзя смешивать. `a && b \|\| c` — ошибка |

### Расстановка скобок (NG / OK)

```wgsl
// NG — проходит статическую валидацию, но браузер (Tint) отклоняет:
//     mixing '*' and '^' requires parenthesis
let h = a * 73856093u ^ b * 19349663u ^ c * 83492791u;

// OK — расставьте скобки вокруг каждого умножения (цепочка одного оператора A ^ B ^ C сама по себе левоассоциативна и легальна)
let h = (a * 73856093u) ^ (b * 19349663u) ^ (c * 83492791u);
```

Код, напечатанный в этом руководстве, этого паттерна не содержит (смешение `+`/`*` в `pack_hash3` и `h ^ (h >> 16u)` уже в скобках, т.е. соответствует спеке). Когда напишете пак, пропускайте его через обе ступени — первую и вторую.

## 39. О независимо похожих материалах

Существует материал сообщества почти с тем же содержанием: [шейдер GlitchHunterCoder/Bloxd-Essay](https://github.com/GlitchHunterCoder/Bloxd-Essay/tree/main/Shader). Он был опубликован раньше этого руководства, но **содержание этого руководства — из собственного анализа glm настоящих bundle-файлов Bloxd (набора webpack-чанков), а не копипаст**. Оба совпадают потому, что независимое исследование одной и той же реализации приводит к тем же выводам.
