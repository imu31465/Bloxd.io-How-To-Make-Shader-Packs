# API v5 Migrationsleitfaden

> Version: 5 · Status: Historical (Migrationsleitfaden der jeweiligen Ära; der Ziel-Build steht im Text)

Ziel-Build: `ab90qa.main.6188124c.js` — **seit der Messung am 2026-11-03 gleichzeitig in Produktion und Preprod live**, und die beiden Bundles sind wieder byte-identisch (md5 `fc3322212d15be2445c0e8df9733fcc` auf dem Haupt-Bundle, live von beiden Hosts geladen), daher gilt alles hier unverändert für die Produktion. Dies ist die größte API-Revision seit v3: das Haupt-Bundle wuchs auf 3,39 MB (+115 KB über den letzten v4-Build), die Chunk-Map hat jetzt 195 ids (c0–c195, 188 emittiert nach den 7 bekannten Löchern), die Shader-Pipeline sitzt weiterhin im c51–c56-Cluster (Loader c53, Validator/Header/Registry-Builder c55, WebGPU/Codegen c56, Fog c9) — aber die Standard-Pack-Vorlage zog nach c116 (in `tcwczu` war sie c124). Keins dieser Layout-Details ist für ein Paket sichtbar.

Was *doch* sichtbar ist: Der Engine-Header wuchs von 6.021 auf **8.954 dekodierte Bytes** (151 → 208 Zeilen) — fast jede Struktur erhielt Felder, vier neue Funktionen dokumentieren das hauseigene Beleuchtungsrezept der Engine, und die `blockFlags`-Bitmaske ist weg, ersetzt durch eine echte `BloxdFlags`-Struktur aus Booleans. Auch das Kompilierzeit-Gate `#ifdef BLOXD_LIGHTING` ist weg: Der Beleuchtungszustand zog als `lit: u32`-Mitglied ins Uniform pro Frame und wird zur Laufzeit mit `bloxdLit()` abgefragt. Die Standard-Pack-Vorlage liefert jetzt **alle neun Hooks** statt sechs. Und der engine-interne `bloxdSp*`-Namespace wuchs von 27 auf 46 Symbole.

Das v5-Änderungsset auf einen Blick:

| Bereich | v4 | v5 |
|---|---|---|
| `pack.json` `apiVersion` | `4` (strikt) | **`5` (strikt)** — v4-Pakete werden beim Laden abgelehnt |
| Block-Identität | `blockFlags: u32` + 6 `bloxdBlockFlag*`-Bit-Konstanten | **`flags: BloxdFlags`** — 14 benannte bool-Felder (§71) |
| Neue Flag-Arten | — | **`slab` `stairs` `flat` `placed` `held` `dropped` `thrown` `lifeform`** — Modelle und Entities sind jetzt vom Terrain unterscheidbar (§71) |
| Modell-Position | — | **`localPosition: vec3f`** auf jeder Eingabestruktur (§72) |
| Enchant & Overlay | engine-exklusiv | **Eingaben + Ausgaben `enchantTier` / `enchantColour` / `enchantSpeed` / `overlayColour`** (§72–§73) |
| Beleuchtungs-Gate | `#ifdef BLOXD_LIGHTING` (Kompilierzeit, 8 Varianten) | **entfernt** — das Uniform erhält `lit: u32` @ Offset 4; zur Laufzeit **`bloxdLit()`** testen; 6 Varianten (§74) |
| Beleuchtungs-Helfer | engine-privates `litColour` | **öffentlich**: `bloxdShading()`, `bloxdWorldLight()`, `bloxdLitColour()` (§74) |
| `bloxdFragmentBlockPosition()` | im Header dokumentiert | **aus dem dokumentierten Header entfernt** — wird aber weiterhin injiziert und vom Validator weiterhin akzeptiert (§75) |
| Standardpaket | 6 Hooks (Vertex+Surface) | **9 Hooks** — Light-Hooks inklusive (§76) |
| `bloxdChunkSize` | nicht im Header | **neue Konstante `bloxdChunkSize: i32 = 32`** (§78) |
| `bloxdSp*`-Namespace | 27 Symbole | **46 Symbole** (+20, −1) (§79) |
| Textur-Registry | 905 nutzbare Namen | **896 nutzbare Namen** — +1, −10 (§80) |
| Loader-Limits, Zip-Regeln, `pack.json`-Form, Hook-Namen, Strict-Vertrag | — | **eingefroren, byte-identische Limits** (§70) |

Die Umstellung von v4 ist größtenteils mechanisch (§77): Die eine stille Falle ist diesmal eine andere — ein Paket, das noch `blockFlags` liest oder Light-Hooks mit `#ifdef BLOXD_LIGHTING` schützt, **scheitert mit einer spezifischen Meldung an der Validierung** (der Analyzer erklärt inzwischen beides), also verhält sich nichts still falsch; aber ein Paket, das *nur die alten Bit-Konstanten dem Namen nach* liest, verweigert das Laden, bis es portiert ist. Wie immer: vor der Verteilung per In-Game-Kompilierung prüfen.

## 69. Das Schicksal von v4-Paketen (erst das Fazit)

**Jedes v4-Paket — einschließlich jedes als v4 verteilten Pakets — scheitert jetzt in Produktion exakt beim Laden.** Der Loader vergleicht `manifest.apiVersion !== 5` mit strictem JavaScript-`!==` — die Versionskonstante `5` und die Header-Vorlage leben in diesem Build im selben Modul (Modul 29836), daher wandern die Prüfung und der Header-Text, gegen den sie validiert, gemeinsam. Das JSON muss die *Zahl* `5` tragen; ein String `"5"` scheitert und wird mit seiner JSON-Schreibweise gemeldet, exakt wie in v4.

Die beiden Ladezeit-Meldungen sind unverändert aus v4, wortlautgetreu aus dem Live-i18n-Wörterbuch:


> `This pack is for shader pack API version {{packVersion}}. Bloxd supports version {{version}}.` — der Key ist vorhanden, gleich aber nicht 5.

Ein gespeichertes (zuvor funktionierendes) v4-Paket wirft dem Spieler nichts entgegen: Das Stored-Pack-Ergebnis löst sich zu `{kind: "none", reason: "otherApiVersion"}` auf, das Paket ist still inaktiv, und der Shader-Pack-Einstellungs-Reiter erklärt sich mit der Statuszeile:

> `This shader pack is for API version {{packVersion}}, so it won't run. Load a version {{version}} pack to replace it.`

Die Manifest-Regeln sind sonst nachgemessen und unverändert: `pack.json` muss ein JSON-Objekt an der Zip-Wurzel sein; `apiVersion` muss vorhanden sein und `=== 5`; `name` ist Pflicht, ein String, nach dem Trimmen nicht leer; `author` ist optional, muss aber, falls vorhanden, ein String sein; alles andere im Manifest wird ignoriert.

## 70. pack.json, der Loader und das Uniform (was unverändert bleibt)

Das gesamte Paketmodell wird von v4 Byte für Byte übernommen. Die Loader-Limits, nachgemessen am Live-Loader-Chunk (c53):

| Limit | Wert | Meldung bei Überschreitung |
|---|---|---|
| `.wgsl`-Dateien pro Paket | 256 | `The pack has more than 256 .wgsl files.` |
| `.wgsl`-Quelltext gesamt | 256 KB | `The pack's .wgsl files are over 256 KB in total.` |
| `pack.json`-Größe | 64 KB | `pack.json is over 64 KB.` |
| Zip-Größe | 32 MB | `The zip is over 32 MB.` |
| Zip-Einträge | 1.024 | `The zip has more than 1024 entries.` |
| Zip-Form | — | geteilte Zips, Zip64, verschlüsselte Einträge, nicht unterstützte Kompressionsmethoden werden je mit einer eigenen Meldung abgelehnt; jede Datei muss gültiges UTF-8 sein; genau ein `pack.json`; keine doppelten Pfade |

Das Uniform pro Frame ist weiterhin `@group(3) @binding(0) var<uniform> bloxdPackInputs: BloxdPackInputs`, weiterhin 64 Bytes — aber es erhielt ein Mitglied. Die Layout-Tabelle, aus dem Live-Uniform-Layout-Modul:

| Offset | Feld | Typ | Anmerkung |
|---|---|---|---|
| 0 | `seconds` | `f32` | Basis von `bloxdSeconds()` |
| 4 | `lit` | `u32` | **neu in v5** — 1, wenn Block-/Himmelslicht an ist; Basis von `bloxdLit()` |
| 16 | `renderOffset` | `vec3i` | Basis von `bloxdRenderOffset()` |
| 32 | `sunDirection` | `vec3f` | Basis von `bloxdSunDirection()` |
| 48 | `eyePosition` | `vec3f` | Basis von `bloxdEyePosition()` |

`lit` rückt in das Padding, das v4 bereits zwischen `seconds` und `renderOffset` hatte (die Offsets 4–15 waren in v4 Ausrichtungs-Spielraum; `renderOffset` bleibt bei 16, weil ein `vec3i` 16-Byte-Ausrichtung braucht), daher bleiben die Gesamtgröße der Struktur und die Offsets aller anderen Mitglieder unverändert. Die Engine schreibt es als ein einzelnes `setUint32(4, lit ? 1 : 0)` — es ist ein Flag, kein Lichtlevel: Die v4-JS-seitigen Namen `terrainLightLevels` / `terrainHeldLight` sind vollständig aus dem Bundle verschwunden.

Das Paket-Bind-Group-Layout ist sonst unverändert: Gruppe 3 ist weiterhin `0` Uniform · `1` Szenentiefe-Textur (Liquid-Varianten) · `2` der `bloxdSpTextureLayers`-Storage-Buffer. `minBindingSize` ist weiterhin 64.

## 71. Die Flags-Neuschreibung: `blockFlags` → `BloxdFlags` (das Highlight)

v4 identifizierte eine Fläche per `blockFlags: u32` und sechs `bloxdBlockFlag*`-Konstanten (opaque 1, emissive 2, vegetation 4, dirt 8, sand 16, rock 32). v5 ersetzt den ganzen Mechanismus durch eine Struktur benannter Booleans, wortlautgetreu aus dem Live-Header zitiert:

```wgsl
// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    // Drawn as block models, so never part of terrain or flagged as opaque.
    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    placed: bool,     // Blocks placed as part of chunks. Not items or vehicles.
    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}
```

Die sechs v4-Bit-Tests bilden eins-zu-eins auf Felder ab — die Migration ist eine Umbenennung, kein Umdenken:

| v4 | v5 |
|---|---|
| `(surface.blockFlags & bloxdBlockFlagOpaque) != 0u` | `surface.flags.opaque` |
| `(surface.blockFlags & bloxdBlockFlagEmissive) != 0u` | `surface.flags.emissive` |
| `(surface.blockFlags & bloxdBlockFlagVegetation) != 0u` | `surface.flags.vegetation` |
| `(surface.blockFlags & bloxdBlockFlagDirt) != 0u` | `surface.flags.dirt` |
| `(surface.blockFlags & bloxdBlockFlagSand) != 0u` | `surface.flags.sand` |
| `(surface.blockFlags & bloxdBlockFlagRock) != 0u` | `surface.flags.rock` |

Die acht **neuen** Felder sind die eigentliche Geschichte. v4 konnte eine Stufe nicht von einem vollen Block unterscheiden, ein gehaltenes Item nicht vom Terrain, einen Spieler nicht von einem Kürbis — jede Nicht-Terrain-Fläche war nur „nicht opak“ mit einer Textur-id. v5 beantwortet „was sehe ich gerade“ direkt:

- **`slab` / `stairs` / `flat`** — die drei Blockmodell-Formen. `flat` deckt die Kreuz-Ebenen-Pflanzen (hohes Gras, Blumen, Feldfrüchte, Spinnweben). Diese werden *als Blockmodelle gezeichnet*, daher hält der Header fest, dass sie nie Teil des Terrains und nie `opaque` sind.
- **`placed`** — Chunk-Geometrie, wie in der Welt platziert; ausdrücklich *keine* Items oder Fahrzeuge.
- **`held`** — Items in einer Hand, erste oder dritte Person. Das ist das Feld, das First-Person-Shader-Autoren seit v1 wollten: Du kannst das gehaltene Item endlich erkennen und anders behandeln als die Welt.
- **`dropped`** / **`thrown`** — Items am Boden / auf Bändern / in Röhren, gegen Items im Flug (Schneebälle, Pfeile, Raketen).
- **`lifeform`** — Spieler, Mobs und NPCs, *einschließlich Rüstung und Kosmetik*.

Zusammen mit `localPosition` (§72) und den Enchant-/Overlay-Eingaben kann die Modell-Pipeline jetzt mit vollem Wissen darüber schattiert werden, was sie rendert. Ein minimales „Glow für gehaltene Items“-Rezept, in v4 unmöglich:

```wgsl
fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    // Brighten whatever the local player is holding, nothing else.
    if (surface.flags.held) {
        out.colour *= 1.15;
    }
    return out;
}
```

Beachte, was sich *nicht* änderte: Die Felder liegen in allen drei Eingabestrukturen an derselben Stelle (`BloxdVertexIn`, `BloxdSurfaceIn`, `BloxdLightIn` — Feldname `flags`, Typ `BloxdFlags`), die Semantik der sechs überlebenden Booleans ist die v4-Semantik mit denselben Randfällen, die der Header jetzt ausspricht („Rocky Dirt is rock too“, „every sandstone is rock too“), und mehrere Flags kombinieren weiterhin frei („sandstone is sand and rock“, „possibly even none“).

## 72. Neue Eingaben: `localPosition`, das Enchant-Quartett und `overlayColour`

`BloxdVertexIn`, `BloxdSurfaceIn` und `BloxdLightIn` gewinnen alle dieselben neuen Mitglieder. Aus dem Header, wortgetreu:

```wgsl
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
```

- **`localPosition`** — die modellraumliche Position des Vertex/Fragments, bevor die Modellinstanz in der Welt platziert wird. `vec3f(0.0)` für Terrain- und Flüssigkeitsflächen (sie haben kein Modell). Für den Arm eines Spielers, ein gehaltenes Schwert, ein Windmühlenblatt ist das die Koordinate, die sich mit dem Modell mitdreht — eine pro-Modell-Animation oder ein Krümmungseffekt nach „wo am Schwert bin ich“ braucht jetzt ein Feld statt Weltraum-Ratelns. In der Light-Struktur hält der Header fest, dass sie „the same as in BloxdVertexIn, after the vertex hook“ ist — d. h. wenn dein Vertex-Hook den Vertex verschiebt, folgt das `localPosition` des Light-Hooks.

Und nur auf `BloxdSurfaceIn` / `BloxdLightIn` (die Vertex-Struktur braucht sie nicht):

```wgsl
     // Enchanted items and armour only, all 0 for anything else.
     enchantTier: u32,     // 1-5 for Tier 1-5.
     enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
     enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

     // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
     // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
     overlayColour: vec4f,
```

- **`enchantTier`** — der Verzauberungs-Tier des Items als Ganzzahl 1–5, für den klassischen „Glint-Intensität nach Tier“-Effekt ohne Parsen der Farbe.
- **`enchantColour`** — das live-Enchant-RGB plus sein *animiertes* Alpha in `.a`: Die Engine animiert den Glint-Sweep, daher gibt dir das Lesen von `.a` pro Fragment das wandernde Muster gratis. Auf unverzauberten Flächen alles Null.
- **`enchantSpeed`** — wie schnell das Enchant-Muster wandert; die eigene Anmerkung des Headers ist „faster at higher tiers“, daher sind `enchantTier` und `enchantSpeed` per Konstruktion konsistent.
- **`overlayColour`** — der Schadens-/Treffer-Blitz und ähnliche Entity-Overlays (RGB + Alpha), 0 für alles, was nicht Spieler oder Mob ist. Die Engine mischt dies *vor* dem Licht; siehe §73 für die Ausgabeseite.

Das alte Quartett (`textureId`, `textureRotation`, `uv`, `mipLevel`) wird unverändert übernommen, mit einer Umformulierung des Kommentars: v4 sagte, `uv` sei „texture coordinates in blocks“; v5 sagt „The texture spans 0-1. `fract(uv)` is drawn.“ — dasselbe Feld, aus Sicht der Textur beschrieben: Eine Texturkachel spannt `0.0–1.0` der uv, und ganzzahlige uv-Schritte kacheln sie an einer sich wiederholenden Wand entlang. Keine Port-Aktion nötig, außer du hast Annahmen über Mehrblock-Spannen handgestrickt.

## 73. Neue Ausgaben: `BloxdSurface` gewinnt `enchantColour` und `overlayColour`

Die Surface-**Ausgabe**struktur wächst um zwei Felder, wortgetreu:

```wgsl
struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}
```

Dein Surface-Hook besitzt jetzt den Verzauberungs-Glint und den Treffer-Blitz, so wie er bereits die Emission besaß:

- `bloxdDefaultSurface` reicht `surface.enchantColour` und `surface.overlayColour` unverändert durch, daher ist der Standard-Look identisch mit dem engine-seitigen Verhalten von v4.
- **`out.enchantColour` zu nullen** entfernt den Enchant-Glint aus deinem eigenen Licht — ein „Realismus ohne Glint“-Paket ist jetzt zwei Zeilen.
- **`out.overlayColour.a` zu verstärken** macht den Treffer-Blitz knackiger, ohne die Basisfarbe anzufassen; die Mischung passiert in `bloxdLitColour` (§74), nach dem Shading, exakt dort, wo die Engine sie hingelegt hat.
- Die Emissions-Reihenfolgen-Notiz trägt wortlautgetreu über: Emission wird *nach dem Licht, vor dem Fog addiert* — und die zwei neuen Felder werden *von `bloxdLitColour` eingemischt*, was *vor* Emission und Fog liegt. Die vollständige Ausgabekette, in Reihenfolge: `colour` → Overlay-Mix → Shading → Enchant-Mix → Weltlicht → `+ emission` → Fog.

## 74. Das Beleuchtungsrezept wird öffentlich: `bloxdLit()` und die drei Helfer

v4 gate-te Lichtcode zur Kompilierzeit: 8 Varianten (`strict|allow` × `lit|unlit` × `terrain|liquid`), wobei `#ifdef BLOXD_LIGHTING` entschied, ob Light-Hooks den lit- oder unlit-Pfad liefen. v5 streicht die ganze Beleuchtungs-Achse aus der Kompilierung:

- Die **Varianten-Matrix ist 6, nicht 8**: `strict|allow` × `terrain|liquid|model`, benannt `allow.terrain` … `strict.liquid` usw. (die Labels, die die Engine selbst für den Loader-Bildschirm baut).
- `BLOXD_STRICT` bleibt strict-exklusiv; `BLOXD_ALPHA` bleibt alles-Liquid plus jede Allow-Variante (aus für strict-Terrain und strict-Modell); `BLOXD_SCENE_DEPTH` bleibt Liquid-exklusiv. **`BLOXD_LIGHTING` existiert nicht mehr.**
- Der Beleuchtungszustand zog ins Uniform (`lit: u32`, §70) und wird im Code mit der neuen Header-Funktion abgefragt:

```wgsl
// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}
```

Hat dein v4-Paket seine Light-Hooks in `#ifdef BLOXD_LIGHTING ... #else ... #endif` eingeschlossen, ist der v5-Port ein früher Return: `if (!bloxdLit()) { return bloxdDefaultLight(surface, light); }`. Der Analyzer sagt dir das sogar — `BLOXD_LIGHTING` zu benutzen erzeugt jetzt die Validierungsmeldung *"BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead."* (wortlautgetreu vom Live-Validator gemessen).

Drei weitere Funktionen kommen in den Header, und es sind die, die v4-Autoren immer wieder von Hand neu herleiteten — das eigene Licht der Engine, dokumentiert als aufrufbares WGSL:

```wgsl
// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}
```

Und `bloxdDefaultLight` benutzt sie selbst — der Standard ist wörtlich „das Engine-Rezept anwenden und dann das emission-erweiterte Ergebnis foggens“:

```wgsl
fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
```

Um `bloxdShading` zu füttern, gewinnt `BloxdLightIn` außerdem zwei Eingaben (wortgetreue Kommentare):

```wgsl
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
```

`diffuse` und `emissive` sind neu in v5 (v4 hatte nur `directional` und `ambient`): Sie lassen dich `bloxdShading` mit Modifikationen neu bauen — z. B. das Weltlicht der Engine behalten, aber den Lambert-Term durch eigenes Wrap-around-Shading ersetzen —, ohne die Materialantwort zu verlieren, die die Engine bereits kennt. Auch die Doc-Kommentare der Lichtlevel wurden von „0 without BLOXD_LIGHTING“ auf „0 when !bloxdLit()“ umformuliert, dasselbe Faktum im v5-Vokabular.

Ein „eigenes Shading, Engine-Weltlicht“-Light-Hook — das Rezept, das v4-Autoren per Skalierung von `litColour` approximierten, jetzt exakt:

```wgsl
fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    // Half-Lambert wrap: soft, never fully dark on the back face.
    let nDotL = light.directional; // already the summed Lambert term
    let wrapped = nDotL * 0.5 + 0.5;
    let shaded = saturate(wrapped * light.diffuse + light.emissive + light.ambient);
    let colour = max(shaded * bloxdWorldLight(light), vec3f(0.0));
    return BloxdLight(bloxdApplyFog(colour + surface.emission, light));
}
```

## 75. Entfernungen: `bloxdFragmentBlockPosition()`, `bloxdBlockFlag*`, `bloxdSpLitColour`

Drei Dinge sind weg, und der Validator sagt sie mit Namen:

- **`bloxdFragmentBlockPosition(position, normal) -> vec3i`** — aus dem dokumentierten Header gestrichen, aber **nicht tatsächlich tot**: Die Signatur-Tabelle des Validators behielt ihren Eintrag (Aufrufe bestehen also in jedem Hook weiterhin die Validierung, Vertex-Hooks eingeschlossen), und der Code-Generator injiziert weiterhin eine Definition in das Terrain-/Liquid-Modul und beide Modell-Programme (`vec3i(floor(position - normal * 0.5)) + bloxdRenderOffset()` für Terrain/Liquid; eine 1/64-verschobene, zellenschnappende Variante für Modelle). v4-Pakete, die ihn aufrufen, laufen weiter. Behandle ihn als deprecated: Er ist jetzt undokumentiert, daher bevorzuge `bloxdWorldPosition()` für kontinuierliche Positionen und `flags` für „auf welchem Block bin ich“ — und rechne damit, dass er in einer künftigen Version verschwinden kann.
- **Die sechs `bloxdBlockFlag*`-Konstanten** — ersetzt durch `BloxdFlags` (§71). Jede überlebende Referenz scheitert mit der Reserved-Name-Diagnose des Analyzers.
- **`bloxdSpLitColour`** — das engine-interne Symbol, dessen Aufgabe die öffentliche `bloxdLitColour()` (§74) übernahm. Es verlässt den `bloxdSp*`-Namespace, der sonst nur wächst (§79).

Die v4-Ära-Funktionen, die unverändert überleben: `bloxdEyePosition()`, `bloxdRenderOffset()`, `bloxdSunDirection()`, `bloxdSeconds()`, `bloxdWorldPosition()`, `bloxdApplyFog()`, `bloxdDefaultVertex()`, `bloxdDefaultSurface()`, `bloxdDefaultLight()`, plus die gesamte Textur-API (`bloxdTexel`, `bloxdTextureSize`, `bloxdTextureId*` — §79 misst die Registry nach) und `BloxdOpaqueBehind` / `bloxdSceneDepth` mit ihrer Liquid-Varianten-Semantik.

## 76. Das Standardpaket liefert alle neun Hooks

Die Vorlage, mit der ein neues Paket startet, enthält jetzt die Light-Hooks — v4s Vorlage hatte sechs (Vertex+Surface pro Programm) und überließ Light-Hooks dem Kopieren aus der Doku. Die v5-Vorlage, wortgetreu und vollständig (1.683 Byte wie ausgeliefert):

```wgsl
// Every hook here returns its engine default. Modify the return values to start
// building a shader pack. If you delete a hook, the default is used instead.

// All blocks but water and block models use terrain hooks.
#ifndef BLOXD_STRICT
// Strict games keep terrain where it is. Without the #ifndef, this hook would
// turn the whole shader pack off there.
fn bloxdTerrainVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Water uses liquid hooks. To share code with another hook, define a function
// and call it from both places.
#ifndef BLOXD_STRICT
fn bloxdLiquidVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdLiquidSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdLiquidLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Models: block models such as slabs and plants, items, players and mobs.
#ifndef BLOXD_STRICT
fn bloxdModelVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdModelLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}
```

Die Kommentare sind neue Formulierungen und als Dokumentation des Lösch-Modells lesenswert: *"Modify the return values to start building a shader pack. If you delete a hook, the default is used instead."* Auch die Liquid-Notiz änderte sich — v4 sagte „If deleted, water uses your terrain hooks instead“, v5 sagt „To share code with another hook, define a function and call it from both places“ — und die Strict-Notiz erklärt das `#ifndef` jetzt in einem Satz: *"Strict games keep terrain where it is. Without the #ifndef, this hook would turn the whole shader pack off there."*

Der Strict-Spiele-Vertrag selbst (v4 §60) ist unverändert: Ein ungeschützter Vertex-Hook meldet `<hook> moves terrain, which strict games prevent.`, ein erreichbares `discard` meldet `discard makes terrain see-through, which strict games prevent.`, und jedes von beiden deaktiviert *alle* Hooks in Strict-Spielen. Die 12 Allow-Titel wurden am Live-Bundle nachgemessen — weiterhin 12, unverändert.

## 77. v4 → v5 Migrationscheckliste

1. **`pack.json`**: `"apiVersion": 5` — die Zahl, kein String.
2. **Flags portieren** (mechanisch, §71): jedes `blockFlags & bloxdBlockFlagX != 0u` → `flags.x`; die Konstanten löschen — der Validator lehnt sie dem Namen nach ab.
3. **Das Beleuchtungs-Gate portieren** (das eine mit Validator-Meldung): `#ifdef BLOXD_LIGHTING` → `if (bloxdLit()) { ... } else { return bloxdDefaultLight(surface, light); }`; `BLOXD_LIGHTING` löst jetzt *"BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead."* aus.
4. **Von `bloxdFragmentBlockPosition` wegwandern** (§75) — es kompiliert weiterhin, ist aber jetzt undokumentiert; `bloxdWorldPosition()` / `flags` verwenden.
5. **Über die neuen Ein-/Ausgaben entscheiden** *(optional)*: `flags.slab/stairs/flat/placed/held/dropped/thrown/lifeform` (§71), `localPosition` (§72), das Enchant-Quartett + `overlayColour` (§72–§73). Durchreichen per `bloxdDefaultSurface` hält den v4-Look exakt.
6. **Die Engine-Rezept-Helfer übernehmen** *(optional, aber empfohlen)*: handgestrickte Lichtfarbe durch `bloxdLitColour(surface, light)` ersetzen — oder mit `bloxdShading` / `bloxdWorldLight` mischen und kombinieren (§74) —, dann `surface.emission` und `bloxdApplyFog` dazugeben, wie es `bloxdDefaultLight` tut.
7. **Strict-Audit** (unverändert aus v4): `#ifndef BLOXD_STRICT` um Vertex-Hooks und jedes erreichbare `discard`.
8. **In-Game-Kompilierprüfung**: der Loader validiert alle **6** Varianten auf einmal (strict × terrain/liquid/model — die Beleuchtungs-Achse kompiliert nicht mehr separat, §74). Dann ein Allow-Spiel und ein Strict-Spiel beäugen.
9. **Eigene Versions-Metadaten bumpen und neu verteilen**: gespeicherte v4-Kopien auf Spielergeräten sind still inaktiv (§69), und nur der Einstellungs-Reiter sagt warum.

## 78. Weitere v5-Änderungen und Notizen

- **`bloxdChunkSize` kommt in den Header** — `const bloxdChunkSize: i32 = 32;` („Blocks along each side of a chunk“). Früher eine engine-seitige magische Zahl; jetzt eine benannte Konstante, auf die du verzweigen kannst. `bloxdPi`/`bloxdTau` unverändert.
- **Der Frame-Funktions-Abschnitt des Headers erhielt einen gemeinsamen Kommentar** — „These functions return the same value for the entire frame“ (v4: „return 1 value per frame, the same for every call site“) — reine Formulierung.
- **Y-Ableitungen werden in Paketcode automatisch negiert.** Der Analyzer schreibt jeden Aufruf von `dpdy`, `dpdyCoarse` oder `dpdyFine` in `(-dpdy(...))` um — die Screen-Space-y-Achse zeigt nach unten, die Negation bringt „Ableitung nach oben“ mit der Intuition zur Deckung. Du schreibst `dpdy(h)` und erwartest „wie ändert sich h nach oben“; der emittierte Code negiert es für dich. `dpdx` und die `fwidth`-Familie sind unangetastet. (Gemessen in der Token-Rewrite-Passage des Validators; die dpdy-Familie ist ausdrücklich als Negationsmenge gelistet.)
- **Die Texturnamen-Diagnosen bekamen eine Schreib-Engine.** Ein Name, der mit `bloxdTextureId` beginnt, sich aber nicht auflöst, bekommt jetzt einen Levenshtein-getriebenen Vorschlag: *"`X' isn't part of the shader pack API. Texture names start with exactly bloxdTextureId: did you mean bloxdTextureIdY?`"* — plus dedizierte Meldungen für Frame-Schreibweisen (*"names a frame of the animated texture Z: use bloxdTextureIdZ, which bloxdTexel animates."*) und gedrehte Schreibweisen (*"names a turned copy of Z: use bloxdTextureIdZ, which bloxdTexel turns as each face shows it."*). Die allgemeine Reservierungsregel wird in den Diagnosen erneut ausgesprochen: *"Packs can't declare names starting with bloxd, other than the hook functions bloxd<Terrain|Liquid|Model><Vertex|Surface|Light>"* sowie *"Packs can't use X: the engine binds every texture and sampler. Surface and light hooks can read atlas textures with bloxdTexel."*
- **Nur referenzierte Textur-Konstanten werden emittiert.** Der `bloxdTextureId*`-Block des Headers wird pro Paket aus den Namen generiert, die du tatsächlich referenzierst — ein Paket mit drei Konstanten bekommt drei `const`-Zeilen vorangestellt, nicht die vollen ~900.
- **`HEADER_VERSION` zog auf `9.<hash>.<hash>`** — dieselbe Zwei-Suffix-Struktur wie v4 (fnv1a32 des Header-Materials, fnv1a32 der sortierten Name-id-Registry), mit der führenden Ganzzahl von 8 auf 9 erhöht. Die Stored-Pack-Recheck-Logik (§55 des [v4-Migrationsleitfadens](v4.md)) ist unverändert: Eine Header-/Registry-Änderung kippt gespeicherte Pakete auf „muss erneut geprüft werden“.
- **i18n-Oberfläche**: die Shader-Pack-Key-Familie ist in der Form unverändert (die `load*`-, `status*`- und Varianten-Label-Keys aus §62 des v4-Leitfadens alle nachgemessen vorhanden; `loadNoWgsl`/`loadNotZip` weiterhin exakt).
- **Bundle-Layout für Nachuntersucher**: Header c55 (unverändert), Loader/Persistenz c51–c53, Validator + Registry-Builder c55, WebGPU-Codegen c56, Fog c9, **Standard-Pack-Vorlage c116** (aus c124 verschoben), die BLOXD_ALPHA-Stellen c51/c52/c53/c55/c9. Chunk-Format-Notiz: Jeder Chunk ist jetzt ein ES-Modul (`export const modules = {...}`) — c53 trägt sogar Module für c52 und c53 —, was zählt, wenn du das Bundle per Textsuche untersuchst (eine Modul-id wie `1371` lebt im Sparse-Module-Array von *main*, in keinem Chunk).

## 82. Der vollständige v5-Engine-Header, wortgetreu

Das Artefakt aus §67, für v5 nachgemessen: der exakte Text, den der Loader jedem Paket voranstellt, restauriert aus dem Live-Produktions-Bundle (`ab90qa`, Chunk c55, Vorlage gerendert mit ihren sechs Live-Interpolationen — `apiVersion` und die fünf Uniform-Lesungen durch `bloxdPackInputs`). 8.954 dekodierte Bytes, 208 Zeilen. Nichts ist paraphrasiert:

```wgsl

// The Bloxd shader pack API, apiVersion 5. Read-only, prepended to all packs.

const bloxdPi: f32 = 3.1415926535898;
const bloxdTau: f32 = 6.2831853071796;

// Blocks along each side of a chunk.
const bloxdChunkSize: i32 = 32;

// These functions return the same value for the entire frame.

// The camera's render position.
fn bloxdEyePosition() -> vec3f {
    return bloxdPackInputs.eyePosition;
}

// Integer distance, in blocks: render position + this offset = world position.
// Changes as the player travels, so render positions stay close to 0,0,0.
// See bloxdWorldPosition for one way to use it.
fn bloxdRenderOffset() -> vec3i {
    return bloxdPackInputs.renderOffset;
}

// The unit vector towards the sun, in world orientation; 0 when there's no sun.
fn bloxdSunDirection() -> vec3f {
    return bloxdPackInputs.sunDirection;
}

// Seconds since the page loaded. As an f32, it has sub-millisecond precision
// for the first 4.5 hours. Get a recurring timer using bloxdSeconds() % period.
fn bloxdSeconds() -> f32 {
    return bloxdPackInputs.seconds;
}

// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}

// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    // Drawn as block models, so never part of terrain or flagged as opaque.
    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    placed: bool,     // Blocks placed as part of chunks. Not items or vehicles.
    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}

// Convert a render position to a world position, with possible f32 inaccuracy.
fn bloxdWorldPosition(position: vec3f) -> vec3f {
    return position + vec3f(bloxdRenderOffset());
}

struct BloxdVertexIn {
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
}

struct BloxdVertex {
    position: vec3f,      // The render position output.
}

struct BloxdSurfaceIn {
    colour: vec3f,        // RGB colour = texture * tint * ambient occlusion.
    alpha: f32,           // Opacity.

    // Enchanted items and armour only, all 0 for anything else.
    enchantTier: u32,     // 1-5 for Tier 1-5.
    enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
    enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

    // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
    // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
    overlayColour: vec4f,

    // These mean the same as in BloxdVertexIn, after the vertex hook.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.

    // These are all 0 if the face has no texture. Most models use textureId 0.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}

// blockLight, skyLight and heldLight are 0-1, from the 0-15 light levels on an
// ease-out curve, e.g. 6->0.45, 12->0.92. They all exclude ambientLightColour.
// bloxdLitColour lights a surface from these as the engine does.
struct BloxdLightIn {
    litColour: vec3f,  // Lit and enchanted RGB colour, before emission and fog.
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
    ambient: vec3f,    // RGB ambient colour, added to directional light.
    blockLight: vec3f, // RGB block light; 0 when !bloxdLit().
    skyLight: f32,     // Sky light; 1 when !bloxdLit().
    ambientLightColour: vec3f, // Minimum RGB light; 1 when !bloxdLit().
    skyLightColour: vec3f, // RGB colour of skyLight; 1 when !bloxdLit().
    heldLight: vec3f,  // RGB held light; 0 when !bloxdLit() or no light held.
    fogColour: vec3f,  // The game's RGB fog colour; 0 when the game has no fog.
    fogAlpha: f32,     // 0 = no fog, 1 = only fogColour.

    // These are the same as in BloxdSurfaceIn.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdLight {
    colour: vec3f, // RGB colour output.
}

struct BloxdOpaqueBehind {
    hit: bool,       // False where nothing opaque is behind (sky).
    position: vec3f, // The render position; 0 when !hit.
    distance: f32,   // From the camera; 0 when !hit.
}

fn bloxdDefaultVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return BloxdVertex(vertex.position);
}

fn bloxdDefaultSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return BloxdSurface(
        surface.colour,
#ifdef BLOXD_ALPHA
        surface.alpha,
#endif
        vec3f(0.0),
        surface.enchantColour,
        surface.overlayColour,
    );
}

// Apply this fragment's fog to colour, as the engine does.
fn bloxdApplyFog(colour: vec3f, light: BloxdLightIn) -> vec3f {
    return mix(colour, light.fogColour, light.fogAlpha);
}

// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}

fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
```
