# Guide de migration vers l'API v5

> Version : 5 · État : Historical (guide de migration de l'époque ; le build cible est indiqué dans le texte)
Build cible : `ab90qa.main.6188124c.js` — **en production et en preprod simultanément (mesuré le 2026-11-03)**, et les deux bundles sont de nouveau identiques octet par octet (md5 `fc3322212d15be2445c0e8dfc9733fcc` sur le bundle principal, récupéré en direct depuis les deux hôtes), donc tout ce qui suit s'applique tel quel à la production. C'est la plus grosse révision de l'API depuis v3 : le bundle principal est passé à 3,39 Mo (+115 Ko par rapport au dernier build v4), la carte des chunks compte désormais 195 ids (c0–c195, 188 émis après les 7 trous connus), le pipeline de shaders reste dans le cluster c51–c56 (chargeur c53, validateur/en-tête/constructeur du registre c55, WebGPU/codegen c56, brouillard c9) — mais le gabarit du pack par défaut a déménagé en c116 (il était en c124 dans `tcwczu`). Aucun de ces détails de disposition n'est visible pour un pack. Reverifié sur le build de production actuel `xkg8x.main.641a7732.js` (2026-11-04, md5 `f11cc032efd474aca567d3793b792057`) : l'en-tête du moteur est identique octet par octet et toutes les mesures de chargeur / variantes / hooks / noms réservés ci-dessous ont été revérifiées inchangées — le registre de textures est la seule surface qui a bougé (896 → 906 noms utilisables ; addenda §80). Preprod (`2lcqcl`) sert un bundle principal différent mais mesuré identique sur chaque surface de shader pack.

Ce qui *est* visible : l'en-tête du moteur est passé de 6 021 à **8 954 octets décodés** (151 → 208 lignes) — presque chaque structure a gagné des champs, quatre nouvelles fonctions documentent la recette d'éclairage propre au moteur, et le masque de bits `blockFlags` a disparu, remplacé par une véritable structure `BloxdFlags` de booléens. L'aiguillage à la compilation `#ifdef BLOXD_LIGHTING` a disparu lui aussi : l'état d'éclairage a déménagé dans l'uniform par frame comme membre `lit: u32` et s'interroge à l'exécution avec `bloxdLit()`. Le gabarit du pack par défaut embarque désormais **les neuf hooks** au lieu de six. Et l'espace de noms interne au moteur `bloxdSp*` est passé de 27 à 46 symboles.

L'ensemble des changements de v5 en un écran :

| Zone | v4 | v5 |
|---|---|---|
| `apiVersion` de `pack.json` | `4` (strict) | **`5` (strict)** — les packs v4 sont rejetés au chargement |
| Identité de bloc | `blockFlags: u32` + 6 constantes de bits `bloxdBlockFlag*` | **`flags: BloxdFlags`** — 14 champs bool nommés (§71) |
| Nouvelles sortes de flags | — | **`slab` `stairs` `flat` `placed` `held` `dropped` `thrown` `lifeform`** — modèles et entités désormais distinguables du terrain (§71) |
| Position de modèle | — | **`localPosition: vec3f`** sur chaque structure d'entrée (§72) |
| Enchantement et superposition | moteur uniquement | **entrées + sorties `enchantTier` / `enchantColour` / `enchantSpeed` / `overlayColour`** (§72–§73) |
| Aiguillage d'éclairage | `#ifdef BLOXD_LIGHTING` (à la compilation, 8 variantes) | **supprimé** — l'uniform gagne `lit: u32` @ offset 4 ; testez **`bloxdLit()`** à l'exécution ; 6 variantes (§74) |
| Auxiliaires d'éclairage | `litColour` privé au moteur | **public** : `bloxdShading()`, `bloxdWorldLight()`, `bloxdLitColour()` (§74) |
| `bloxdFragmentBlockPosition()` | documenté dans l'en-tête | **hors de l'en-tête documenté** — mais toujours injecté et toujours accepté par le validateur (§75) |
| Pack par défaut | 6 hooks (sommet+surface) | **9 hooks** — hooks de lumière inclus (§76) |
| `bloxdChunkSize` | absent de l'en-tête | **nouvelle const `bloxdChunkSize: i32 = 32`** (§78) |
| Espace de noms `bloxdSp*` | 27 symboles | **46 symboles** (+20, −1) (§79) |
| Registre de textures | 905 noms utilisables | **896 noms utilisables** — +1, −10 (§80) |
| Limites du chargeur, règles de zip, forme de `pack.json`, noms des hooks, contrat strict | — | **figé, limites identiques octet par octet** (§70) |

La conversion depuis v4 est pour l'essentiel mécanique (§77) : le piège silencieux est différent cette fois — un pack qui lit encore `blockFlags` ou protège ses hooks de lumière par `#ifdef BLOXD_LIGHTING` **échoue à la validation avec un message spécifique** (l'analyseur explique désormais les deux cas), donc rien ne se comporte silencieusement de travers ; mais un pack qui se contente de *lire les anciennes constantes de bits* par nom refusera de charger tant qu'il n'aura pas été porté. Comme toujours, vérifiez par une compilation en jeu avant de distribuer.

## 69. Le sort des packs v4 (d'abord la conclusion)

**Tout pack v4 — y compris tout pack distribué comme v4 — échoue désormais en production, exactement au chargement.** Le chargeur compare `manifest.apiVersion !== 5` avec le `!==` strict de JavaScript — la constante de version `5` et le gabarit de l'en-tête vivent dans le même module de ce build (module 29836), donc la vérification et le texte d'en-tête auquel elle se rapporte évoluent ensemble. Le JSON doit porter le *nombre* `5` ; une chaîne `"5"` échoue et est signalée avec son orthographe JSON, exactement comme en v4.

Les deux messages au moment du chargement sont inchangés par rapport à v4, verbatim du dictionnaire i18n en production :


> `This pack is for shader pack API version {{packVersion}}. Bloxd supports version {{version}}.` — la clé est présente mais ne vaut pas 5.

Un pack v4 sauvegardé (qui fonctionnait auparavant) ne lève rien au joueur : le résultat du pack sauvegardé se résout en `{kind: "none", reason: "otherApiVersion"}`, le pack est silencieusement inactif, et l'onglet des réglages de shader packs s'explique de lui-même avec la ligne d'état :

> `This shader pack is for API version {{packVersion}}, so it won't run. Load a version {{version}} pack to replace it.`

Les règles du manifeste sont par ailleurs remesurées et inchangées : `pack.json` doit être un objet JSON à la racine du zip ; `apiVersion` doit être présent et `=== 5` ; `name` est requis, une chaîne, non vide après trim ; `author` est optionnel mais doit être une chaîne s'il est présent ; tout le reste du manifeste est ignoré.

## 70. pack.json, le chargeur et l'uniform (ce qui ne change pas)

Tout le modèle de pack passe de v4 octet par octet. Les limites du chargeur, remesurées sur le chunk du chargeur en production (c53) :

| Limite | Valeur | Message en cas de dépassement |
|---|---|---|
| fichiers `.wgsl` par pack | 256 | `The pack has more than 256 .wgsl files.` |
| source `.wgsl` totale | 256 Ko | `The pack's .wgsl files are over 256 KB in total.` |
| taille de `pack.json` | 64 Ko | `pack.json is over 64 KB.` |
| taille du zip | 32 Mo | `The zip is over 32 MB.` |
| entrées du zip | 1 024 | `The zip has more than 1024 entries.` |
| forme du zip | — | les zips découpés, le Zip64, les entrées chiffrées et les méthodes de compression non prises en charge sont chacun rejetés avec un message dédié ; chaque fichier doit être de l'UTF-8 valide ; exactement un `pack.json` ; aucun chemin en double |

L'uniform par frame reste `@group(3) @binding(0) var<uniform> bloxdPackInputs: BloxdPackInputs`, toujours 64 octets — mais il a gagné un membre. La table de disposition, tirée du module de disposition de l'uniform en production :

| Offset | Champ | Type | Remarque |
|---|---|---|---|
| 0 | `seconds` | `f32` | alimente `bloxdSeconds()` |
| 4 | `lit` | `u32` | **nouveau en v5** — 1 quand l'éclairage bloc/ciel est actif ; alimente `bloxdLit()` |
| 16 | `renderOffset` | `vec3i` | alimente `bloxdRenderOffset()` |
| 32 | `sunDirection` | `vec3f` | alimente `bloxdSunDirection()` |
| 48 | `eyePosition` | `vec3f` | alimente `bloxdEyePosition()` |

`lit` s'insère dans le padding que v4 avait déjà entre `seconds` et `renderOffset` (les offsets 4–15 étaient des trous d'alignement en v4 ; `renderOffset` reste à 16 parce qu'un `vec3i` exige un alignement de 16 octets), donc la taille totale de la structure et l'offset de tous les autres membres sont inchangés. Le moteur l'écrit avec un unique `setUint32(4, lit ? 1 : 0)` — c'est un flag, pas un niveau de lumière : les noms côté JS de v4 `terrainLightLevels` / `terrainHeldLight` ont entièrement disparu du bundle.

La disposition du groupe de bindings du pack est par ailleurs inchangée : le groupe 3 reste `0` uniform · `1` texture de profondeur de scène (variantes liquid) · `2` le buffer de stockage `bloxdSpTextureLayers`. `minBindingSize` reste 64.

## 71. La réécriture des flags : `blockFlags` → `BloxdFlags` (le grand chantier)

v4 identifiait une face à l'aide d'un `blockFlags: u32` et de six constantes `bloxdBlockFlag*` (opaque 1, emissive 2, vegetation 4, dirt 8, sand 16, rock 32). v5 remplace tout le mécanisme par une structure de booléens nommés, citée verbatim de l'en-tête en production :

```wgsl
// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    // Drawn as block models, so never part of terrain or flagged as opaque.
    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    placed: bool,     // Blocks placed as part of chunks. Not items or vehicles.
    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}
```

Les six tests de bits de v4 se reportent un à un sur des champs — la migration est un renommage, pas une refonte :

| v4 | v5 |
|---|---|
| `(surface.blockFlags & bloxdBlockFlagOpaque) != 0u` | `surface.flags.opaque` |
| `(surface.blockFlags & bloxdBlockFlagEmissive) != 0u` | `surface.flags.emissive` |
| `(surface.blockFlags & bloxdBlockFlagVegetation) != 0u` | `surface.flags.vegetation` |
| `(surface.blockFlags & bloxdBlockFlagDirt) != 0u` | `surface.flags.dirt` |
| `(surface.blockFlags & bloxdBlockFlagSand) != 0u` | `surface.flags.sand` |
| `(surface.blockFlags & bloxdBlockFlagRock) != 0u` | `surface.flags.rock` |

Les huit champs **nouveaux** sont la vraie histoire. v4 n'avait aucun moyen de distinguer une dalle d'un bloc plein, un objet tenu du terrain, ou un joueur d'une citrouille — toute face hors terrain n'était qu'un « non opaque » avec un id de texture. v5 répond directement à « que suis-je en train de regarder » :

- **`slab` / `stairs` / `flat`** — les trois formes de modèle de bloc. `flat` couvre les plantes en plans croisés (hautes herbes, fleurs, cultures, toiles d'araignée). Elles sont *dessinées comme des modèles de blocs*, donc l'en-tête note qu'elles ne font jamais partie du terrain et ne sont jamais `opaque`.
- **`placed`** — la géométrie des chunks telle que posée dans le monde ; explicitement *ni* les objets *ni* les véhicules.
- **`held`** — les objets en main, à la première comme à la troisième personne. C'est le champ que les auteurs de shaders première personne réclamaient depuis v1 : vous pouvez enfin détecter l'objet tenu et le traiter différemment du monde.
- **`dropped`** / **`thrown`** — les objets au sol / sur tapis roulant / dans un tuyau, face aux objets en vol (boules de neige, flèches, fusées).
- **`lifeform`** — joueurs, mobs et PNJ, *armures et cosmétiques inclus*.

Combinés avec `localPosition` (§72) et les entrées enchantement/superposition, le pipeline des modèles peut désormais être ombré en connaissance complète de ce qu'il est en train de rendre. Une recette minimale de « halo de l'objet tenu », impossible en v4 :

```wgsl
fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    // Éclaircit ce que le joueur local tient en main, rien d'autre.
    if (surface.flags.held) {
        out.colour *= 1.15;
    }
    return out;
}
```

Notez ce qui *n'a pas* changé : les champs vivent au même endroit dans les trois structures d'entrée (`BloxdVertexIn`, `BloxdSurfaceIn`, `BloxdLightIn` — nom de champ `flags`, type `BloxdFlags`), la sémantique des six booléens survivants est la sémantique v4 avec les mêmes cas limites que l'en-tête épelle désormais (« Rocky Dirt is rock too », « every sandstone is rock too »), et plusieurs flags se combinent toujours aussi librement (« sandstone is sand and rock », « possibly even none »).

## 72. Nouvelles entrées : `localPosition`, le quatuor d'enchantement et `overlayColour`

`BloxdVertexIn`, `BloxdSurfaceIn` et `BloxdLightIn` gagnent tous les mêmes nouveaux membres. De l'en-tête, verbatim :

```wgsl
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
```

- **`localPosition`** — la position en espace modèle du sommet/fragment, avant que l'instance du modèle ne soit placée dans le monde. `vec3f(0.0)` pour les faces de terrain et de liquide (elles n'ont pas de modèle). Pour le bras d'un joueur, une épée tenue, la pale d'un moulin, c'est la coordonnée qui tourne avec le modèle — une animation par modèle ou un effet de courbure indexé sur « où en suis-je sur l'épée » tient désormais en un champ au lieu de suppositions en espace monde. Dans la structure light, l'en-tête note qu'il est « the same as in BloxdVertexIn, after the vertex hook » — c.-à-d. que si votre hook de sommet déplace le sommet, le `localPosition` du hook de lumière suit.

Et sur `BloxdSurfaceIn` / `BloxdLightIn` uniquement (la structure de sommet n'en a pas besoin) :

```wgsl
     // Enchanted items and armour only, all 0 for anything else.
     enchantTier: u32,     // 1-5 for Tier 1-5.
     enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
     enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

     // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
     // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
     overlayColour: vec4f,
```

- **`enchantTier`** — le palier d'enchantement de l'objet sous forme d'entier 1–5, pour l'effet classique « intensité de reflet par palier » sans avoir à analyser la couleur.
- **`enchantColour`** — le RVB d'enchantement en direct plus son alpha *animé* dans `.a` : le moteur anime le balayage du reflet, donc lire `.a` par fragment donne gratuitement le motif en mouvement. Des zéros partout sur les faces non enchantées.
- **`enchantSpeed`** — la vitesse à laquelle le motif d'enchantement se déplace ; la note de l'en-tête lui-même est « faster at higher tiers », donc `enchantTier` et `enchantSpeed` sont cohérents par construction.
- **`overlayColour`** — le flash de dégâts/blessure et les superpositions d'entités similaires (RVB + alpha), 0 pour tout ce qui n'est ni joueur ni mob. Le moteur le mélange *avant* l'éclairage ; voir §73 pour le côté sortie.

L'ancien quatuor (`textureId`, `textureRotation`, `uv`, `mipLevel`) passe tel quel, avec un commentaire reformulé : v4 disait que `uv` était « texture coordinates in blocks » ; v5 dit « The texture spans 0-1. `fract(uv)` is drawn. » — le même champ, décrit du point de vue de la texture : une tuile de texture couvre `0.0–1.0` de uv, et les pas entiers de uv la pavent le long d'un mur répété. Aucune action de portage nécessaire, sauf si vous aviez fabriqué à la main des hypothèses sur des portées multi-blocs.

## 73. Nouvelles sorties : `BloxdSurface` gagne `enchantColour` et `overlayColour`

La structure de **sortie** de surface gagne deux champs, verbatim :

```wgsl
struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}
```

Votre hook de surface possède désormais le reflet d'enchantement et le flash de dégâts, au même titre que l'émission qu'il possédait déjà :

- `bloxdDefaultSurface` transmet `surface.enchantColour` et `surface.overlayColour` sans modification, donc le rendu par défaut est identique au comportement côté moteur de v4.
- **Mettre `out.enchantColour` à zéro** dans votre hook retire le reflet d'enchantement de votre éclairage personnalisé — un pack « réalisme sans reflet » tient désormais en deux lignes.
- **Amplifier `out.overlayColour.a`** rend le flash de dégâts plus percutant sans toucher à la couleur de base ; le mélange a lieu dans `bloxdLitColour` (§74), après l'ombrage, exactement là où le moteur le plaçait.
- La note sur l'ordre de l'émission passe telle quelle : l'émission est *ajoutée après l'éclairage, avant le brouillard* — et les deux nouveaux champs sont *mélangés par `bloxdLitColour`*, qui vient *avant* l'émission et le brouillard. La chaîne de sortie complète, dans l'ordre : `colour` → mélange overlay → ombrage → mélange enchantement → lumière du monde → `+ emission` → brouillard.

## 74. La recette d'éclairage devient publique : `bloxdLit()` et les trois auxiliaires

v4 verrouillait le code d'éclairage à la compilation : 8 variantes (`strict|allow` × `lit|unlit` × `terrain|liquid`), avec `#ifdef BLOXD_LIGHTING` qui décidait si les hooks de lumière empruntaient le chemin lit ou unlit. v5 retire tout l'axe d'éclairage de la compilation :

- La **matrice de variantes est de 6, pas 8** : `strict|allow` × `terrain|liquid|model`, nommées `allow.terrain` … `strict.liquid` etc. (les étiquettes que le moteur construit lui-même pour l'écran du chargeur).
- `BLOXD_STRICT` reste strict uniquement ; `BLOXD_ALPHA` reste tout liquid plus toutes les variantes allow (désactivé pour terrain strict et modèle strict) ; `BLOXD_SCENE_DEPTH` reste liquid uniquement. **`BLOXD_LIGHTING` n'existe plus.**
- L'état d'éclairage a déménagé vers l'uniform (`lit: u32`, §70) et s'interroge dans le code avec la nouvelle fonction d'en-tête :

```wgsl
// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}
```

Si votre pack v4 enveloppait ses hooks de lumière dans `#ifdef BLOXD_LIGHTING ... #else ... #endif`, le portage v5 est un retour anticipé : `if (!bloxdLit()) { return bloxdDefaultLight(surface, light); }`. L'analyseur vous le dit même — utiliser `BLOXD_LIGHTING` produit désormais le message de validation *« BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead. »* (mesuré verbatim sur le validateur en production).

Trois fonctions de plus rejoignent l'en-tête, et ce sont celles que les auteurs v4 continuaient de redériver à la main — l'éclairage propre au moteur, documenté comme du WGSL appelable :

```wgsl
// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}
```

Et `bloxdDefaultLight` lui-même les utilise désormais — la valeur par défaut est littéralement « appliquer la recette du moteur puis embrumer le résultat étendu de l'émission » :

```wgsl
fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
```

Pour alimenter `bloxdShading`, `BloxdLightIn` gagne aussi deux entrées (commentaires verbatim) :

```wgsl
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
```

`diffuse` et `emissive` sont nouveaux en v5 (v4 n'avait que `directional` et `ambient`) : ils permettent de reconstruire `bloxdShading` avec des modifications — p. ex. garder la lumière du monde du moteur mais remplacer le terme de Lambert par votre propre ombrage enveloppant — sans perdre la réponse matériau que le moteur connaît déjà. Les commentaires de documentation sur les niveaux de lumière ont aussi été reformulés, de « 0 without BLOXD_LIGHTING » en « 0 when !bloxdLit() », ce qui est le même fait dans le vocabulaire v5.

Un hook de lumière « ombrage personnalisé, lumière du monde du moteur » — la recette que les auteurs v4 approximaient en mettant `litColour` à l'échelle, désormais exacte :

```wgsl
fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    // Half-Lambert enveloppant : doux, jamais complètement sombre sur la face arrière.
    let nDotL = light.directional; // déjà le terme de Lambert sommé
    let wrapped = nDotL * 0.5 + 0.5;
    let shaded = saturate(wrapped * light.diffuse + light.emissive + light.ambient);
    let colour = max(shaded * bloxdWorldLight(light), vec3f(0.0));
    return BloxdLight(bloxdApplyFog(colour + surface.emission, light));
}
```

## 75. Suppressions : `bloxdFragmentBlockPosition()`, `bloxdBlockFlag*`, `bloxdSpLitColour`

Trois choses ont disparu, et le validateur les nomme :

- **`bloxdFragmentBlockPosition(position, normal) -> vec3i`** — retiré de l'en-tête documenté, mais **pas réellement mort** : la table des signatures du validateur a gardé son entrée (donc les appels passent toujours la validation dans tous les hooks, sommet compris), et le générateur de code injecte toujours une définition dans le module terrain/liquid et dans les deux programmes modèle (`vec3i(floor(position - normal * 0.5)) + bloxdRenderOffset()` pour terrain/liquid ; une variante à offset de 1/64 avec alignement sur la cellule pour les modèles). Les packs v4 qui l'appellent continuent de fonctionner. Considérez-la comme dépréciée : elle est désormais non documentée, donc préférez `bloxdWorldPosition()` pour les positions continues et `flags` pour « sur quel bloc suis-je », et attendez-vous à ce qu'elle puisse disparaître dans une version future.
- **Les six constantes `bloxdBlockFlag*`** — remplacées par `BloxdFlags` (§71). Toute référence survivante échoue à la validation avec le diagnostic de nom réservé de l'analyseur.
- **`bloxdSpLitColour`** — le symbole interne au moteur dont le rôle est devenu le `bloxdLitColour()` public (§74). Il quitte l'espace de noms `bloxdSp*`, qui par ailleurs ne fait que croître (§79).

Les fonctions de l'époque v4 qui survivent inchangées : `bloxdEyePosition()`, `bloxdRenderOffset()`, `bloxdSunDirection()`, `bloxdSeconds()`, `bloxdWorldPosition()`, `bloxdApplyFog()`, `bloxdDefaultVertex()`, `bloxdDefaultSurface()`, `bloxdDefaultLight()`, plus toute l'API de textures (`bloxdTexel`, `bloxdTextureSize`, `bloxdTextureId*` — le §79 remesure le registre) et `BloxdOpaqueBehind` / `bloxdSceneDepth` avec leur sémantique des variantes liquid.

## 76. Le pack par défaut embarque les neuf hooks

Le gabarit dont un nouveau pack part désormais inclut les hooks de lumière — celui de v4 en comptait six (sommet+surface par programme) et laissait les hooks de lumière à copier depuis la documentation. Celui de v5, verbatim et complet (1 683 octets tels que livrés) :

```wgsl
// Every hook here returns its engine default. Modify the return values to start
// building a shader pack. If you delete a hook, the default is used instead.

// All blocks but water and block models use terrain hooks.
#ifndef BLOXD_STRICT
// Strict games keep terrain where it is. Without the #ifndef, this hook would
// turn the whole shader pack off there.
fn bloxdTerrainVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Water uses liquid hooks. To share code with another hook, define a function
// and call it from both places.
#ifndef BLOXD_STRICT
fn bloxdLiquidVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdLiquidSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdLiquidLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Models: block models such as slabs and plants, items, players and mobs.
#ifndef BLOXD_STRICT
fn bloxdModelVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdModelLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}
```

Les commentaires sont une nouvelle rédaction et valent d'être lus comme documentation du modèle de suppression : *« Modify the return values to start building a shader pack. If you delete a hook, the default is used instead. »* La note liquid a changé aussi — v4 disait « If deleted, water uses your terrain hooks instead », v5 dit « To share code with another hook, define a function and call it from both places » — et la note strict explique désormais le `#ifndef` en une phrase : *« Strict games keep terrain where it is. Without the #ifndef, this hook would turn the whole shader pack off there. »*

Le contrat des jeux stricts lui-même (v4 §60) est inchangé : un hook de sommet non protégé produit `<hook> moves terrain, which strict games prevent.`, un `discard` atteignable produit `discard makes terrain see-through, which strict games prevent.`, et chacun des deux désactive *tous* les hooks dans les jeux stricts. Les 12 titres allow ont été remesurés sur le bundle en production — toujours 12, inchangés.

## 77. Checklist de migration de v4 à v5

1. **`pack.json`** : `"apiVersion": 5` — le nombre, pas une chaîne.
2. **Portez les flags** (mécanique, §71) : chaque `blockFlags & bloxdBlockFlagX != 0u` → `flags.x` ; supprimez les constantes — le validateur les rejette par nom.
3. **Portez l'aiguillage d'éclairage** (celui qui a un message du validateur) : `#ifdef BLOXD_LIGHTING` → `if (bloxdLit()) { ... } else { return bloxdDefaultLight(surface, light); }` ; `BLOXD_LIGHTING` déclenche désormais *« BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead. »*
4. **Migrez hors de `bloxdFragmentBlockPosition`** (§75) — il compile toujours, mais il est désormais non documenté ; utilisez `bloxdWorldPosition()` / `flags`.
5. **Décidez des nouvelles entrées/sorties** *(facultatif)* : `flags.slab/stairs/flat/placed/held/dropped/thrown/lifeform` (§71), `localPosition` (§72), le quatuor d'enchantement + `overlayColour` (§72–§73). Le passage direct via `bloxdDefaultSurface` conserve exactement le rendu v4.
6. **Adoptez les auxiliaires de la recette du moteur** *(facultatif mais recommandé)* : remplacez la couleur de lumière faite main par `bloxdLitColour(surface, light)` — ou composez avec `bloxdShading` / `bloxdWorldLight` (§74) — puis ajoutez `surface.emission` et `bloxdApplyFog` comme le fait `bloxdDefaultLight`.
7. **Audit strict** (inchangé depuis v4) : `#ifndef BLOXD_STRICT` autour des hooks de sommet et de tout `discard` atteignable.
8. **Vérification de compilation en jeu** : le chargeur valide les **6** variantes d'un coup (strict × terrain/liquid/model — l'axe d'éclairage ne compile plus séparément, §74). Puis inspectez à l'œil un jeu allow et un jeu strict.
9. **Incrémentez les métadonnées de votre propre version et redistribuez** : les copies v4 sauvegardées sur les machines des joueurs sont silencieusement inactives (§69) et seul l'onglet des réglages dit pourquoi.

## 78. Autres changements et notes de v5

- **`bloxdChunkSize` rejoint l'en-tête** — `const bloxdChunkSize: i32 = 32;` (« Blocks along each side of a chunk »). Auparavant un nombre magique côté moteur ; désormais une constante nommée sur laquelle vous pouvez brancher. `bloxdPi`/`bloxdTau` inchangés.
- **La section des fonctions par frame de l'en-tête a reçu un commentaire partagé** — « These functions return the same value for the entire frame » (v4 : « return 1 value per frame, the same for every call site ») — purement rédactionnel.
- **Les dérivées en Y sont automatiquement niées dans le code des packs.** L'analyseur réécrit chaque appel à `dpdy`, `dpdyCoarse` ou `dpdyFine` en `(-dpdy(...))` — l'axe y de l'espace écran pointe vers le bas, donc la négation aligne « dérivée par rapport à la direction vers le haut » sur l'intuition. Vous écrivez `dpdy(h)` en vous attendant à « comment h varie-t-il quand on monte » ; le code émis le nie pour vous. `dpdx` et la famille `fwidth` restent intacts. (Mesuré dans la passe de réécriture de tokens du validateur ; la famille dpdy est précisément listée comme étant l'ensemble à nier.)
- **Les diagnostics de noms de textures ont gagné un moteur orthographique.** Un nom qui commence par `bloxdTextureId` mais ne résout pas reçoit désormais une suggestion fondée sur Levenshtein : *« `X' isn't part of the shader pack API. Texture names start with exactly bloxdTextureId: did you mean bloxdTextureIdY?` »* — plus des messages dédiés pour les orthographes d'image (*« names a frame of the animated texture Z: use bloxdTextureIdZ, which bloxdTexel animates. »*) et les orthographes tournées (*« names a turned copy of Z: use bloxdTextureIdZ, which bloxdTexel turns as each face shows it. »*). La règle générale de réservation est réénoncée dans les diagnostics : *« Packs can't declare names starting with bloxd, other than the hook functions bloxd<Terrain|Liquid|Model><Vertex|Surface|Light> »*, et *« Packs can't use X: the engine binds every texture and sampler. Surface and light hooks can read atlas textures with bloxdTexel. »*
- **Seules les constantes de textures référencées sont émises.** Le bloc `bloxdTextureId*` de l'en-tête est généré par pack à partir des noms que vous référencez réellement — un pack qui utilise trois constantes reçoit trois lignes `const` en préfixe, pas les ~900 complètes.
- **`HEADER_VERSION` est passé à `9.<hash>.<hash>`** — même structure à deux suffixes qu'en v4 (fnv1a32 du matériau d'en-tête, fnv1a32 du registre trié nom-id), avec l'entier de tête incrémenté de 8 à 9. La logique de revérification des packs sauvegardés (§55 du [guide de migration v4](v4.md)) est inchangée : un changement d'en-tête ou de registre bascule les packs sauvegardés en « à revérifier ».
- **Surface i18n** : la famille de clés des shader packs est inchangée en forme (les clés `load*`, `status*` et d'étiquettes de variante du guide v4 §62 toutes remesurées présentes ; `loadNoWgsl`/`loadNotZip` toujours exactes).
- **Disposition du bundle pour les re-chercheurs** : en-tête c55 (inchangé), chargeur/persistance c51–c53, validateur + constructeur du registre c55, codegen WebGPU c56, brouillard c9, **gabarit du pack par défaut c116** (déplacé depuis c124), les sites BLOXD_ALPHA c51/c52/c53/c55/c9. Note sur le format des chunks : chaque chunk est désormais un module ES (`export const modules = {...}`) — c53 porte même les modules de c52 comme de c53 — ce qui compte si vous faites une recherche textuelle dans le bundle (un id de module comme `1371` vit dans le tableau épars de modules de *main*, dans aucun chunk).

## 79. Intérieurs du moteur v5 : le pipeline de textures et l'espace `bloxdSp*` à 46 symboles

Le codegen de textures à trois variantes du v4 §63 est reconduit avec la même forme. Restauré depuis le générateur en production (c56) :

**Variante 1 — aucun texture pack actif** (le bloc généré en entier ; `bloxdTextureSize` et `bloxdTexel` sont des stubs) :

```wgsl
fn bloxdTextureSize(bloxdSpMipLevel: f32) -> vec2u {
        return vec2u(1u);
}
fn bloxdTexel(bloxdSpTextureId: u32, bloxdSpUv: vec2f, bloxdSpMipLevel: f32) -> vec4f {
        return vec4f(1.0);
}
```

**Variante 2 — le chemin atlas** (par défaut dans les jeux) : `bloxdTextureSize` renvoie `textureDimensions(textureAtlas0, u32(clamp(round(bloxdSpMipLevel), 0.0, f32(textureNumLevels(textureAtlas0) - 1u))))`, et `bloxdTexel` applique le quart de tour de la face avant le chargement — la subtilité de rotation de v4 (guide de migration v4 §57.4), désormais explicitée en une chaîne if sur le `bloxdSpTurned` généré :

```wgsl
        // Each quarter turn clockwise the face shows its texture at reads the unturned texture at (v, 1 - u)
        var bloxdSpTurned = bloxdSpUv;
        if (bloxdSpTextureRotation == 1u) {
                bloxdSpTurned = vec2f(bloxdSpUv.y, 1.0 - bloxdSpUv.x);
        } else if (bloxdSpTextureRotation == 2u) {
                bloxdSpTurned = 1.0 - bloxdSpUv;
        } else if (bloxdSpTextureRotation == 3u) {
                bloxdSpTurned = vec2f(1.0 - bloxdSpUv.y, bloxdSpUv.x);
        }
```

(Le nom `bloxdSpTextureRotation` dans cet extrait est le stockage propre au moteur pour le membre rotation du quatuor d'entrée — le chemin de livraison du v4 §63.2, inchangé dans son rôle.) **Variante 3 — textures de texture pack personnalisé** — échantillonne une cellule par texture d'un atlas en couches via `textureLoad(<atlas>, min(bloxdSpCellAt * bloxdSpSize + bloxdSpAt, <dims> - 1u), bloxdSpLevel)`, avec un chemin `bloxdSpOwnTexel` pour le texel propre du pack.

const bloxdTau: f32 = 6.2831853071796;

// The camera's render position.
fn bloxdEyePosition() -> vec3f {
    return bloxdPackInputs.eyePosition;
}

// Changes as the player travels, so render positions stay close to 0,0,0.
// See bloxdWorldPosition for one way to use it.
fn bloxdRenderOffset() -> vec3i {
    return bloxdPackInputs.renderOffset;
}

// The unit vector towards the sun, in world orientation; 0 when there's no sun.
fn bloxdSunDirection() -> vec3f {
    return bloxdPackInputs.sunDirection;
}

// for the first 4.5 hours. Get a recurring timer using bloxdSeconds() % period.
fn bloxdSeconds() -> f32 {
    return bloxdPackInputs.seconds;
}

// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}

// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}

// Convert a render position to a world position, with possible f32 inaccuracy.
fn bloxdWorldPosition(position: vec3f) -> vec3f {
    return position + vec3f(bloxdRenderOffset());
}

struct BloxdVertexIn {
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
}

struct BloxdVertex {
    position: vec3f,      // The render position output.
}

struct BloxdSurfaceIn {
    colour: vec3f,        // RGB colour = texture * tint * ambient occlusion.
    alpha: f32,           // Opacity.

    // Enchanted items and armour only, all 0 for anything else.
    enchantTier: u32,     // 1-5 for Tier 1-5.
    enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
    enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

    // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
    // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
    overlayColour: vec4f,

    // These mean the same as in BloxdVertexIn, after the vertex hook.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.

    // These are all 0 if the face has no texture. Most models use textureId 0.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}

// blockLight, skyLight and heldLight are 0-1, from the 0-15 light levels on an
// ease-out curve, e.g. 6->0.45, 12->0.92. They all exclude ambientLightColour.
// bloxdLitColour lights a surface from these as the engine does.
struct BloxdLightIn {
    litColour: vec3f,  // Lit and enchanted RGB colour, before emission and fog.
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
    ambient: vec3f,    // RGB ambient colour, added to directional light.
    blockLight: vec3f, // RGB block light; 0 when !bloxdLit().
    skyLight: f32,     // Sky light; 1 when !bloxdLit().
    ambientLightColour: vec3f, // Minimum RGB light; 1 when !bloxdLit().
    skyLightColour: vec3f, // RGB colour of skyLight; 1 when !bloxdLit().
    heldLight: vec3f,  // RGB held light; 0 when !bloxdLit() or no light held.
    fogColour: vec3f,  // The game's RGB fog colour; 0 when the game has no fog.
    fogAlpha: f32,     // 0 = no fog, 1 = only fogColour.

    // These are the same as in BloxdSurfaceIn.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdLight {
    colour: vec3f, // RGB colour output.
}

struct BloxdOpaqueBehind {
    hit: bool,       // False where nothing opaque is behind (sky).
    position: vec3f, // The render position; 0 when !hit.
    distance: f32,   // From the camera; 0 when !hit.
}

fn bloxdDefaultVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return BloxdVertex(vertex.position);
}

fn bloxdDefaultSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return BloxdSurface(
        surface.colour,
#ifdef BLOXD_ALPHA
        surface.alpha,
#endif
        vec3f(0.0),
        surface.enchantColour,
        surface.overlayColour,
    );
}

// Apply this fragment's fog to colour, as the engine does.
fn bloxdApplyFog(colour: vec3f, light: BloxdLightIn) -> vec3f {
    return mix(colour, light.fogColour, light.fogAlpha);
}

// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}

fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
