# Guia de migração para a API v2

> Versão: 2 · Estado: Historical (guia de migração da época; a build alvo está indicada no texto)
Build alvo: `6qxffk.main.5912a15f.js` (deploy em produção em 2026-10-16). As Partes I–VII deste guia já estão reescritas para a base v2; este guia reúne os pontos de migração da v1 e as novidades da v2. Os exemplos de código das novidades passam na validação de 8/8 variantes no compilador v2 e na validação do compilador WGSL do navegador (Tint) (§38), mas a conversão v2 de receitas existentes é substituição mecânica de identificadores — verifique sempre com uma compilação em jogo antes de distribuir.

## 31. Destino dos pacotes v1 (conclusão primeiro)

O jogo exige que o `apiVersion` do manifesto **coincida estritamente com 2**. Carregar um pacote v1 é rejeitado com `This pack is for shader pack API version 1. Bloxd supports version 2.` (chave i18n `shaderPack:loadWrongApiVersion`). **Não há suporte paralelo v1/v2**. O motor também reverifica o `validation.headerVersion` dos pacotes salvos (um hash do texto completo do cabeçalho), então o mecanismo que marca automaticamente pacotes salvos como "needs re-check" em atualizações do motor é o mesmo da v1.

## 32. Renomeação total de identificadores (tabela de correspondência)

A v2 unifica a nomenclatura com sublinhados em camelCase. **Nomes antigos são totalmente inutilizáveis.**

| v1 | v2 |
|---|---|
| `bloxd_terrain_vertex` | `bloxdTerrainVertex` |
| `bloxd_terrain_surface` | `bloxdTerrainSurface` |
| `bloxd_terrain_light` | `bloxdTerrainLight` |
| `bloxd_liquid_vertex` | `bloxdLiquidVertex` |
| `bloxd_liquid_surface` | `bloxdLiquidSurface` |
| `bloxd_liquid_light` | `bloxdLiquidLight` |
| `bloxd_defaultVertex` | `bloxdDefaultVertex` |
| `bloxd_defaultSurface` | `bloxdDefaultSurface` |
| `bloxd_defaultLight` | `bloxdDefaultLight` |
| `bloxd_VertexIn` | `BloxdVertexIn` |
| `bloxd_Vertex` | `BloxdVertex` |
| `bloxd_SurfaceIn` | `BloxdSurfaceIn` |
| `bloxd_Surface` | `BloxdSurface` |
| `bloxd_LightIn` | `BloxdLightIn` |
| `bloxd_Light` | `BloxdLight` |
| `bloxd_packInputs` (uniform interno) | `bloxdPackInputs` (`@group(3) @binding(0)`, 64B) |

Os tipos de hook (vertex / surface / light × terrain / liquid, 6 no total) e o formato `pack.json` (`apiVersion` / `name` / `author`) não mudam. Os limites do carregador também não (zip 32MB / 1024 entradas / 256 arquivos `.wgsl` / 256KB no total / manifesto de 64KB).

## 33. Destino dos campos removidos

Na v1, `time` / `eyePosition` / `sunDirection` / `originOffset` eram campos de struct. Na v2 **esses campos são removidos; em vez deles usam-se funções de cabeçalho que leem o uniform do motor (`bloxdPackInputs`)**. Como as funções leem o uniform diretamente, **elas podem ser chamadas de funções de escopo de módulo fora dos hooks e de hooks vertex**.

| v1 | v2 |
|---|---|
| `s.time` / `v.time` / `l.time` | `bloxdTime()` |
| `s.sunDirection` / `l.sunDirection` | `bloxdSunDirection()` |
| `s.eyePosition` / `l.eyePosition` | `bloxdEyePosition()` |
| `s.originOffset` / `l.originOffset` | `bloxdOriginOffset()` |
| `s.position + vec3f(...)` para conversão em coordenadas de mundo | `bloxdWorldPosition(s.position)` |
| `vec3i(floor(pos - normal*0.5)) + originOffset` | `bloxdFaceBlock(pos, normal)` |

## 34. Novidade 1: `blockId` (sombreamento por bloco)

Os três structs `BloxdVertexIn` / `BloxdSurfaceIn` / `BloxdLightIn` ganharam `blockId: u32`. É o **ID do bloco dono** (0–65535), uniforme em toda a face (passado com `@interpolate(flat)`). Use-o para identificação do tipo de bloco independente da cor da textura. Mas a tabela de ID para tipo de bloco vive dentro do motor e é invisível aos pacotes, então **qual ID é qual bloco pode ser medido no mundo, ou consultado na referência abaixo**. Internamente, esse ID é carregado embutido no alpha da cor do vértice (8 bits baixos) e no w da normal (8 bits altos) — 16 bits no total, daí vem o teto de 65535. O próprio sistema blockId só é ativado enquanto existir um pacote de shaders ativo (sem um pacote, a fiação mantém seus alvos de preenchimento, mas dentro das definições de structs da Parte II essa diferença é inobservável).

**Referência**: o autor publica uma listagem de entradas do jogo em [Bloxd-Entries-Data](https://github.com/imu31465/Bloxd-Entries-Data) (`entries.json`: uma tabela id ↔ nome de bloco; variantes de rotação/meta como `Furnace|meta|rot2` são listadas como IDs separados). As correspondências podem mudar com as atualizações do jogo — para algo definitivo, confirme no jogo real.

Exemplos de blocos comuns (de entries.json em 2026-10-18; apenas as famílias de terreno de id baixo mostradas):

| ID | Nome do bloco | ID | Nome do bloco |
|---|---|---|---|
| 0 | Air | 15 | Maple Wood Planks |
| 1 | Unloaded | 28 | Stone |
| 2 | Dirt | 29 | Messy Stone |
| 3 | Messy Dirt | 31 | Smooth Stone |
| 4 | Grass Block | 126 | Water |
| 5 | Sand | 128 | Bricks |
| 6 | Clay | 139 | Ice |
| 7 | Gravel | 147 | Bedrock |
| 8 | Snow | 149 | Cactus |
| 9 | Maple Log | 1491 | Lava |

entries.json também lista itens que não são blocos (ferramentas etc.), mas só os ids de famílias de blocos chegam aos hooks de terreno / líquido.

### R-F. Tinta por tipo de bloco via blockId

```wgsl
fn blockTint(blockId: u32) -> vec3f {
    // ex. inclina ids pétreos (padrão de bits altos) ao frio
    let stripe = f32((blockId >> 4u) & 1u);
    return mix(vec3f(1.0), vec3f(0.85, 0.95, 1.0), stripe * 0.5);
}

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var result = bloxdDefaultSurface(surface);
    result.colour *= blockTint(surface.blockId);
    return result;
}
```

### R-G. Medir blockId no mundo — o pacote de exibição em planos de bits

Uma receita de depuração para procurar no mundo os ids de blocos que faltam na tabela de correspondência. Mude a constante `plane` inicial por `0, 1, 2, …` enquanto lê a cor da face do bloco que quer identificar.

```wgsl
const plane: u32 = 0u;

fn bloxdTerrainSurface(s: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(s);
    let d = (s.blockId >> (plane * 3u)) & 7u;
    var palette = array<vec3f, 8>(
        vec3f(0.0, 0.0, 0.0), vec3f(1.0, 0.0, 0.0), vec3f(0.0, 1.0, 0.0), vec3f(1.0, 1.0, 0.0),
        vec3f(0.0, 0.0, 1.0), vec3f(1.0, 0.0, 1.0), vec3f(0.0, 1.0, 1.0), vec3f(1.0, 1.0, 1.0));
    out.colour = palette[d];
    return out;
}
```

A cor da face codifica 3 bits do blockId diretamente como RGB (preto = 0 / vermelho = 1 / verde = 2 / amarelo = 3 / azul = 4 / magenta = 5 / ciano = 6 / branco = 7). Uma observação lê um dígito octal. Se p0 → p3 lerem 3, 2, 7, 2, então o octal 2723 = 1491, lido a partir do dígito de cima, é o id (Lava). As famílias de terreno de id baixo terminam com duas observações (p0, p1). Usa só o hook surface, então roda também em títulos estritos.

### R-H. Balançar só as folhas — limitar o hook vertex por blockId

A receita de vento R7 ([Receitas](../recipes/)) faz todo o terreno ondular, mas o hook vertex também pode ler `blockId`, então os alvos podem ser limitados aos blocos de folha. A lista de ids e o array WGSL (medidos em 2026-10-18; 22 tipos — Pine / Aspen / Maple / Jungle / Plum / Cedar / Palm / Autumn Maple / Fallen Maple / Pear / Cherry / Fallen Cherry / Spectral / Mango / variantes frutíferas / Autumn Aspen):

```wgsl
const LEAF_IDS = array<u32, 22>(
    100u, 101u, 102u, 103u, 491u, 492u, 493u, 653u, 655u, 911u,
    1226u, 1227u, 1636u, 1969u, 2019u, 2020u, 2021u, 2022u, 2023u,
    2024u, 2025u, 2085u);

// os hooks vertex são autodesativados em títulos estritos (ver §36)
#ifndef BLOXD_STRICT

fn sp_isLeaf(id: u32) -> bool {
    for (var i = 0u; i < 22u; i++) {
        if (LEAF_IDS[i] == id) { return true; }
    }
    return false;
}

fn bloxdTerrainVertex(v: BloxdVertexIn) -> BloxdVertex {
    var out = bloxdDefaultVertex(v);
    if (sp_isLeaf(v.blockId)) {
        let wp   = bloxdWorldPosition(v.position);
        let t    = bloxdTime();
        // o deslocamento é uma função suave da posição de mundo. Vértices compartilhados que
        // apontam para o mesmo ponto de mundo se movem de forma idêntica, então as faces nunca se rasgam ([Receitas](../recipes/) R7 - mesmo princípio)
        let sway = sin(wp.x * 0.9 + t * 1.7) * cos(wp.z * 0.7 + t * 1.1);
        out.position.x += sway * 0.045;
        out.position.z += sway * 0.030;
    }
    return out;
}

#endif
```

- A lista de ids cresce com as atualizações do motor (só durante a medição, 50 tipos de blocos foram adicionados numa build nova). Para continuar a usá-la, procure as adições via [Bloxd-Entries-Data](https://github.com/imu31465/Bloxd-Entries-Data) ou meça com a exibição em planos de bits do R-G, e estenda o array
- `Fallen Maple Leaves` (655) / `Fallen Cherry Leaves` (1227) são tapetes de folhas não sólidos no chão. Balançá-los faz parecer que eles descolam do chão, então excluí-los do array é uma opção
- Em títulos estritos o hook vertex é desativado por completo, mas com a guarda acima o pacote simplesmente "para de balançar" — os efeitos do lado fragment continuam funcionando

## 35. Novidade 2: `BLOXD_SCENE_DEPTH` e `bloxdOpaqueBehind()` (a principal)

O acesso à profundidade, estruturalmente impossível na v1, é desbloqueado **apenas para programas liquid**. Sem cor, mas **a geometria — distância e posição da face opaca atrás — está disponível**. O uso típico é o cálculo da cor de absorção a partir da espessura de água medida.

Regras de uso:

| Uso | Resultado |
|---|---|
| Chamado sem guarda em `bloxdLiquidSurface` / `bloxdLiquidLight` | OK (sempre definido em variantes liquid) |
| Chamado sem guarda em `bloxdTerrainSurface` | ERROR. Envolva com `#ifdef BLOXD_SCENE_DEPTH` |
| Chamado em hooks vertex | ERROR (só hooks surface / light) |

Para usar profundidade também em hooks de terreno, envolva com `#ifdef BLOXD_SCENE_DEPTH` (hooks de terreno são reutilizados pelos programas liquid, então a profundidade só vive do lado liquid).

### R-E. Absorção por espessura de água (Beer-Lambert)

```wgsl
fn bloxdLiquidSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var result = bloxdDefaultSurface(surface);
    let behind = bloxdOpaqueBehind();
    if (behind.found) {
        // comprimento da coluna de água = daqui até a face opaca atrás
        let thickness = distance(behind.position, surface.position);
        // absorção Beer-Lambert: o vermelho cai rápido, o azul chega longe
        let absorb = exp(-thickness * vec3f(0.35, 0.14, 0.08));
        result.colour *= absorb;
    } else {
        // nada atrás = tinta para o azul de água profunda
        result.colour = mix(result.colour, vec3f(0.05, 0.15, 0.30), 0.4);
    }
    return result;
}
```

Aplicações: absorção/dispersão por espessura, projeção de ondulações estilo cáustica a partir de coordenadas de mundo do fundo via `behind.position`, distinção entre céu e oclusão com `found=false` para o reflexo do céu na água, turvação em estágios conforme a profundidade. Se o pipeline de cópia de profundidade falhar ao ser construído, ele degrada com segurança para "nada atrás". A prontidão da textura de profundidade é decidida uma única vez, quando o renderizador da página é criado, pelo critério "o pacote ativo lê profundidade" — então **recarregue sempre a página ao usar um pacote que lê profundidade**. Se a profundidade for pedida com um pacote ativo mas a página não foi recarregada, o console mostra uma vez o aviso `…reads scene depth on a page that didn't turn it on` e a textura de profundidade é substituída por um fallback 1×1, fazendo `bloxdOpaqueBehind()` retornar sempre `found = false`.

## 36. Outras mudanças da v2

- **Fallback de hooks**: programas liquid caem de volta para os hooks de terreno quando `bloxdLiquidXxx` não está definido. **Pacotes só com hooks de terreno afetam a água como está**. Defina hooks do lado liquid explicitamente quando não for intencional.
- **Sem mais guardas `BLOXD_LIGHTING` para campos**: `blockLight` etc. existem em todas as variantes, com valores padrão quando não iluminadas (0 / 1 / branco / 0). Use `#ifdef BLOXD_LIGHTING` apenas para detectar iluminação. Manter guardas existentes não muda nada.
- **Mudança na condição de definição de `BLOXD_ALPHA`**: definido em variantes de terreno não estritas e em todas as variantes liquid, indefinido em strict × terrain. Mantenha a guarda ao escrever alpha em hooks de terreno.
- **Construção direta de structs proibida**: chamadas de construtor como `BloxdLight(...)` são rejeitadas pela validação estática. Sempre modifique a partir de `bloxdDefault*`, ou use uma cópia da entrada.
- **`let _ =` vira `_ =`**: a atribuição de descarte do WGSL `_ = f();` é válida, mas `let _ = f();` é rejeitada.
- **offInStrict**: definir um hook vertex, ou um `discard` alcançável a partir de hooks surface / light, autodesativa o pacote inteiro em jogos estritos em vez de dar erro (a UI de configurações mostra `shaderPack:offInStrict`; continua rodando em jogos allow). Envolva hooks vertex e `discard` com `#ifndef BLOXD_STRICT`. Note que a própria mensagem da UI oficial de configurações instrui "wrap what remains with `#ifndef BLOXD_STRICT`" — essa prática é recomendação oficial, não convenção.
- **Extensões de névoa**: os modos de névoa LINEAR / EXP / EXP2 estão implementados, mas os ajustes do jogo continuam usando sempre LINEAR, então as specs de névoa existentes continuam funcionando. A semântica de `fogColour` agora está documentada oficialmente (preto apenas em cenas totalmente sem névoa).
- **Sem mudanças**: curva de lift, piso de canal de 35%, atenuação de heldLight (`pow(lightDist, 0.75)`) e boost ambiente, spec de direção de sol/lua, cor de névoa padrão, wrap de tempo (3600 s), luzes direcionais (máx 4), apenas Lite (WebGPU), mecanismo de salvamento (IndexedDB), `mod` palavra reservada.

## 37. Lista de migração v1 → v2

1. **pack.json**: `"apiVersion": 1` → `"apiVersion": 2`
2. **Identificadores**: substitua tudo conforme a tabela §32 (nomes de hooks, structs, funções default)
3. **Porte dos campos removidos**: para funções de cabeçalho conforme a tabela §33 (`s.time` → `bloxdTime()` etc.)
4. **Renomeie `fogFactor` → `fogVisibility`**
5. **Remova a construção direta de structs**
6. **Corrija `let _ =` para `_ =`**
7. **Envolva hooks vertex e discard com `#ifndef BLOXD_STRICT`**
8. **Confirme que a água também sente os efeitos de hooks de terreno**; defina hooks liquid explicitamente quando não for intencional
9. (Opcional) Gerencie você mesmo a névoa a partir de `litColour` / adicione absorção por espessura de água com `bloxdOpaqueBehind()` / estilização por bloco com `blockId`
10. **Valide também a segunda etapa (Tint do navegador)** — ponha parênteses especialmente em expressões que contenham `^` `&` `|` `<<` `>>`. Código que passa na validação estática ainda pode ser rejeitado pelo navegador (§38)

## 38. Segunda etapa de validação — o compilador WGSL do navegador é mais estrito que o analisador embutido

A validação de pacotes no jogo tem **2 etapas**. A primeira etapa é a validação estática (o analisador JS embutido do motor. Ele verifica regras próprias de pacotes como assinaturas de hooks, sintaxe proibida, uso de sceneDepth), e a segunda etapa é a validação do navegador (ele compila stubs que acompanham o resultado de compilação com uma implementação WebGPU real, remapeando os erros de volta para as linhas do arquivo-fonte do pacote para exibição. O "Saved, but it won't run until you fix these errors" da UI é esta etapa). Um sufixo como `(only in terrain)` no fim da exibição de um erro é "a classe de program da variante em que esse erro ocorreu".

O analisador embutido não implementa as regras de ligação (binding) de operadores do WGSL, então **código que passa na validação estática ainda pode ser rejeitado pelo navegador**. A vítima clássica é o idioma de hash de inteiros:

| Operador | Consequência |
|---|---|
| `<<` `>>` | Só podem ligar diretamente em nível unário. `a + b << c` é erro |
| `&` `^` `\|` | Só podem ligar diretamente em nível unário. `a * b ^ c` é erro |
| `&&` `\|\|` | Não podem ser misturados. `a && b \|\| c` é erro |

### Como pôr parênteses (NG / OK)

```wgsl
// NG — passa na validação estática mas o navegador (Tint) o rejeita:
//     mixing '*' and '^' requires parenthesis
let h = a * 73856093u ^ b * 19349663u ^ c * 83492791u;

// OK — ponha parênteses em cada multiplicação (uma cadeia do mesmo operador A ^ B ^ C é legal por associatividade à esquerda)
let h = (a * 73856093u) ^ (b * 19349663u) ^ (c * 83492791u);
```

O código impresso neste guia não contém nada desse padrão (a mistura `+`/`*` de `pack_hash3` e `h ^ (h >> 16u)` já vão entre parênteses, logo em conformidade). Quando escrever um pacote, passe na primeira e na segunda etapa.

## 39. Sobre materiais independentemente similares

Existe um material comunitário de conteúdo quase igual: [Shader de GlitchHunterCoder/Bloxd-Essay](https://github.com/GlitchHunterCoder/Bloxd-Essay/tree/main/Shader).
