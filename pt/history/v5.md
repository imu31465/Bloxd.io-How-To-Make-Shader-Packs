# Guia de migração para a API v5

> Versão: 5 · Estado: Historical (guia de migração da época; o build alvo está indicado no texto)
Build alvo: `ab90qa.main.6188124c.js` — **ativo em produção e preprod simultaneamente (medido em 2026-11-03)**, e os dois bundles voltaram a ser idênticos byte a byte (md5 `fc3322212d15be2445c0e8dfc9733fcc` no bundle principal, baixado ao vivo de ambos os hosts), então tudo aqui se aplica à produção tal qual. Esta é a maior revisão da API desde a v3: o bundle principal cresceu para 3,39 MB (+115 KB sobre o último build v4), o mapa de chunks agora tem 195 ids (c0–c195, 188 emitidos após os 7 buracos conhecidos), o pipeline de shaders continua no cluster c51–c56 (carregador c53, validador/cabeçalho/construtor do registro c55, WebGPU/codegen c56, névoa c9) — mas o template do pack padrão mudou para c116 (estava em c124 em `tcwczu`). Nenhum desses detalhes de layout é visível para um pack. Reverificado no build de produção atual `xkg8x.main.641a7732.js` (2026-11-04, md5 `f11cc032efd474aca567d3793b792057`): o cabeçalho do motor é idêntico byte a byte e todas as medições de carregador / variantes / hooks / nomes reservados abaixo foram re-checadas inalteradas — o registro de texturas é a única superfície que se moveu (896 → 906 nomes utilizáveis; adendo §80). Preprod (`2lcqcl`) serve um bundle principal diferente, mas mediu idêntico em todas as superfícies de shader packs. Reverificado de novo em `bny9u.main.02116121.js` (2026-11-05, md5 `60eea80ec48253b7ac6cc45604dc8273`, servido byte a byte idêntico por produção e preprod): cabeçalho, template de pack padrão, limites do carregador, disposição do uniform, hooks, variantes, macros, nomes reservados e mensagens de validação re-medidos inalterados; o registro moveu-se de novo (906 → 911 nomes utilizáveis; adendo §80), o número de definições de jogo cresceu de 111 para 115, e os chunks do pipeline de shaders foram renumerados (carregador c54, validador/cabeçalho c56, WebGPU/codegen c57, template c122).

O que *é* visível: o cabeçalho do motor cresceu de 6.021 para **8.954 bytes decodificados** (151 → 208 linhas) — quase toda struct ganhou campos, quatro funções novas documentam a própria receita de iluminação do motor, e a máscara de bits `blockFlags` sumiu, substituída por uma struct `BloxdFlags` de booleanos de verdade. A chave de compilação `#ifdef BLOXD_LIGHTING` também sumiu: o estado da iluminação passou para o uniform por frame como membro `lit: u32` e é consultado em tempo de execução com `bloxdLit()`. O template do pack padrão agora vem com **todos os nove hooks** em vez de seis. E o namespace interno do motor `bloxdSp*` cresceu de 27 para 46 símbolos.

O conjunto de mudanças da v5 em uma tela:

| Área | v4 | v5 |
|---|---|---|
| `apiVersion` do `pack.json` | `4` (strict) | **`5` (strict)** — packs v4 são rejeitados no carregamento |
| Identidade de bloco | `blockFlags: u32` + 6 constantes de bit `bloxdBlockFlag*` | **`flags: BloxdFlags`** — 14 campos bool nomeados (§71) |
| Novos tipos de flag | — | **`slab` `stairs` `flat` `placed` `held` `dropped` `thrown` `lifeform`** — modelos e entidades agora são distinguíveis do terrain (§71) |
| Posição de modelo | — | **`localPosition: vec3f`** em toda struct de entrada (§72) |
| Encantamento e sobreposição | somente no motor | **entradas + saídas `enchantTier` / `enchantColour` / `enchantSpeed` / `overlayColour`** (§72–§73) |
| Chave de iluminação | `#ifdef BLOXD_LIGHTING` (tempo de compilação, 8 variantes) | **removida** — o uniform ganha `lit: u32` @ offset 4; teste **`bloxdLit()`** em tempo de execução; 6 variantes (§74) |
| Auxiliares de iluminação | `litColour` privado do motor | **públicas**: `bloxdShading()`, `bloxdWorldLight()`, `bloxdLitColour()` (§74) |
| `bloxdFragmentBlockPosition()` | documentado no cabeçalho | **fora do cabeçalho documentado** — mas ainda injetada e ainda aceita pelo validador (§75) |
| Pack padrão | 6 hooks (vertex+surface) | **9 hooks** — hooks de luz incluídos (§76) |
| `bloxdChunkSize` | não estava no cabeçalho | **nova const `bloxdChunkSize: i32 = 32`** (§78) |
| Namespace `bloxdSp*` | 27 símbolos | **46 símbolos** (+20, −1) (§79) |
| Registro de texturas | 905 nomes utilizáveis | **896 nomes utilizáveis** — +1, −10 (§80) |
| Limites do carregador, regras de zip, forma do `pack.json`, nomes dos hooks, contrato strict | — | **congelados, limites idênticos byte a byte** (§70) |

A conversão da v4 é em sua maioria mecânica (§77): a armadilha silenciosa, desta vez, é outra — um pack que ainda lê `blockFlags` ou protege os hooks de luz com `#ifdef BLOXD_LIGHTING` **falha na validação com uma mensagem específica** (o analisador agora explica ambos), então nada se comporta mal em silêncio; mas um pack que apenas *lê as antigas constantes de bit* pelo nome vai se recusar a carregar até ser portado. Como sempre, verifique com uma compilação no jogo antes de distribuir.

## 69. Destino dos packs v4 (conclusão primeiro)

**Todo pack v4 — incluindo todo pack distribuído como v4 — agora falha em produção exatamente no carregamento.** O carregador compara `manifest.apiVersion !== 5` com o `!==` estrito do JavaScript — a constante de versão `5` e o template de cabeçalho vivem no mesmo módulo deste build (módulo 29836), então a verificação e o texto de cabeçalho contra o qual ela valida se movem juntos. O JSON deve carregar o *número* `5`; uma string `"5"` falha e é reportada com a sua grafia JSON, exatamente como na v4.

As duas mensagens de carregamento estão inalteradas em relação à v4, verbatim do dicionário i18n ativo:


> `This pack is for shader pack API version {{packVersion}}. Bloxd supports version {{version}}.` — a chave está presente, mas não é igual a 5.

Um pack v4 guardado (que antes funcionava) não lança nada ao jogador: o resultado do pack guardado resolve para `{kind: "none", reason: "otherApiVersion"}`, o pack fica silenciosamente inativo, e a aba de ajustes de pacotes de shaders se explica com a linha de status:

> `This shader pack is for API version {{packVersion}}, so it won't run. Load a version {{version}} pack to replace it.`

As regras do manifesto, fora isso, foram remedidas e seguem inalteradas: `pack.json` deve ser um objeto JSON na raiz do zip; `apiVersion` deve estar presente e ser `=== 5`; `name` é obrigatório, uma string, não vazia após o trim; `author` é opcional, mas deve ser uma string se presente; todo o resto do manifesto é ignorado.

## 70. pack.json, o carregador e o uniform (o que permanece inalterado)

O modelo inteiro de pack passa da v4 byte a byte. Os limites do carregador, remedidos no chunk do carregador ativo (c53):

| Limite | Valor | Mensagem ao exceder |
|---|---|---|
| Arquivos `.wgsl` por pack | 256 | `The pack has more than 256 .wgsl files.` |
| Fonte `.wgsl` total | 256 KB | `The pack's .wgsl files are over 256 KB in total.` |
| Tamanho do `pack.json` | 64 KB | `pack.json is over 64 KB.` |
| Tamanho do zip | 32 MB | `The zip is over 32 MB.` |
| Entradas do zip | 1.024 | `The zip has more than 1024 entries.` |
| Forma do zip | — | zips divididos, Zip64, entradas criptografadas e métodos de compressão não suportados são cada um rejeitados com uma mensagem dedicada; todo arquivo deve ser UTF-8 válido; exatamente um `pack.json`; sem caminhos duplicados |

O uniform por frame continua sendo `@group(3) @binding(0) var<uniform> bloxdPackInputs: BloxdPackInputs`, continua com 64 bytes — mas ganhou um membro. A tabela de layout, do módulo de layout de uniform ativo:

| Offset | Campo | Tipo | Nota |
|---|---|---|---|
| 0 | `seconds` | `f32` | respalda `bloxdSeconds()` |
| 4 | `lit` | `u32` | **novo na v5** — 1 quando a iluminação de bloco/céu está ligada; respalda `bloxdLit()` |
| 16 | `renderOffset` | `vec3i` | respalda `bloxdRenderOffset()` |
| 32 | `sunDirection` | `vec3f` | respalda `bloxdSunDirection()` |
| 48 | `eyePosition` | `vec3f` | respalda `bloxdEyePosition()` |

`lit` se encaixa no padding que a v4 já tinha entre `seconds` e `renderOffset` (os offsets 4–15 eram folga de alinhamento na v4; `renderOffset` fica em 16 porque um `vec3i` precisa de alinhamento de 16 bytes), então o tamanho total da struct e o offset de todos os outros membros não mudam. O motor o escreve com um único `setUint32(4, lit ? 1 : 0)` — é uma flag, não um nível de luz: os nomes do lado JS da v4 `terrainLightLevels` / `terrainHeldLight` sumiram do bundle inteiramente.

O layout de bind groups do pack não muda por fora disso: o grupo 3 continua `0` uniform · `1` textura de scene depth (variantes liquid) · `2` o buffer de armazenamento `bloxdSpTextureLayers`. `minBindingSize` continua 64.

## 71. A reescrita das flags: `blockFlags` → `BloxdFlags` (a manchete)

A v4 identificava uma face com um `blockFlags: u32` e seis constantes `bloxdBlockFlag*` (opaque 1, emissive 2, vegetation 4, dirt 8, sand 16, rock 32). A v5 substitui o mecanismo inteiro por uma struct de booleanos nomeados, citada verbatim do cabeçalho ativo:

```wgsl
// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    // Drawn as block models, so never part of terrain or flagged as opaque.
    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    placed: bool,     // Blocks placed as part of chunks. Not items or vehicles.
    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}
```

Os seis testes de bit da v4 mapeiam um-para-um em campos — a migração é um renome, não um repensar:

| v4 | v5 |
|---|---|
| `(surface.blockFlags & bloxdBlockFlagOpaque) != 0u` | `surface.flags.opaque` |
| `(surface.blockFlags & bloxdBlockFlagEmissive) != 0u` | `surface.flags.emissive` |
| `(surface.blockFlags & bloxdBlockFlagVegetation) != 0u` | `surface.flags.vegetation` |
| `(surface.blockFlags & bloxdBlockFlagDirt) != 0u` | `surface.flags.dirt` |
| `(surface.blockFlags & bloxdBlockFlagSand) != 0u` | `surface.flags.sand` |
| `(surface.blockFlags & bloxdBlockFlagRock) != 0u` | `surface.flags.rock` |

Os oito campos **novos** são a história de verdade. A v4 não tinha como distinguir uma laje de um bloco cheio, um item na mão do terrain, ou um jogador de uma abóbora — toda face não-terrain era apenas "não opaca" com um id de textura. A v5 responde "no que estou olhando" diretamente:

- **`slab` / `stairs` / `flat`** — as três formas de modelo de bloco. `flat` cobre as plantas de planos cruzados (grama alta, flores, plantações, teias de aranha). Elas são *desenhadas como modelos de bloco*, então o cabeçalho observa que nunca fazem parte do terrain e nunca são `opaque`.
- **`placed`** — geometria de chunk tal como colocada no mundo; explicitamente *não* itens nem veículos.
- **`held`** — itens em uma mão, em primeira ou terceira pessoa. Este é o campo que os autores de shaders em primeira pessoa queriam desde a v1: você finalmente pode detectar o item na mão e tratá-lo de forma diferente do mundo.
- **`dropped`** / **`thrown`** — itens no chão / em esteiras / em tubos, contra itens em voo (bolas de neve, flechas, foguetes).
- **`lifeform`** — jogadores, mobs e NPCs, *incluindo armaduras e cosméticos*.

Combinado com `localPosition` (§72) e as entradas de encantamento/sobreposição, o pipeline de modelos agora pode ser sombreado com pleno conhecimento do que está renderizando. Uma receita mínima de "brilho do item na mão", impossível na v4:

```wgsl
fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    var out = bloxdDefaultSurface(surface);
    // Clareia o que o jogador local segura, nada mais.
    if (surface.flags.held) {
        out.colour *= 1.15;
    }
    return out;
}
```

Note o que *não* mudou: os campos vivem no mesmo lugar nas três structs de entrada (`BloxdVertexIn`, `BloxdSurfaceIn`, `BloxdLightIn` — nome do campo `flags`, tipo `BloxdFlags`), a semântica dos seis booleanos sobreviventes é a semântica da v4 com os mesmos casos-limite que o cabeçalho agora explicita ("Rocky Dirt is rock too", "every sandstone is rock too"), e várias flags continuam se combinando livremente ("sandstone is sand and rock", "possibly even none").

## 72. Novas entradas: `localPosition`, o quarteto de encantamento e `overlayColour`

`BloxdVertexIn`, `BloxdSurfaceIn` e `BloxdLightIn` ganham todos os mesmos novos membros. Do cabeçalho, verbatim:

```wgsl
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
```

- **`localPosition`** — a posição em espaço de modelo do vértice/fragmento, antes de a instância do modelo ser colocada no mundo. `vec3f(0.0)` para faces de terrain e liquid (elas não têm modelo). Para o braço de um jogador, uma espada na mão, a pá de um moinho, esta é a coordenada que gira com o modelo — uma animação por modelo ou um efeito de curvatura indexado em "em que parte da espada estou" agora usa um campo, em vez de suposições em espaço de mundo. Na struct light, o cabeçalho observa que ela é "the same as in BloxdVertexIn, after the vertex hook" — ou seja, se o seu hook de vértice move o vértice, o `localPosition` do hook de luz o acompanha.

E apenas em `BloxdSurfaceIn` / `BloxdLightIn` (a struct de vértice não precisa delas):

```wgsl
     // Enchanted items and armour only, all 0 for anything else.
     enchantTier: u32,     // 1-5 for Tier 1-5.
     enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
     enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

     // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
     // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
     overlayColour: vec4f,
```

- **`enchantTier`** — o tier de encantamento do item como um inteiro 1–5, para o clássico efeito "intensidade do brilho por tier" sem fazer parse da cor.
- **`enchantColour`** — o RGB vivo do encantamento mais o seu alfa *animado* em `.a`: o motor anima a varredura do brilho, então ler `.a` por fragmento dá de graça o padrão em movimento. Tudo zero em faces sem encantamento.
- **`enchantSpeed`** — a rapidez com que o padrão de encantamento se move; a nota do próprio cabeçalho é "faster at higher tiers", então `enchantTier` e `enchantSpeed` são consistentes por construção.
- **`overlayColour`** — o clarão de dano/ferimento e sobreposições semelhantes de entidades (RGB + alfa), 0 para qualquer coisa que não seja jogador ou mob. O motor mistura isto *antes* da iluminação; veja §73 para o lado da saída.

O antigo quarteto (`textureId`, `textureRotation`, `uv`, `mipLevel`) passa intacto, com um comentário reescrito: a v4 dizia que `uv` eram "texture coordinates in blocks"; a v5 diz "The texture spans 0-1. `fract(uv)` is drawn." — o mesmo campo, descrito do ponto de vista da textura: um ladrilho de textura cobre `0.0–1.0` de uv, e passos inteiros de uv o ladrilham ao longo de uma parede repetida. Nenhuma ação de porte é necessária, a menos que você tenha codificado à mão suposições sobre extensões de vários blocos.

## 73. Novas saídas: `BloxdSurface` ganha `enchantColour` e `overlayColour`

A struct de **saída** de surface ganha dois campos, verbatim:

```wgsl
struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}
```

O seu hook de surface agora é dono do brilho do encantamento e do clarão de dano, do mesmo modo como já era da emissão:

- `bloxdDefaultSurface` repassa `surface.enchantColour` e `surface.overlayColour` sem alteração, então a aparência padrão é idêntica ao comportamento do lado do motor na v4.
- **Zerar `out.enchantColour`** no seu hook remove o brilho do encantamento da sua iluminação personalizada — um pack de "realismo sem brilho" agora são duas linhas.
- **Amplificar `out.overlayColour.a`** torna o clarão de dano mais marcante sem tocar na cor base; a mistura acontece em `bloxdLitColour` (§74), após o sombreamento, exatamente onde o motor a colocava.
- A nota sobre a ordem da emissão passa verbatim: a emissão é *somada após a iluminação, antes da névoa* — e os dois campos novos são *misturados por `bloxdLitColour`*, que vem *antes* da emissão e da névoa. A cadeia de saída completa, em ordem: `colour` → mistura da sobreposição → sombreamento → mistura do encantamento → luz do mundo → `+ emission` → névoa.

## 74. A receita de iluminação fica pública: `bloxdLit()` e os três auxiliares

A v4 controlava o código de iluminação em tempo de compilação: 8 variantes (`strict|allow` × `lit|unlit` × `terrain|liquid`), com `#ifdef BLOXD_LIGHTING` decidindo se os hooks de luz rodavam o caminho lit ou o unlit. A v5 retira o eixo de iluminação inteiro da compilação:

- A **matriz de variantes é 6, não 8**: `strict|allow` × `terrain|liquid|model`, com nomes `allow.terrain` … `strict.liquid` etc. (as etiquetas que o próprio motor constrói para a tela do carregador).
- `BLOXD_STRICT` continua somente-strict; `BLOXD_ALPHA` continua todo-liquid mais toda variante allow (desligada para strict terrain e strict model); `BLOXD_SCENE_DEPTH` continua somente-liquid. **`BLOXD_LIGHTING` não existe mais.**
- O estado da iluminação foi para o uniform (`lit: u32`, §70) e é consultado no código com a nova função de cabeçalho:

```wgsl
// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}
```

Se o seu pack v4 envolvia os hooks de luz em `#ifdef BLOXD_LIGHTING ... #else ... #endif`, o porte para a v5 é um retorno antecipado: `if (!bloxdLit()) { return bloxdDefaultLight(surface, light); }`. O analisador até diz isso a você — usar `BLOXD_LIGHTING` agora produz a mensagem de validação *"BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead."* (medida verbatim do validador ativo).

Mais três funções entram para o cabeçalho, e são justamente as que os autores da v4 viviam rederivando à mão — a própria iluminação do motor, documentada como WGSL invocável:

```wgsl
// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}
```

E o próprio `bloxdDefaultLight` agora as usa — o padrão é literalmente "aplicar a receita do motor e então pôr névoa no resultado estendido com emissão":

```wgsl
fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
```

Para alimentar `bloxdShading`, `BloxdLightIn` também ganha duas entradas (comentários verbatim):

```wgsl
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
```

`diffuse` e `emissive` são novos na v5 (a v4 tinha apenas `directional` e `ambient`): eles permitem reconstruir `bloxdShading` com modificações — p. ex. manter a luz do mundo do motor mas substituir o termo de Lambert pelo seu próprio sombreamento envolvente — sem perder a resposta de material que o motor já conhece. Os comentários de documentação sobre os níveis de luz também foram reescritos, de "0 without BLOXD_LIGHTING" para "0 when !bloxdLit()", o que é o mesmo fato no vocabulário da v5.

Um hook de luz de "sombreamento próprio, luz do mundo do motor" — a receita que os autores da v4 aproximavam escalando `litColour`, agora exata:

```wgsl
fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    // Envelope de Half-Lambert: suave, nunca totalmente escuro na face de trás.
    let nDotL = light.directional; // já é o termo de Lambert somado
    let wrapped = nDotL * 0.5 + 0.5;
    let shaded = saturate(wrapped * light.diffuse + light.emissive + light.ambient);
    let colour = max(shaded * bloxdWorldLight(light), vec3f(0.0));
    return BloxdLight(bloxdApplyFog(colour + surface.emission, light));
}
```

## 75. Remoções: `bloxdFragmentBlockPosition()`, `bloxdBlockFlag*`, `bloxdSpLitColour`

Três coisas se foram, e o validador diz isso pelo nome:

- **`bloxdFragmentBlockPosition(position, normal) -> vec3i`** — saiu do cabeçalho documentado, mas **não está morta de fato**: a tabela de assinaturas do validador manteve a entrada dela (então chamadas ainda passam na validação em qualquer hook, vértice incluído), e o gerador de código ainda injeta uma definição no módulo terrain/liquid e em ambos os programas de modelo (`vec3i(floor(position - normal * 0.5)) + bloxdRenderOffset()` para terrain/liquid; uma variante com offset de 1/64 e ajuste a células para modelos). Packs v4 que a chamam continuam funcionando. Trate-a como deprecada: ela está sem documentação agora, então prefira `bloxdWorldPosition()` para posições contínuas e `flags` para "em qual bloco estou", e espere que ela possa sumir em uma versão futura.
- **As seis constantes `bloxdBlockFlag*`** — substituídas por `BloxdFlags` (§71). Qualquer referência sobrevivente falha na validação com o diagnóstico de nome reservado do analisador.
- **`bloxdSpLitColour`** — o símbolo interno do motor cujo trabalho virou o público `bloxdLitColour()` (§74). Ele sai do namespace `bloxdSp*`, que, fora isso, só cresce (§79).

As funções da era v4 que sobrevivem inalteradas: `bloxdEyePosition()`, `bloxdRenderOffset()`, `bloxdSunDirection()`, `bloxdSeconds()`, `bloxdWorldPosition()`, `bloxdApplyFog()`, `bloxdDefaultVertex()`, `bloxdDefaultSurface()`, `bloxdDefaultLight()`, mais toda a API de texturas (`bloxdTexel`, `bloxdTextureSize`, `bloxdTextureId*` — o §79 remede o registro) e `BloxdOpaqueBehind` / `bloxdSceneDepth` com sua semântica de variantes liquid.

## 76. O pack padrão vem com os nove hooks

O template de que um pack novo parte agora inclui os hooks de luz — o template da v4 tinha seis (vertex+surface por programa) e deixava os hooks de luz para serem copiados da documentação. O da v5, verbatim e completo (1.633 bytes como distribuído):

```wgsl
// Every hook here returns its engine default. Modify the return values to start
// building a shader pack. If you delete a hook, the default is used instead.

// All blocks but water and block models use terrain hooks.
#ifndef BLOXD_STRICT
// Strict games keep terrain where it is. Without the #ifndef, this hook would
// turn the whole shader pack off there.
fn bloxdTerrainVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdTerrainLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Water uses liquid hooks. To share code with another hook, define a function
// and call it from both places.
#ifndef BLOXD_STRICT
fn bloxdLiquidVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdLiquidSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdLiquidLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}

// Models: block models such as slabs and plants, items, players and mobs.
#ifndef BLOXD_STRICT
fn bloxdModelVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return bloxdDefaultVertex(vertex);
}
#endif

fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return bloxdDefaultSurface(surface);
}

fn bloxdModelLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    return bloxdDefaultLight(surface, light);
}
```

Os comentários são uma redação nova e valem a leitura como documentação do modelo de exclusão: *"Modify the return values to start building a shader pack. If you delete a hook, the default is used instead."* A nota de liquid também mudou — a v4 dizia "If deleted, water uses your terrain hooks instead", a v5 diz "To share code with another hook, define a function and call it from both places" — e a nota strict agora explica o `#ifndef` em uma frase: *"Strict games keep terrain where it is. Without the #ifndef, this hook would turn the whole shader pack off there."*

O contrato de jogos strict em si (v4 §60) não mudou: um hook de vértice sem guarda reporta `<hook> moves terrain, which strict games prevent.`, um `discard` alcançável reporta `discard makes terrain see-through, which strict games prevent.`, e qualquer um dos dois desativa *todos* os hooks em jogos strict. Os 12 títulos allow foram remedidos no bundle ativo — continuam 12, inalterados.

## 77. Checklist de migração v4 → v5

1. **`pack.json`**: `"apiVersion": 5` — o número, não uma string.
2. **Porte as flags** (mecânico, §71): cada `blockFlags & bloxdBlockFlagX != 0u` → `flags.x`; apague as constantes — o validador as rejeita pelo nome.
3. **Porte a chave de iluminação** (a única com mensagem do validador): `#ifdef BLOXD_LIGHTING` → `if (bloxdLit()) { ... } else { return bloxdDefaultLight(surface, light); }`; `BLOXD_LIGHTING` agora dispara *"BLOXD_LIGHTING was removed in apiVersion 5; test bloxdLit() in code instead."*
4. **Migre para fora de `bloxdFragmentBlockPosition`** (§75) — ela ainda compila, mas está sem documentação agora; use `bloxdWorldPosition()` / `flags`.
5. **Decida sobre as novas entradas/saídas** *(opcional)*: `flags.slab/stairs/flat/placed/held/dropped/thrown/lifeform` (§71), `localPosition` (§72), o quarteto de encantamento + `overlayColour` (§72–§73). O repasse via `bloxdDefaultSurface` mantém exatamente a aparência da v4.
6. **Adote os auxiliares da receita do motor** *(opcional, mas recomendado)*: substitua a cor de luz feita à mão por `bloxdLitColour(surface, light)` — ou misture e combine com `bloxdShading` / `bloxdWorldLight` (§74) — e então adicione `surface.emission` e `bloxdApplyFog` como `bloxdDefaultLight` faz.
7. **Auditoria strict** (inalterada desde a v4): `#ifndef BLOXD_STRICT` em volta dos hooks de vértice e de qualquer `discard` alcançável.
8. **Verificação de compilação no jogo**: o carregador valida todas as **6** variantes de uma vez (strict × terrain/liquid/model — o eixo de iluminação não compila mais separadamente, §74). Depois confira visualmente um jogo allow e um jogo strict.
9. **Incremente os metadados da sua própria versão e redistribua**: cópias v4 guardadas nas máquinas dos jogadores ficam silenciosamente inativas (§69) e só a aba de ajustes diz o porquê.

### 77.1 Um porte completo de v4 → v5, antes e depois

Um pack v4 compacto — "tintura de vegetação + reforço de luz na mão" — como falharia hoje, e portado:

```wgsl
// ---- v4 (falha na validação em ab90qa) ----

```

```wgsl

fn bloxdTerrainSurface(surface: BloxdSurfaceIn) -> BloxdSurface {

        out.colour *= vec3f(1.0, 1.08, 0.9);

    var out = bloxdDefaultLight(surface, light);

```

```wgsl
fn bloxdModelSurface(surface: BloxdSurfaceIn) -> BloxdSurface {

    if (surface.flags.lifeform && !surface.flags.held) {
```

## 78. Outras mudanças e notas da v5

- **`bloxdChunkSize` entra para o cabeçalho** — `const bloxdChunkSize: i32 = 32;` ("Blocks along each side of a chunk"). Antes, um número mágico do lado do motor; agora, uma constante nomeada sobre a qual você pode ramificar. `bloxdPi`/`bloxdTau` inalteradas.
- **A seção de funções por frame do cabeçalho ganhou um comentário compartilhado** — "These functions return the same value for the entire frame" (v4: "return 1 value per frame, the same for every call site") — pura redação.
- **Derivadas em Y são negadas automaticamente no código do pack.** O analisador reescreve toda chamada a `dpdy`, `dpdyCoarse` ou `dpdyFine` em `(-dpdy(...))` — o eixo y do espaço de tela aponta para baixo, então a negação faz a "derivada em relação a subir" corresponder à intuição. Você escreve `dpdy(h)` esperando "como h muda ao subir"; o código emitido a nega para você. `dpdx` e a família `fwidth` ficam intactas. (Medido na passagem de reescrita de tokens do validador; a família dpdy está listada especificamente como o conjunto da negação.)
- **Os diagnósticos de nome de textura ganharam um motor de grafias.** Um nome que começa com `bloxdTextureId` mas não resolve agora recebe uma sugestão via Levenshtein: *"`X' isn't part of the shader pack API. Texture names start with exactly bloxdTextureId: did you mean bloxdTextureIdY?"* — mais mensagens dedicadas para grafias de quadro (*"names a frame of the animated texture Z: use bloxdTextureIdZ, which bloxdTexel animates."*) e grafias giradas (*"names a turned copy of Z: use bloxdTextureIdZ, which bloxdTexel turns as each face shows it."*). A regra geral de reserva é reenunciada nos diagnósticos: *"Packs can't declare names starting with bloxd, other than the hook functions bloxd<Terrain|Liquid|Model><Vertex|Surface|Light>"*, e *"Packs can't use X: the engine binds every texture and sampler. Surface and light hooks can read atlas textures with bloxdTexel."*
- **Somente as constantes de textura referenciadas são emitidas.** O bloco `bloxdTextureId*` do cabeçalho é gerado por pack a partir dos nomes que você realmente referencia — um pack que usa três constantes recebe três linhas `const` prefixadas, não as ~900 completas.
- **`HEADER_VERSION` passou para `9.<hash>.<hash>`** — mesma estrutura de dois sufixos da v4 (fnv1a32 do material do cabeçalho, fnv1a32 do registro ordenado nome-id), com o inteiro inicial elevado de 8 para 9. A lógica de reverificação de packs guardados (§55 do [guia v4](v4.md)) não mudou: uma mudança de cabeçalho/registro alterna packs guardados para "precisa de nova verificação".
- **Superfície i18n**: a família de chaves de pacotes de shaders está inalterada em forma (as chaves `load*`, `status*` e de rótulos de variante do guia v4 §62 todas remedidas presentes; `loadNoWgsl`/`loadNotZip` continuam exatas).
- **Layout do bundle para re-pesquisadores**: cabeçalho c55 (inalterado), carregador/persistência c51–c53, validador + construtor do registro c55, codegen WebGPU c56, névoa c9, **template do pack padrão c116** (movido de c124), os pontos de BLOXD_ALPHA c51/c52/c53/c55/c9. Nota sobre o formato dos chunks: cada chunk agora é um módulo ES (`export const modules = {...}`) — c53 inclusive carrega módulos tanto para c52 quanto para c53 — o que importa se você faz busca de texto no bundle (um id de módulo como `1371` vive no array esparso de módulos de *main*, não em nenhum chunk).

## 79. Internos do motor v5: o pipeline de texturas e o namespace `bloxdSp*` de 46 símbolos

O codegen de texturas de três variantes da v4 §63 passa adiante com a mesma forma. Restaurado do gerador ativo (c56):

**Variante 1 — nenhum pacote de texturas ativo** (o bloco gerado inteiro; `bloxdTextureSize` e `bloxdTexel` são stubs):

**Variante 2 — o caminho do atlas** (o padrão nos jogos): `bloxdTextureSize` devolve `textureDimensions(textureAtlas0, u32(clamp(round(bloxdSpMipLevel), 0.0, f32(textureNumLevels(textureAtlas0) - 1u))))`, e `bloxdTexel` aplica o quarto de volta de rotação da face antes de carregar — a sutileza de rotação da v4 (guia v4 §57.4), agora escrita como uma cadeia de if explícita sobre o `bloxdSpTurned` gerado:

```wgsl
        // Each quarter turn clockwise the face shows its texture at reads the unturned texture at (v, 1 - u)
        var bloxdSpTurned = bloxdSpUv;
        if (bloxdSpTextureRotation == 1u) {
                bloxdSpTurned = vec2f(bloxdSpUv.y, 1.0 - bloxdSpUv.x);
        } else if (bloxdSpTextureRotation == 2u) {
                bloxdSpTurned = 1.0 - bloxdSpUv;

                bloxdSpTurned = vec2f(1.0 - bloxdSpUv.y, bloxdSpUv.x);

```

## 82. O cabeçalho completo do motor v5, verbatim

O artefato do §67, remedido para a v5: o texto exato que o carregador antepõe a cada pack, restaurado do bundle de produção ativo (`ab90qa`, chunk c55, template renderizado com as suas seis interpolações ativas — `apiVersion` e as cinco leituras de uniform através de `bloxdPackInputs`). 8.954 bytes decodificados, 208 linhas. Nada está parafraseado:

```wgsl

// The Bloxd shader pack API, apiVersion 5. Read-only, prepended to all packs.

const bloxdPi: f32 = 3.1415926535898;
const bloxdTau: f32 = 6.2831853071796;

// Blocks along each side of a chunk.
const bloxdChunkSize: i32 = 32;

// These functions return the same value for the entire frame.

// The camera's render position.
fn bloxdEyePosition() -> vec3f {
    return bloxdPackInputs.eyePosition;
}

// Integer distance, in blocks: render position + this offset = world position.
// Changes as the player travels, so render positions stay close to 0,0,0.
// See bloxdWorldPosition for one way to use it.
fn bloxdRenderOffset() -> vec3i {
    return bloxdPackInputs.renderOffset;
}

// The unit vector towards the sun, in world orientation; 0 when there's no sun.
fn bloxdSunDirection() -> vec3f {
    return bloxdPackInputs.sunDirection;
}

// Seconds since the page loaded. As an f32, it has sub-millisecond precision
// for the first 4.5 hours. Get a recurring timer using bloxdSeconds() % period.
fn bloxdSeconds() -> f32 {
    return bloxdPackInputs.seconds;
}

// Whether block and sky lighting is on. When it's off, BloxdLightIn's
// blockLight and heldLight are 0, and its skyLight and light colours are 1.
fn bloxdLit() -> bool {
    return bloxdPackInputs.lit != 0u;
}

// What kind of block, item or lifeform a face is. Any number of flags may be
// set, possibly even none. For example, sandstone is sand and rock.
struct BloxdFlags {
    opaque: bool,     // Opaque blocks, i.e. full cubes with no gaps or holes.
    emissive: bool,   // Blocks that emit light, e.g. lava and glowing ores.
    vegetation: bool, // Leaves, grass blocks and leafy plants, e.g. tall grass.
    dirt: bool,       // Soil, grass blocks included. Rocky Dirt is rock too.
    sand: bool,       // Sand, Red Sand and every sandstone, which is rock too.
    rock: bool,       // Stone variants, and more, e.g. gravel, ores and magma.

    // Drawn as block models, so never part of terrain or flagged as opaque.
    slab: bool,       // Half blocks.
    stairs: bool,     // Stairs and corner stairs.
    flat: bool,       // Planes, e.g. tall grass, flowers, crops and cobwebs.

    placed: bool,     // Blocks placed as part of chunks. Not items or vehicles.
    held: bool,       // Items in a hand, in first or third person.
    dropped: bool,    // Dropped items, on the ground, on a belt or in a pipe.
    thrown: bool,     // Items in flight, e.g. snowballs, arrows and rockets.

    lifeform: bool,   // Players, mobs and NPCs. Includes armour and cosmetics.
}

// Convert a render position to a world position, with possible f32 inaccuracy.
fn bloxdWorldPosition(position: vec3f) -> vec3f {
    return position + vec3f(bloxdRenderOffset());
}

struct BloxdVertexIn {
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
}

struct BloxdVertex {
    position: vec3f,      // The render position output.
}

struct BloxdSurfaceIn {
    colour: vec3f,        // RGB colour = texture * tint * ambient occlusion.
    alpha: f32,           // Opacity.

    // Enchanted items and armour only, all 0 for anything else.
    enchantTier: u32,     // 1-5 for Tier 1-5.
    enchantColour: vec4f, // RGB enchant colour, and its animated alpha.
    enchantSpeed: f32,    // How fast the pattern moves, faster at higher tiers.

    // Players and mobs only, 0 for anything else: RGB overlay colour, e.g. the
    // red flash when hurt, and its alpha. bloxdLitColour mixes it into colour.
    overlayColour: vec4f,

    // These mean the same as in BloxdVertexIn, after the vertex hook.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.

    // These are all 0 if the face has no texture. Most models use textureId 0.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdSurface {
    colour: vec3f,        // RGB colour output.
#ifdef BLOXD_ALPHA
    alpha: f32,           // Opacity output.
#endif
    emission: vec3f,      // Emissive RGB, added after lighting, before fog.
    enchantColour: vec4f, // Enchant output, mixed in by bloxdLitColour.
    overlayColour: vec4f, // Overlay output, mixed in by bloxdLitColour.
}

// blockLight, skyLight and heldLight are 0-1, from the 0-15 light levels on an
// ease-out curve, e.g. 6->0.45, 12->0.92. They all exclude ambientLightColour.
// bloxdLitColour lights a surface from these as the engine does.
struct BloxdLightIn {
    litColour: vec3f,  // Lit and enchanted RGB colour, before emission and fog.
    directional: f32,  // Summed Lambert from directional lights; 0 if none.
    diffuse: vec3f,    // The material's RGB response to directional light.
    emissive: vec3f,   // The material's RGB glow, added to directional light.
    ambient: vec3f,    // RGB ambient colour, added to directional light.
    blockLight: vec3f, // RGB block light; 0 when !bloxdLit().
    skyLight: f32,     // Sky light; 1 when !bloxdLit().
    ambientLightColour: vec3f, // Minimum RGB light; 1 when !bloxdLit().
    skyLightColour: vec3f, // RGB colour of skyLight; 1 when !bloxdLit().
    heldLight: vec3f,  // RGB held light; 0 when !bloxdLit() or no light held.
    fogColour: vec3f,  // The game's RGB fog colour; 0 when the game has no fog.
    fogAlpha: f32,     // 0 = no fog, 1 = only fogColour.

    // These are the same as in BloxdSurfaceIn.
    position: vec3f,      // Render position.
    normal: vec3f,        // Unit vector pointing away from the face.
    localPosition: vec3f, // A model's local coordinates. 0 for terrain/liquid.
    flags: BloxdFlags,    // What kind of block, item or lifeform.
    textureId: u32,       // This face's texture. Compare with bloxdTextureId*.
    textureRotation: u32, // Quarter turns clockwise, which bloxdTexel applies.
    uv: vec2f,            // The texture spans 0-1. fract(uv) is drawn.
    mipLevel: f32,        // Texture mipmap level. 0 = full size, 1 = half, etc.
}

struct BloxdLight {
    colour: vec3f, // RGB colour output.
}

struct BloxdOpaqueBehind {
    hit: bool,       // False where nothing opaque is behind (sky).
    position: vec3f, // The render position; 0 when !hit.
    distance: f32,   // From the camera; 0 when !hit.
}

fn bloxdDefaultVertex(vertex: BloxdVertexIn) -> BloxdVertex {
    return BloxdVertex(vertex.position);
}

fn bloxdDefaultSurface(surface: BloxdSurfaceIn) -> BloxdSurface {
    return BloxdSurface(
        surface.colour,
#ifdef BLOXD_ALPHA
        surface.alpha,
#endif
        vec3f(0.0),
        surface.enchantColour,
        surface.overlayColour,
    );
}

// Apply this fragment's fog to colour, as the engine does.
fn bloxdApplyFog(colour: vec3f, light: BloxdLightIn) -> vec3f {
    return mix(colour, light.fogColour, light.fogAlpha);
}

// How the face's material and angle light it: directional light on its
// diffuse colour, plus its emissive and ambient terms, clamped to 0-1.
fn bloxdShading(light: BloxdLightIn) -> vec3f {
    let diffuse = light.directional * light.diffuse;
    return saturate(diffuse + light.emissive + light.ambient);
}

// The world's light at this fragment: the brightest of block, sky and held
// light, none below ambientLightColour.
fn bloxdWorldLight(light: BloxdLightIn) -> vec3f {
    let ambientLight = light.ambientLightColour;
    let blockLight = ambientLight + light.blockLight * (1.0 - ambientLight);
    let skyLight = mix(ambientLight, light.skyLightColour, light.skyLight);
    let heldLight = ambientLight + light.heldLight * (1.0 - ambientLight);
    return max(max(blockLight, skyLight), heldLight);
}

// The surface's colour lit as the engine does, before emission and fog:
// mixed with overlayColour, then bloxdShading, then mixed with
// enchantColour, then bloxdWorldLight.
fn bloxdLitColour(surface: BloxdSurface, light: BloxdLightIn) -> vec3f {
    let overlay = surface.overlayColour;
    let overlaid = mix(surface.colour, overlay.rgb, overlay.a);
    let shaded = bloxdShading(light) * overlaid;
    let enchant = surface.enchantColour;
    let enchanted = mix(shaded, enchant.rgb, enchant.a);
    return max(enchanted * bloxdWorldLight(light), vec3f(0.0));
}

fn bloxdDefaultLight(surface: BloxdSurface, light: BloxdLightIn) -> BloxdLight {
    let lit = bloxdLitColour(surface, light);
    return BloxdLight(bloxdApplyFog(lit + surface.emission, light));
}
```
