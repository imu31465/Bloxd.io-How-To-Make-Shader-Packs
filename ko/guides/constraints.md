# 셰이더 팩으로 가능한 것과 불가능한 것

> 대상 API: 5 · 대상 빌드: `v98qt8` (2026-11-08, 프로덕션·preprod 확인) · 상태: Verified (현재 API로 이식됨 — 실기기 재확인 권장)

셰이더 팩의 리얼화 「천장」을 한 페이지에 정리한다: 현재 API가 어디까지 닿는지, 원리적으로 불가능한 것은 무엇인지, 조건부인 것은 무엇인지, 제한이 존재하는 이유, 그리고 가장 가까운 대체 수단. 만들기 시작하기 전에 여기서 구상한 표현이 실현 가능한지 확인한다.

## 현재 API로 가능한 것

- **면별 색·투명도·발광 제어** — 3개의 `Surface` 훅이 지형·액체·모델에 대해 색 (및 조건부 alpha 와 emission) 을 반환한다
- **조명의 완전한 재구축** — 3개의 `Light` 훅과 조명 API (`bloxdShading()` / `bloxdWorldLight()` / `bloxdLitColour()`) 가 엔진 자신의 레시피를 조합 가능한 함수로 공개한다 ([조명 API](../api/lighting.md))
- **블록 편집을 실시간으로 추종하는 투영풍 그림자** — `skyLight` 는 복셀 단위의 하늘 가림 데이터; 리프트 역변환 + 임계값 컷을 거치면 나무 밑·처마 밑의 선명한 그림자가 된다 ([그림자](shadows.md))
- **게임 자신의 텍스처 읽기** — `bloxdTexel()` 이 블록 텍스처 아틀라스와 모델 고유 텍스처를 엔진 샘플러와 정확히 같은 방식으로 샘플링한다 ([텍스처 API](../api/texture-api.md))
- **모델별 효과** — `flags` 가 「손에 든 아이템」「떨어진 아이템」「플레이어」「반 블록」임을 직접 알려준다 ([flags](../api/flags.md)); `localPosition` 이 모델 국소 좌표를 준다 ([입출력 구조체](../api/structures.md))
- **인챈트 글린트와 피격 플래시 오버레이** — `enchantTier` / `enchantColour` / `enchantSpeed` 와 `overlayColour` 를 읽고 덮어쓸 수 있다 ([인챈트 효과](../recipes/enchant-effects.md))
- **시간과 애니메이션** — `bloxdSeconds()`, 월드 좌표, 태양 방향이 움직임을 구동한다 ([시간과 애니메이션](../recipes/animation.md))

## 현재 API로 불가능한 것

| 표현 | 이유 |
|---|---|
| 픽셀 정밀 섀도맵 (태양 추종 그림자·반음영) | 깊이 텍스처를 참조할 수 없다 (액체 한정의 `bloxdOpaqueBehind()` 는 기하 정보뿐이라 섀도맵으로 쓸 수 없다). 광선 가림 판정도 훅에 입력되지 않는다 |
| SSAO | 씬 깊이에 접근 불가 (메셔가 구운 정점 AO만 있다; 액체 한정 깊이는 SSAO에 쓸 수 없다) |
| SSR (반사) | 씬색을 얻을 수 없다. 프레넬으로 하늘색을 섞는 유사 표현만 가능하다 |
| 블룸 / 글레어 | 포스트프로세스에 걸 수 있는 훅이 없다 |
| 피사계 심도·색수차·그레인 | 풀스크린 후처리가 필요하다 |
| 체적광 (god rays) | 마찬가지 |
| 커스텀 PBR 맵 (노멀 / 거칠기 / 금속도 텍스처) | 팩은 자신의 텍스처를 추가할 수 없다 — API는 `bloxdTexel()` 로 게임의 기존 텍스처를 *읽을* 뿐이며, 그것들은 PBR 채널 없는 평범한 색 텍스처다. 유사 PBR 응답은 색 휘도와 `flags` 에서 추정하는 수밖에 없다 ([텍스처 API](../api/texture-api.md)) |
| 수중 굴절 | 씬색을 얻을 수 없다. 액체 한정 깊이 (`bloxdOpaqueBehind()`) 로 두께 흡수와 바닥 투영은 가능하다 ([물을 자연스럽게 보이게 하기](water.md)) |
| 수중 베일 (파란 틴트)의 제거·변경 | 베일은 카메라가 들어 있는 액체 블록 정의 color/alpha에서 생성되는 emissive 풀스크린 quad로, 훅 파이프라인 밖 (최전면) 에 그려지므로 팩은 색도 농도도 바꿀 수 없다 |
| 수중 직접 검출 | 카메라의 잠수를 나타내는 입력이 없고, 수중에서도 fogStart / fogEnd / fogColour 가 변하지 않으므로 fogAlpha 등에서 수중을 추정할 믿을 만한 방법도 없다 |
| 하늘·구름·태양 원반 자체의 변경 | 훅은 지형/액체/모델 기하의 면마다 실행된다; 스카이박스는 어떤 훅 파이프라인에도 속하지 않는다 |

## 조건부 능력

- **버텍스 애니메이션과 `discard`** — 게임 정의가 명시적으로 `shaderPackPolicy: "allow"` 를 가진 타이틀에서만 가능; 그 외 모든 곳에서 `BLOXD_STRICT` 가 이 훅들을 컴파일에서 제외한다 ([게임별 셰이더 팩 정책](../internals/policy.md))
- **씬 깊이 (`bloxdOpaqueBehind()`)** — 액체 훅 한정이며 `BLOXD_SCENE_DEPTH` 가 필요; 지형·모델 훅에는 깊이 접근이 없다 ([함수](../api/functions.md))
- **`bloxdTexel()` / `bloxdTextureSize()`** — surface 와 light 훅 한정, 파이프라인에 텍스처가 있는 구성에서만 유효; 텍스처 없는 구성에서는 흰색을 반환하는 스텁으로 컴파일된다 ([텍스처 API](../api/texture-api.md))
- **지형 alpha (`BLOXD_ALPHA`)** — 그것을 정의하는 배리언트에서만 사용 가능하다 ([배리언트와 가드](../getting-started/variants.md))

## 이 제한들이 존재하는 이유

「진짜」 포스트프로세스 셰이더가 필요로 하는 네 종류의 입력이 구조적으로 존재하지 않는다:

1. **씬색 없음** — 훅은 각 면이 그려지는 동안 실행된다; 읽을 프레임버퍼 텍스처가 없으므로 SSR, 굴절, 「내 뒤에 무엇이 있는가」에서 파생되는 모든 계산이 불가능하다
2. **씬 깊이 없음** — 액체 한정의 `bloxdOpaqueBehind()` 기하 프로브가 유일한 예외; SSAO 와 섀도맵은 완전한 깊이 버퍼를 필요로 한다
3. **포스트프로세스 단계 없음** — 프레임 합성이 끝난 뒤에 실행되는 훅이 없으므로 블룸, DOF, 색수차, 그레인, god rays 에는 진입점이 없다
4. **하늘 접근 없음** — 스카이박스, 구름, 태양 원반은 훅 파이프라인 밖에서 그려지며, `bloxdSunDirection()` 외에 그것들을 기술하는 입력이 없다

수중 베일은 같은 구조의 특수 사례다: 카메라가 들어 있는 액체 블록 정의에서 생성되어 최전면에 그려지는 emissive 풀스크린 quad — 모든 훅 파이프라인의 바깥.

## 가장 가까운 대체 수단

| 원하는 것 | 팩 측의 가장 가까운 접근 |
|---|---|
| 반사 | 하늘빛에 가까운 색으로의 프레넬 가중 블렌드 + 태양 글린트 ([물을 자연스럽게 보이게 하기](water.md)) |
| PBR 머티리얼 | 휘도 기반 스페큘러/거칠기 추정 + `flags` 기반 머티리얼 분류 ([색](../recipes/colors.md), [리얼화](../recipes/realism.md)) |
| 블룸 / 발광 | emission 출력 — 더없이 진짜 가산 발광이지만 면 단위이지 포스트프로세스 블러가 아니다 ([발광](../recipes/emission.md)) |
| 앰비언트 오클루전 | `surface.colour` 에 이미 구워 들어간 메셔 정점 AO; skyLight 감소는 대규모 AO를 겸한다 ([그림자](shadows.md)) |
| 수심 흡수 | 액체 훅 안에서의 `bloxdOpaqueBehind()` 두께 + 바닥 투영 ([액체](../recipes/liquids.md)) |
| 수중 분위기 | 베일을 받아들이고, 그 너머로 보이는 것을 꾸민다 (지형/액체는 수중에서도 정상적으로 렌더링된다) |

## 그림자의 진실 — 「나무 그림자」는 만들 수 있다

위 표에서 불가능한 것은 **태양을 추종하는 픽셀 정밀 섀도맵** 뿐이다. 엔진은 처음부터 「그림자」를 계산하고 있으며, 그것이 `skyLight` 이다. 메시 측 LightEngine 은 마인크래프트풍 알고리즘을 돌린다:

1. **종렬 스캔**: 각 (x,z) 열을 위에서 아래로 훑는다. 하늘에서 오는 빛은 15에서 시작해 **불투명 블록에서 0** 이 되며, `lightFilter` (공기 1 / 물 3 / 불투명 15) 로 감쇠하면서 내려간다
2. **BFS 플러드필**: 6방향 이웃으로 옆으로 퍼진다 (블록당 -1) — 이것이 그림자 가장자리를 부드럽게 만드는 정체다. 반경 r 의 가림물 밑에서의 생값은 (15-r)/15
3. blockLight (횃불 등) 는 RGB 3채널 (4bit 팩) 의 별도 BFS다

즉 `l.skyLight` 는 단순한 밝기 파라미터가 아니라 **「그 장소에서 하늘이 보이는가」의 복셀 분해능 가림 데이터 = 섀도맵**이다. 나무 밑, 처마 밑, 실내는 수치가 이미 낮으며, 정점 보간으로 매끄러워진 채 도달한다. 블록을 놓거나 부수면 즉시 재계산된다 = **실시간 추종 그림자**. 바닐라는 이것을 `mix(앰비언트색, 하늘색, skyLight)` 로 「살짝」 섞어 쓸 뿐이다.

올바른 도구는 [그림자](shadows.md)의 2단계 (**리프트 역변환으로 생값 복원 → 임계값 `smoothstep` 으로 이값화**; `th = 1 - r/15` 로 「그림자로 간주할 가림 반경」을 직접 정한다) 에 **태양 직사광을 sky 로 게이트** (태양은 하늘이 보이는 곳에만 닿는다 = 투영의 본질) 를 더하고, 양지는 난색 / 그늘은 냉색으로 물들이는 구성이다.

**솔직한 제한**: 이 그림자는 「위쪽 하늘」 기준이므로 **태양이 시간에 따라 움직여도 회전하지 않는다**. 분해능은 블록 단위 (부드러운 가장자리는 BFS 확산에서 온다). 엔진 조명 템플릿에는 여전히 닫힌 채 남은 `var shadow: f32 = 1.;` 섀도맵 스텁 (항상 1.0 = 무효) 이 있으며 — 「계획되었던」 픽셀 정밀 회전 그림자의 흔적으로 해석된다. 픽셀 정밀 회전 그림자가 꼭 필요하다면 API 밖의 방법 (예: userscript GLSL 주입, 정책 리스크 있음) 만이 남는다.

## 수중의 실상

수중 겉모습은 3층으로 이루어진다:

| 층 | 내용 | 팩에서 다룰 수 있는가? |
|---|---|---|
| ① 지형/액체 그리기 | 훅으로 가공할 수 있다. light 훅은 수중에서도 평소처럼 호출된다 | 가능 (「베일 밑」에서 통한다) |
| ② 액체 정의색 베일 | 카메라 위치의 액체 블록 정의 color/alpha로 만든 emissive 풀스크린 quad, 최전면에 그려진다. 게임 설정 `cameraTint` 이 설정되어 있으면 그쪽이 우선한다 | 불가 (색도 농도도 바꿀 수 없다) |
| ③ cameraTint | 게임 설정 | 불가 |

실무 포인트: 팩은 수중에서도 계속 동작한다 / 베일은 없앨 수 없다 / 수중 여부로 분기할 수 없다 (fogStart / fogEnd / fogColour 는 수중에서 변하지 않으므로 fogAlpha 로도 검출할 수 없다).
