# パフォーマンスを考慮した実装

> 対象API: 5 · 対象ビルド: `ab90qa` · 検証状況: Verified (計測ベースの実践指針)

シェーダーパックはすべてのフラグメント (terrain / liquid / model の全ピクセル) で実行されるため、書き方次第でフレームレートが大きく変わります。ここでは計測に基づく指針をまとめます。

## 最初に知るべきこと

- **light フックはフラグメントの最終段**: terrain・liquid・model の描かれるすべてのピクセルで呼ばれます。画面の大部分がこれにあたります
- **パックは WebGPU レンダラーで実行**: モバイルを含む多様な GPU で動く前提でコストを評価する
- ローダのサイズ上限 (`.wgsl` 合計 256 KB) は「コンパイル時間」の実用上限でもあります

## コストの目安 (安い順)

| 操作 | コスト | 備考 |
|---|---|---|
| `mix` / `clamp` / 四則 | ◎ 最小 | |
| `l.skyLight` / `l.blockLight` 等の入力読み取り | ◎ | uniform/vertex属性由来 |
| `smoothstep` / `pow` | ○ | `pow` は指数で変わる |
| `sin` / `cos` | ○ | 波・アニメーションの基本部品 |
| `dot` / `normalize` | ○ | |
| `bloxdTexel()` (テクスチャサンプル) | △ | mip を上げると安い (縮小サンプル) |
| `dpdx` / `dpdy` / `fwidth` | △ | surface/light フックのみ |
| 分岐 (`if`) | △ | WGSL は両側を評価しうる。均一な条件 (フラグ判定) は安い |
| ハッシュ乱数 (多数の `sin`/`fract`) | △ | R9.8 マイクロバンプ等は距離で抑える |

## 実践的な指針

1. **効果を必要な面に限定する** — 「全部に +20% 明るく」より `flags` で選別 (例: `if (surface.flags.vegetation)`)。分岐コストより効果の節約が勝つ
2. **距離でディテールを落とす** — `distance(surface.position, bloxdEyePosition())` が閾値以上なら何もしない early-out。マイクロバンプ・ハッシュノイズ系は特に有効
3. **mip を使う** — `bloxdTexel(id, uv, mipLevel + 1.0)` は 1/4 解像度の平均として機能する ([テクスチャAPIの実働例](../api/texture-api.md#実働例))
4. **1つのフックで済むなら surface で** — light フックは最終段で全ピクセル。色調整だけなら surface フックに置く方が呼ばれ方が同じでも処理の性質上まとめやすい
5. **段階的に追加して FPS を比較する** — ディテールを少しずつ足し、実機で確認する ([実機テスト](testing.md))
6. **`#ifdef` ガードは実行コストに効かない** — 6バリアントはコンパイル単位。実行時の節約は距離・フラグ分岐で作る

## 計測の作法

- ブラウザの開発者ツール (パフォーマンスパネル / WebGPU 統計) でパック有無の FPS を比較
- 画面一杯に地形が見えるシーン (影が多い森など) と、水面部 (liquid フック) を別々に測る
- モバイル実機でも確認する — デスクトップの数十倍遅いことがある
