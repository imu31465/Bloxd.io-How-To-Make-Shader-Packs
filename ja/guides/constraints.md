# シェーダーパックにできること・できないこと

> 対象API: 5 · 対象ビルド: `bny9u` (2026-11-05 本番確認) · 検証状況: Verified (現行API移植済み — 動作は同一ビルドで実機確認を推奨)

現行APIの「天井」を1ページにまとめる: 何に到達でき、何が構造的に不可能で、何が条件付きなのか、その理由と、最も近い代替手法。作り始める前に表現の狙いが実現可能かをここで確かめられる。

## 現行APIにできること

- **面ごとの色・透明度・発光** — 3つの `Surface` フックが地形・液体・モデルそれぞれについて colour (と条件付きの alpha・emission) を返す
- **ライティングの全面的な再構築** — 3つの `Light` フックとライティングAPI (`bloxdShading()` / `bloxdWorldLight()` / `bloxdLitColour()`) がエンジン自身のレシピを合成可能な関数として公開している ([ライティング](../api/lighting.md))
- **ブロック編集にリアルタイム追従する投影型の影** — `skyLight` はボクセル解像度の空からの遮蔽データ。リフト反転 + 閾値カットで木の下や屋根の下くっきり暗くできる ([影の表現](shadows.md))
- **ゲーム側テクスチャの読み取り** — `bloxdTexel()` はエンジンのサンプラと同じ仕組みでブロックテクスチャアトラスやモデル固有テクスチャをサンプリングする ([テクスチャAPI](../api/texture-api.md))
- **モデル単位の演出** — `flags` に「これは手に持ったアイテム」「これはドロップ品」「これはプレイヤー」「これはスラブ」が入る ([フラグ](../api/flags.md))。`localPosition` でモデルローカル座標も直接分かる ([入出力構造体](../api/structures.md))
- **エンチャントきらめきと被弾フラッシュの制御** — `enchantTier` / `enchantColour` / `enchantSpeed` と `overlayColour` は読み取りも上書きもできる ([エンチャント効果](../recipes/enchant-effects.md))
- **時間とアニメーション** — `bloxdSeconds()`・ワールド座標・太陽方向で動きを作る ([時間とアニメーション](../recipes/animation.md))

## 現行APIにできないこと

| 表現 | 理由 |
|---|---|
| ピクセル精度のシャドウマップ (太陽とともに回転する影・ペナンブラ) | 深度テクスチャを参照できない (液体専用の `bloxdOpaqueBehind()` は幾何情報のみで、シャドウマップには利用できない)。光の視線に対する遮蔽判定はフックに入力されない |
| SSAO | シーンの深度にアクセスできない (AO はメシャーが頂点カラーにベイクしたもののみ。液体専用の深度は SSAO には利用できない) |
| SSR (反射) | シーンの色を取得できない。フレネル効果により空色を乗せる擬似的な処理のみ可能 |
| ブルーム / グレア | ポストプロセスにフックが存在しない |
| 被写界深度・色収差・グレイン | フルスクリーンの後処理が必要 |
| 体積光 (ゴッドレイ) | 同上 |
| 独自の PBR マップ (法線 / ラフネス / メタリックテクスチャ) | パックは独自のテクスチャを追加できない — APIはゲーム側の既存テクスチャの「読み取り」のみで、しかもそれらは PBR チャンネルを持たないプレーンなカラーテクスチャである。擬似PBRは色の輝度と `flags` から推定するしかない ([テクスチャAPI](../api/texture-api.md)) |
| 水中屈折 | シーン色は取れない。液体限定の深度 (`bloxdOpaqueBehind()`) で厚み吸収・底面投影は可能 ([水を自然に見せる方法](water.md)) |
| 水中ヴェール (青色のティント) の除去・変更 | ヴェールは「カメラが入っている液体ブロックの定義された color/alpha」から生成されるエミッシブなフルスクリーンクワッドであり、フックのパイプライン外 (最前面) に描画されるため、パックからは色も濃度も変更できない |
| 水中の直接検出 | カメラが水中にあるかどうかを示す入力がなく、水中でも fogStart / fogEnd / fogColour が変化しないため、fogAlpha などから水中を信頼できる形で推定する方法がない |
| 空・雲・太陽円盤そのものの変更 | フックは地形・液体・モデルのジオメトリについて面単位で走る。スカイボックスはどのフックパイプラインにも含まれない |

## 条件付きでできること

- **頂点アニメーションと `discard`** — 定義に `shaderPackPolicy: "allow"` を持つゲームのみ。それ以外では `BLOXD_STRICT` が定義され、該当フックはコンパイル時に無効化される ([ゲーム別の適用ポリシー](../internals/policy.md))
- **シーン深度 (`bloxdOpaqueBehind()`)** — 液体フックのみ、かつ `BLOXD_SCENE_DEPTH` が必要。地形・モデルフックに深度へのアクセスはない ([関数](../api/functions.md))
- **`bloxdTexel()` / `bloxdTextureSize()`** — surface / light フックのみ。またテクスチャを持つパイプラインでのみ実装され、テクスチャなし構成では白を返すスタブにコンパイルされる ([テクスチャAPI](../api/texture-api.md))
- **地形の alpha (`BLOXD_ALPHA`)** — バリアントがそれを定義している場合のみ ([バリアントとマクロガード](../getting-started/variants.md))

## 制約が生じる技術的な理由

「本物の」ポストプロセスシェーダーに必要な 4 つの入力が構造的に存在しない:

1. **シーン色がない** — フックは各面の描画中に走る。読めるフレームバッファテクスチャがないため、SSR・屈折・「背後に何があるか」由来の表現は計算できない
2. **シーン深度がない** — 液体専用の `bloxdOpaqueBehind()` ジオメトリ探査を除く。SSAO とシャドウマップにはフルの深度バッファが必要
3. **ポストプロセス段階がない** — フレーム合成後に走るフックは存在しない。ブルーム・被写界深度・色収差・グレイン・ゴッドレイに入り口がない
4. **空へのアクセスがない** — スカイボックス・雲・太陽円盤はフックパイプラインの外で描画され、`bloxdSunDirection()` 以外に入力がない

水中ヴェールは同じ構造の特殊ケース: カメラが入っている液体ブロックの定義から生成されるエミッシブなフルスクリーンクワッドが最前面に描かれ、どのフックパイプラインの外でもある。

## 最も近い代替手法

| 実現したいこと | パック側での最善策 |
|---|---|
| 反射 | フレネル重み付きで空色へ混ぜる + 太陽グリント ([水を自然に見せる方法](water.md)) |
| PBR マテリアル | 輝度ベースのスペキュラ/ラフネス推定 + `flags` による材質クラス分け ([色](../recipes/colors.md)・[リアル化](../recipes/realism.md)) |
| ブルーム / グロー | emission 出力 — 本物の加算グローだが、ポストプロセスのブラーではなく面単位 ([発光](../recipes/emission.md)) |
| アンビエントオクルージョン | `surface.colour` に既にベイク済みの頂点AO。skyLight 減光が大スケールAOを兼ねる ([影の表現](shadows.md)) |
| 水の深さによる吸収 | 液体フックでの `bloxdOpaqueBehind()` 厚み + 底面投影 ([液体](../recipes/liquids.md)) |
| 水中のムード | ヴェールは受け入れる。ヴェール越しに見えるもの (地形・液体は水中でも通常描画) を加工する |

## 影の真実 — 「木の影が落ちる」は作れる

上の表で実現不可能なのは**太陽とともに回転するピクセル精度のシャドウマップ**だけである。エンジンは当初から「影」を計算しており、それが `skyLight` である。メッシュ生成側の LightEngine は Minecraft 型のアルゴリズムで動作する:

1. **縦列スキャン**: 各 (x,z) 列を上から下へ走査。空からの光は 15 で開始し、**不透明ブロックで 0** となり、`lightFilter` (空気 1 / 水 3 / 不透明 15) で減衰しながら下降する
2. **BFS フラッドフィル (幅優先探索)**: 6 近傍へ横方向に拡散 (1 ブロックで -1) — これが影のエッジをソフトにする要因。半径 r の遮蔽物の下での生値は (15-r)/15 となる
3. blockLight (トーチ等) は RGB 3 チャンネル (4bit パック) の別 BFS

つまり `l.skyLight` は単なる明るさパラメータではなく、**「その位置から空が見えるか」を示すボクセル解像度の遮蔽データ = 影マップ**である。木の下・屋根の下・建物内部はすでに数値が低く、頂点補間により滑らかに伝達される。ブロックを設置または破壊すれば LightEngine が即座に再計算する = **リアルタイムに追従する影**である。バニラではこれを `mix(環境色, 空色, skyLight)` で「控えめに」使用するため、影が薄くなる。

使うべき道具は [影の表現](shadows.md) の2ステップ (**リフト反転で生値を復元 → `smoothstep` 閾値で2値化**。`th = 1 - r/15` で「影とみなす遮蔽半径」を直接調整) に、**sky による直射日光のゲート** (空が見える場所にしか太陽が届かない = 投影の本質)、そして暖色の日向 / 寒色の影色の組み合わせである。

**正直な限界**: この影は「上向きの空」ベースなので、**太陽の移動とともに回転はしない**。解像度はブロック単位 (ソフトなエッジは BFS 拡散による)。エンジンのライティングテンプレートにはシャドウマップ用の `var shadow: f32 = 1.;` スタブ (常に 1.0 = 無効) が閉じたまま残っている — 「予定されていた」ピクセル精度の回転影の痕跡と解釈される。ピクセル精度の回転影が必須なら、API 外の手段 (ユーザースクリプトによる GLSL 注入など、ポリシー上のリスクあり) しか残らない。

## 水中の正体

水中の見た目は 3 層からなる:

| 層 | 中身 | パックから操作できるか |
|---|---|---|
| ① 地形 / 液体の描画 | フックで処理される。Light フックは水中でも通常どおり呼ばれる | できる (「ヴェールの下」で動く) |
| ② 液体定義のヴェール | カメラ位置の液体ブロック定義の color/alpha から生成されるエミッシブなフルスクリーンクワッド。最前面に描画される。ゲーム設定 `cameraTint` があればそちらが優先 | できない (色も濃度も変更不可) |
| ③ cameraTint | ゲーム側の設定 | できない |

実務上の要点: パックは水中でも動き続ける / ヴェールは除去できない / 水中判定は分岐できない (fogStart / fogEnd / fogColour は水中でも変化しないため、fogAlpha からも検出できない)。
